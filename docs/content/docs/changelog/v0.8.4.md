[Release on GitHub](https://github.com/godot-pty/gpty/compare/v0.8.3...v0.8.4)

v0.8.4 is about making a pane describe itself: where it starts, what it runs, and what it is called. A terminal tile can carry a launch line that runs through your shell, a pane remembers its own directory, and a settings value outside its declared vocabulary is refused where it is written rather than silently normalized. The same pass gave the profile vocabulary one spelling - a *profile* is the named reusable tile arrangement, a *layout* is the grid inside one workspace - and moved the public verbs from `layout` to `profile`, with no alias left behind.

Under the surface the release is mostly hardening: the PTY input queue is bounded, the plugin store's reader is bounded and tolerates additive drift, the release job no longer runs project code with a write token, and `main` can no longer be pushed to directly.

## Added

- **A terminal pane can carry a launch command.** A tile may hold `launch`: one line, at most 1024 characters, trimmed, with no control characters and no U+FFFD. It is expanded when the pane's child is started, so it runs through your shell exactly as a pane command does - `omp update && omp` works, where a bare program name could not - and every path that starts a child reaches the same helper (restore, spawn, profile activation, a restored workspace), so there is no second spawn path that skips it. A launch line wins over the pane's `command` and `shell_args`. Pane Settings gained a **Launch command** field: it reads and writes the tile's launch line and nothing else, its placeholder is your shell while the line is empty, and its caption says it takes effect at this pane's next start rather than in the program already running. Save Profile's per-pane field became a launch line too, labelled with the pane's name, so typing `lazygit` saves a line that runs `lazygit` through the shell; Workspace Trust and the plugin install review name a launch line as something a restored file will run.
- **A pane remembers its own directory.** Pane Settings' directory row sets where this pane's child starts, and the workspace directory remains the fallback. The choice is stored in `user://pane_cwd.json` keyed by the workspace *and* the pane, because a pane id alone follows a profile from one repository into another; that needed a stable per-workspace id, so `workspaces.json` entries now carry one, minted on the first load of a store that lacks it and written straight back. Both child backends consult the same answer, and the Pane Settings "Inherits" line, the workspace picker and the two Rust edge docs read it too.
- **A settings rule can name a closed vocabulary.** A rule may carry `values`, checked after its length check, so a value outside the set is refused at every source: `pane-set` and `new-pane --setting` answer `-32602` naming the key, a saved tile drops it and the workspace reports it once, and the live pane keeps the value it had. `pane-settings` publishes `values` beside `kind`, `file` and `ipc`, so a caller can discover the set instead of guessing. The vocabularies moved to one owner - code-viewer languages and view modes, file-tree open modes, wiki view modes and the Inspector's backends - so the dropdown, the file reader and the socket each check the same list.
- **`scripts/install-cli` installs a release bundle behind a stable PATH link.** It copies an extracted directory or the release `.tar.gz` to `$GPTY_INSTALL_ROOT/<version>` (default `~/.local/opt/gpty`), repoints `current` at it, and links `gpty` and `gpty-gui` through `current`, so an upgrade is a swap rather than a link into a directory that a later cleanup deletes.
- **The defect classes have a counter.** `docs/content/docs/agents/defect-classes.md` names the 14 mechanisms the project keeps fixing and pairs each with the control that catches it, every `fix` commit now carries a `Cause:` trailer naming one, and `./scripts/fix-forensics` counts classes, hotspots and undeclared fixes over a range. 401 of 1255 commits on `main` are fixes; the first control it produced compares the grid caps that three files declare separately.

## Changed

- **The public verbs are `profile`, not `layout`.** `gpty profile save|load|list`, the MCP tools `profile-save` / `profile-load` / `profile-list` and the IPC methods `profileSave` / `profileLoad` / `profileList` replace the old spelling, and the old one is gone: **any script or agent that called `gpty layout save`, `gpty layout load`, `gpty layout list` or the `layout-*` tools must switch to `profile`** - there is no alias. The four layers that have to agree moved together (clap, the CLI's wire literals, the GDExtension method allowlist and the GUI's dispatch), and the doc comments on the three subcommands are the MCP tool descriptions.
- **One vocabulary for profiles and layouts.** The sidebar's entry point is "More profiles →" (the tool-profiles live in plugin repositories), the workspace-restore dialog opens "This saved workspace set contains N workspace(s) whose panes start a different program…" because a layout lives inside one workspace and the file being restored is the set, and the plugin review prints "no program (geometry only)" for a profile whose tiles carry nothing to run. A *profile* is the named reusable tile arrangement; a *layout* is the grid inside one workspace.
- **The built-in Agent Workspace no longer names OMP.** It is described as "A terminal beside an Inspector for private Q&A and a Reasoning pane for the agent's live commentary", wired with `agent-terminal`/`agent-inspector`/`agent-reasoning`, and the Inspector tile no longer pins a backend - its default happens to be OMP, the first adapter the observability panes support. The pane copy stopped naming a tool. The published twin, `godot-pty/gpty-agent-workspace`, carries the same three ids; **a saved layout or workspace keeps the ids it was saved with and is unaffected by the rename.**
- **The plugin ecosystem gains an `OMP Workspace` profile.** `godot-pty/gpty-omp` 0.2.0 ships a three-tile arrangement beside its single-pane `OMP` launcher: terminal running `omp`, Inspector on the `omp` backend, Reasoning following the terminal, with its own `omp-ws-*` ids so the two cannot collide.
- **A profile's grid unit survives a save and a load.** Profiles authored in a coarser grid are no longer silently treated as unit-1, and the unit is stamped by every producer - the Save Profile dialog, `profileSave`, the shipped defaults - so a profile written from live tiles cannot claim a unit it was not measured in.
- **Input that cannot be delivered is refused instead of queued forever.** Two bounded stages replace the unbounded ones: a 256-message queue into the PTY engine and a 16-chunk writer queue inside it. A pane whose child stops reading can no longer grow the process without limit; `gpty inject` answers a `refused` error when the queue is full and `broadcast` reports a `refused` count, so a caller learns the input did not land rather than assuming it did.
- **The plugin store tolerates additive drift from a newer writer.** A store written by a newer build is readable by an older CLI: an unknown *sibling* key is ignored at every level (file root, record, profile entry, concept entry), while a missing required field, a wrong type, a bad shape, a cap and the id/revision formats are still refused - so a renamed or removed field still fails, and tolerance covers only what was added.
- **A pane stops re-sanitizing what the settings table already sanitized.** All five pane bodies let the shared `apply_settings` do the assignments and keep only their live side effects, so a value is normalized once at the edge instead of twice with two chances to disagree.

## Fixed

- **A pane with no configured directory started in two different places.** A terminal's shell and a `cli_view`'s child received different answers when neither the pane nor the workspace named a directory - measured in a sandbox, `pwd` answered `/home/<user>` in a terminal and the project directory in a `cli_view`. Both now resolve the user's home explicitly, and one owner feeds the Pane Settings "Inherits" line, the workspace picker and the edge docs.
- **A scheme with fewer than 16 colours inherited the rest of the previous one.** The palette setter now assigns a complete 16-colour array - every valid entry fills its own slot, every other slot falls back to the system default - so a short or malformed scheme can no longer paint indices 4-15 with the colours of the scheme before it. Re-applying the current scheme costs no repaint.
- **Settings and the command palette keep a fixed height their content does not fill.** A centred card is sized to its content up to its design size and the window: filtering the palette from 15 rows to two shrinks the card downward and the query field never moves under the caret, and a short Settings tab no longer paints a dead band below its last row while a tall tab keeps the design height and scrolls. A palette replaced rather than patched also stops a stale row surviving its own replacement.
- **Every pane-bearing capture was a bare pane body.** The capture harness is a `-s` entry point, which compiles before autoloads exist, so a typed reference pulled an autoload into the compile and the entry point failed with `Identifier not found`; the image was still written, with every pane body a plain `Control`. The harness no longer reaches those symbols at compile time and the capture gate fails on a script error instead of saving the picture.
- **A code viewer re-read its file on every settings edit.** Editing the pane's name or font size re-read the document and reset the read-only editor's scroll and caret; the viewer now reloads only when the path itself moved.
- **A per-pane store was rewritten on every settings keystroke.** The settings panel re-applies its gathered dictionary on a 150 ms debounce, and the env store wrote the file each time even when the value was unchanged - so editing a pane's *name* re-wrote `user://pane_env.json` at typing speed. It now writes only on an actual change.
- **`paneSet` answered `changed: []` when a setting was cleared.** `pane-set <pane> --setting launch=` cleared the tile's launch line and reported success with no changed key, and setting one key could drop `shell`/`shell_args` from the read-back without saying so. The answer now walks the union of the before and after settings and names every key that appeared, disappeared or changed.
- **A plugin could not declare the four newest event types.** The manifest validator listed nine names while the event socket's vocabulary has ten, so a manifest subscribing to `session.shutdown`, `agent.settled`, `turn.finished` or `tool.finished` was refused as unknown. The vocabulary is now one shared array with a duplicate-name test, and a test pins the extension's wire table against it name-for-name.
- **The plugin store had no byte cap.** A planted tile array was read whole; the reader now takes at most the cap (16 MiB, the plugin count times the 64 KiB manifest cap) plus one byte and refuses a longer file before decoding it, and the GUI's two start-up readers go through the same function.
- **`pitfalls.md` is indexed by failure class.** The 126 flat bullets now sit under the 14 defect-class headings, each bullet's text unchanged, so a debugging session can read the ones that match the failure it is chasing.
- **Two demo clips showed a command line the script no longer types.** The showcase, cli-view and profiles clips were recaptured, and the recapture found four script defects - among them a seeded workspace that named no directory, so a `git status` demo listed the developer's own checkout.
- **The macOS bundle shipped FFmpeg built for a newer macOS than the app declares.** Measured from the v0.8.3 asset's Mach-O load commands: arm64 FFmpeg declared macOS 26.0 and x86_64 declared 15.0, while the Godot template itself is 11.0 / 10.13. The FFmpeg build now targets 11.0 and 10.13, `scripts/check-macos-minos` gates every slice in the bundler, and the x86_64 preset minimum moves to 10.13. The bundle also stopped shipping three real copies of every FFmpeg library: only the canonical file is kept and the aliases are recreated as symlinks. **That last part did not reach the archive**: `macos_libs` creates the aliases, but the artifact transport dereferences symlinks and FFmpeg's unversioned `libavcodec.dylib` is a real file that is lipo'd as a second canonical copy, so the shipped macOS zip still carries three real copies of each library (v0.8.3 95,698,840 → v0.8.4 96,084,344 bytes). The corrected bundler lands in the next release.
- **A release CLI installed by linking the download dangles after an upgrade.** A `~/.local/bin/gpty` left pointing into a cleaned-up directory failed with the same "Executable not found in $PATH" as a missing binary; the installer above replaced that pattern with one stable layout.
- **Security Insights is named `security-insights.yml`, so the OSPS scanner reads it.** The scanner behind LFX discovers only that name, so the project's declarations were reported absent; renamed, with the public repositories, the secret-scanning and gitleaks declarations, and the repository status filled in.
- **Nothing scanned the index or the history for secrets.** `scripts/check-secrets` refuses private-key blocks and cloud/token prefixes in the git index and runs in `ci-check --fast` (so the pre-commit hook runs it), and a scheduled gitleaks job scans the full history on push, on a pull request and weekly.
- **The release flow committed straight to `main`, and `main` could be pushed to directly.** `0.8.x` is now the integration branch, a `gpty-bot` GitHub App pushes it and opens the release pull request (it never approves or merges), and a `main` ruleset with no bypass actors requires a pull request, a code-owner review and the full check set. The app's grant is exactly contents, pull requests and metadata. The rest of the policy set is enforced too: DCO and Conventional Commits on a pull request, a signed annotated tag for every actor with no bypass, Dependabot updates targeting `0.8.x`, and full-SHA pinning for all 68 action references.
- **The release job executed the tagged tree with `contents: write` and OIDC.** It is split so no write or OIDC privilege is present while project code runs: a read-only gate validates the tag (format, signature, ancestry, versions, lockfiles, defect trailers, docs), a read-only job exports and uploads the archives, and only the publishing job holds the write token - it downloads the staged files, runs no project code, and waits on the `release` environment's required reviewer.
- **The macOS/Windows/docs CI tail.** The Windows build verifies its vcpkg FFmpeg version before packaging and records the port revision; the docs module moved to Go 1.27.4, Hextra 0.13.0 and Hugo 0.170.0, which is what the LFX security scan was reporting against.
