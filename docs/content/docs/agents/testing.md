- **UI/UX assessment method** - used by the UI re-baselines (v0.8.0 and v0.8.4) and the terminal fidelity probes (v0.9.1 and v0.9.2). Run the real app (the actual main scene, autoloads and Rust extension) in a private sandbox with a fresh first-run state, so no existing settings or layouts influence it; drive it through the committed capture harness (`scripts/ui-capture <state> <out-dir>`, staging table `godot/tests/bench/ui_capture.gd`), which seeds a named state through the real autoloads with synthetic clicks and key events and saves the app's own rendered viewport as PNG - never a desktop capture; `scripts/ui-capture --list` prints the states (first launch, sidebar, settings, pane settings, palette, empty workspace, 125 % UI scale at 1920×1080 and the same request in an 800×500 window, light workspace, light settings, 1280×760, 800×500, 560×340, wiki vault, wiki graph, concept editor, plugin review, save profile, workspace trust, agent badges), and a surface that needs auditing becomes a state in that table rather than another scratch driver. Keyboard reachability is part of the method: `scripts/ui-capture --audit-focus <state>` stages the same state and prints the focus owner, the visible dialog's own focus owner, whether Escape closes the surface, every visible `FOCUS_NONE` button, and the Tab order; a visible control with no keyboard path is a finding even when a shortcut or a mouse path exists. The Tab-order walk follows explicit `focus_next` rings and stops at the first one it enters, so on a surface whose first stop is inside a ring it prints that ring and not the rest - read `focusable=` and the mouse-only lines for the whole surface, and stage a state whose first focusable control is the surface you mean (the BUILD row *The focus audit stops inside the first keyboard ring* widens the walk). A capture needs a real display driver (`--headless` has no redraw pass), each launch is bounded (`CAPTURE_TIMEOUT`, default 120 s: a launch that never presents a frame is killed and fails its state instead of hanging the run or leaving a blank window behind), two runs of one state must be pixel-identical, and `scripts/ui-capture-check` asserts that plus that a perturbed control changes exactly one image (it needs a display, so it is not in `ci-check`) - a state that stages something animated must pin it for the same reason (`agent-badges` re-applies the badge and stops the pane's per-frame work: the spinner cycles at 8 fps and the attention pulse at 1.2 Hz, so a live one never repeats); small windows (800×500, 560×340) resize the root viewport, so the image is the layout at that size, not OS window behaviour; read the UI code to explain what the captures show and to count hard-coded styling; compute contrast as WCAG ratios from colour constants in the code or from sampled pixels. Mark each finding **verified** (reproduced in the running app, with a control where one mattered), **observed** (seen once or without a control) or **code** (read in the source, not exercised); roadmap rows use these words, plus *not tested* and *measured*. List what the assessment did not examine, and queue that list as a row instead of dropping it. Do not modify project files while assessing.
- **Tests own their temp artifacts.** Any test that binds a socket or writes a database, store directory or fake script creates a `tempfile::TempDir` in the test body and lets it drop (a helper that hands back a path must hand back the guard too — a bare `PathBuf` whose `TempDir` dropped at return is a leak with extra steps). Bind it to a name: `let _ = …` drops it immediately. `tempfile` is a dev-dependency of every crate that needs it, `std::env::temp_dir()` is where the guard lives, and `scripts/ci-check` runs both cargo test passes under an empty `TMPDIR` and fails the run if anything is still in it — so an unguarded test is caught by the first full gate, not by a full `/tmp` months later.
- Tests live in `godot/tests/` - `unit/` for pure-logic classes, `integration/` for scene-tree tests. A test that needs a pane's shell sets `SettingsManager.cfg_shell_command = SettingsManager.default_shell_command()` (never a literal `/bin/sh`: on Windows that is refused by `validate_executable` and the spawn fails as an engine error, which GUT counts as a test failure), and a test that needs exact bytes from a *child* builds its command line with `ShellFixtures.print_text()` (`godot/tests/helpers/shell_fixtures.gd`) - and a test that needs a *mode* to come from the child rather than from its shell spawns its pane with `ShellFixtures.no_line_editing_args()` (`bash --noediting`; the default shell sets DECSET 2004 around every line its readline edits, which made `test_bracketed_paste.gd` pass 3/3 even with the fixture's command line replaced by a bare `sleep 30`) - spawning through `Workspace._spawn_pane`, not `TerminalManager.spawn_pane`, because only the former parents the wrapper so `_ready` runs the shell - and a transition (on, then off) in that file uses `ShellFixtures.print_text_pair()`, since a holding fixture cannot be typed into a second time - or, when its child is spawned as argv instead of typed into a shell (a `cli_view` pane), with `ShellFixtures.print_text_argv()`: `print_text()` returns a *cmd.exe* command line, and on Windows argv hands that line to `cmd.exe /c`, which re-parses it - `\"` is not cmd syntax, so PowerShell received the script as a quoted *string* and printed it rather than running it (measured on `windows-smoke`), which is why the argv form names PowerShell directly there and keeps the shell on POSIX - and, when it *waits* for those bytes, waits for the shell to be printing first (a nonzero `idle_ms` in `get_status()`: a line typed into a console app that has not attached yet is read by nothing) and then gives the child's own startup a budget sized for a process launch rather than for the assertion. A cold `powershell.exe` on a Windows runner measured past the 10 s `test_bracketed_paste.gd` used to allow, which reported a cold start as "the mode never arrived" (`windows-smoke`).
- A test that compares a path **Rust produced** with a GDScript string must normalize separators: `std::fs::canonicalize` answers `\\?\C:\...` with backslashes on Windows while `user://`-globalized paths use `/`, so `ends_with("/name")` passes on Linux and fails on `windows-smoke` (measured 2026-11-01: `test_the_native_mirror_is_this_list`, one failing test of 902 while the mirror itself was correct). Compare the last component or replace `\` with `/` first - never the host's spelling.
- Mocking autoloads: Use `MockAutoloads.setup()` / `teardown()` in `before_each`/`after_each`.
- Persistence managers (`SettingsManager`, `ProfileManager`, `WorkspaceStore`) are mocked via `set_script()` on the existing autoload node, redirecting `_read_file`/`_write_file` to an in-memory Dictionary - avoids touching disk and preserves Godot 4 global name bindings. (`SettingsManager` etc. are static constants - never `free()` autoload nodes).
- Signal testing: GDScript lambdas cannot capture outer primitives. Use GUT's `watch_signals(node)` + `assert_signal_emitted(node, "signal_name")` instead of `node.signal.connect(func(): captured_var = true)`.
- Editor tests must *type*, not assign: a `TextEdit`/`CodeEdit` programmatic `text = …` goes through `_set_text(p_text, /*emit_signal=*/false)` and emits only `text_set` - `text_changed` is emitted for edits (`insert_text_at_caret`, `remove_text`, undo) and is **deferred, one frame later** (`call_deferred`; Godot 4.7.2, `scene/gui/text_edit.cpp`). So a test that assigned `text` and asserted a live preview or a dirty marker would assert nothing, and code that trusts the signal's timing would break on both counts - `wiki_pane.gd` recomputes its dirty state from the buffer instead, and `test_wiki_pane.gd`'s `_type_into()` driver (`select_all` + `insert_text_at_caret` + one process frame) is the way edits reach it in a test.
- Type checks: `body is SomeClass` requires a compile-time class name. For runtime type discrimination, use `body._pane_type()` string discriminators.
- A headless run cannot answer a UI question whose truth is a pointer or a paint. Under `--headless` Godot has no display driver: `Viewport.gui_get_hovered_control()` is null even over a plainly visible `Button` (measured 4.7.2), no tooltip ever appears, and `frame_post_draw` never fires. So a test of a hover, a tooltip or a popup asserts the inputs the engine reads rather than the outcome - the control's `mouse_filter` (a `MOUSE_FILTER_IGNORE` label is never a hover target), its `tooltip_text`/`get_tooltip()`, its `accessibility_name`, its `accessibility_live` - and the visible half is proven on a headed launch or by a `scripts/ui-capture` image of the state. This is why the agent-state badge's tooltip is pinned by `mouse_filter` plus the string in `test_agent_badges.gd` and its rendering by the `agent-badges` capture, while the pointer landing on the badge was verified once on the headed build.
- Accessibility is measured in two halves, because headless can prove neither the tree nor the reader: GUT asserts the metadata the app produces (`test_accessibility.gd`: `A11y.publish`'s node shape, pane identities, the terminal's `visible_text()`, and that no glyph-only button lacks an `accessibility_name`), `scripts/ui-capture --audit-accessibility <state>` prints a staged state's names/live modes/recorded values and the glyph buttons that have none (`unnamed=0` is the pass), and `scripts/accessibility-probe` walks the exposed AT-SPI tree of a rebuilt export (`./scripts/build` first; the Arch editor build has no AccessKit driver, and `A11y.screen_reader()` is false-unknown headless). The probe needs a display, a live at-spi bus and `org.a11y.Status.IsEnabled` (it sets and restores it), so it is not in `ci-check`. It also prints a report-only `a11y-values:` line (`text-interfaces`, `value-interfaces`, `marker-in-value`, `role-names`) that never gates the run: that line is how a later engine is graded on whether an element's value reaches AT at all. The `file-dialog` capture state walks the sidebar's workspace-directory button, so the picker's own frame is a captured surface; `--audit-focus file-dialog` covers its Escape and traversal.
- Headless resource leaks: GUT warnings about unfreed children and GDExtension `RID`/`ObjectDB` leaks are benign in headless mode - the dummy render server doesn't track GDExtension resources. Production renderer handles these correctly.
- A new `class_name` needs `godot --headless --path godot --import` before `gut-check` can see it: headless runs resolve global classes from `godot/.godot/global_script_class_cache.cfg`, which only the importer refreshes (that is why `ci-check` imports before GUT) - running `gut-check` alone right after adding a class fails with "Could not find type".
- The GUT gate is `./scripts/gut-check`, never the bare `godot -s addons/gut/gut_cmdln.gd` command (`ci-check` and `ci.yml` both call the script; CONTRIBUTING and the testing docs point at it). GUT exits 0 after a parse error aborts the run - measured 4 of 40 scripts, 1.3 s instead of 57 s, no Run Summary - so the script owns the command and judges the output instead: Godot parse/script-error lines fail it, the Run Summary must be present and end in `All tests passed!`, the reported script count must equal the `test_*.gd` files the gdirs hold, and every script must contribute at least one test. The script also owns the clock: it ends a run the moment a parse/script-error line appears (measured 2 s from launch to a FAIL that prints the line, where the old runner spent the whole timeout), and the deadline itself (default 600 s) escalates SIGTERM to SIGKILL, because Godot does not die on SIGTERM while a script waits - `timeout 300` was still alive with its Godot child after seven minutes (2026-11-02), which is how runs survived a 600 s cutoff. A run that produces no output for `GUT_STALL_TIMEOUT` (default 120 s) is a hang rather than a slow test - the suite starts a test every ~0.15 s and the longest single test waits 2.1 s - so it is killed well before the deadline and the failure names the last test started, its script, and the `-gselect` command that re-runs just that file (`GUT_STALL_TIMEOUT=0` disables the check). Adding a test directory means adding it to that script, not just to a command line: GUT does not recurse (`include_subdirectories` is off), and a `test_*.gd` nested below a gdir is reported as never-run rather than quietly skipped. The script also owns a **private endpoint and profile for the run**, which is not hygiene but the gate working at all: the suite spawns real panes, every instance binds the control *and* event endpoints, and one instance owns each - so a developer's open workspace used to make every pane-spawning test refuse its bind, set the test instance's shutdown flag and quit it mid-suite (measured 2026-10-14: 12 scripts, no Run Summary, which reads as a crash rather than as "close the app"). `GPTY_SOCKET` moves both listeners at once (the event path is derived from the control one; on Windows it is the pipe name), `XDG_RUNTIME_DIR`/`XDG_DATA_HOME`/`XDG_STATE_HOME` point at one 0700 temp dir the trap removes, and `GPTY_SECRET` is cleared so a developer's shell cannot make the test instance demand a secret no test client has. The suite's **user root** is the same sandbox: `GPTY_TEST_USER_DIR` is set on every platform, and it is the one seam both halves read - `BasePersistenceManager.resolve_store_path` redirects every `user://` store through it and the gdext `history_db_path` redirects the scrollback database the same way. Setting it on Unix too is deliberate (the XDG dirs already cover Godot's `user://` there): the normal Linux gate exercises the seam, so a Windows-only path cannot drift unnoticed. On Windows, where the XDG variables do nothing because Godot resolves `user://` through the Known Folder API, `LOCALAPPDATA`/`APPDATA` are sandboxed as well (the Rust state/data directories read them directly). The GUT run does **not** use `--log-file`: Godot's file logging is off by default (`debug/file_logging` is unset), so there is no engine log to move, and the gate's own log capture already holds stdout for its judgment. The smoke does use it (it needs a failure-time engine log); adding it to the GUT command was the only difference from the known-good Windows run and the step hung with both the MSYS and `cygpath` spellings, so it stays out until a Windows run pins that down. `GUT_TIMEOUT` (600 s) caps the Godot process so a hung suite fails the gate instead of holding the runner to the six-hour job cap; the script enforces it itself (SIGTERM, then SIGKILL), so it no longer depends on a `timeout` binary and stock macOS is bounded too. `-d` is not passed: Godot parses it as `--debug`, and a runtime error in a test then breaks into the interactive debugger - measured on Windows as a 1.7 GB flood of the same `Debugger Break` that stalled the suite until the timeout; without it GUT records the failure and the gate's own checks fail the run. Tests that need a filesystem path use `TestPaths.user_path(...)`, never `ProjectSettings.globalize_path("user://...")`: a bare `user://` path bypasses the seam and on Windows writes the developer's real profile. Do not add a second rule - `BasePersistenceManager.resolve_store_path` is the store half, `history_db_path` the gdext half, and `TestPaths.user_dir()` asks the same `user_root_override()` for the directory.
- The live pane-API smoke is `scripts/smoke_pane_api.py` - one harness for every platform, because the transport is the only difference between them (Unix socket vs named pipe; the event client is the same file over `open()`). `ci-check` and the Linux CI job run it with `python3`; the `windows-smoke` job on `windows-latest` runs the same file with `python`, which is the only place the Windows named-pipe control/event listeners and a real Windows pane (default shell `%COMSPEC%`) are exercised. GUT runs on both: the suite starts panes with `SettingsManager.default_shell_command()` and asks `ShellFixtures.print_text()` for a command line that emits exact bytes on either platform (POSIX `printf '%b'`, Windows PowerShell `[Console]::Write`), so the `windows-smoke` job runs `scripts/gut-check` too (under Git Bash - the gate is one bash script for both platforms). Windows gaps pend rather than fail, and each pend names its gap (a fake adapter written as a POSIX shell script; a world-writable file mode, which is not a Windows notion; the three `gpty_state` declaration tests, where ConPTY consumes the OSC): `gut-check` prints every pending test and fails on `[Risky]` (a test that ran without asserting), so an explicitly-pended platform gap cannot hide a suite that stopped asserting. Pending is a Windows-only allowance: outside Windows `gut-check` fails on any `[Pending]` test, because there it can only mean a skip nobody decided on (the extension is a build requirement, so a test that needs `GptyAi` or `GptyCliView` asserts it is present instead of standing down). A step that waits for a program the pane has to *launch* sizes its budget for that launch, not for the round trip the step is about: `node` outran the 10 s the extension step used to allow on `windows-smoke` (the pane tail held the echoed command line and nothing else, `idle_ms` ~9.8 s), so the step reported "the event never arrived" for a Node.js that was still starting - the same lesson as the GUT fixture's cold `powershell.exe`. The `cli_view` step runs in the same harness: it creates a pane through `new-pane --type cli_view --command <program> --arg …` and asserts the child's stdout arrives in `pane-read`, which is what proves the argv spawn surface live on whichever platform runs the smoke. The concept step seeds one concept into the run's sandboxed user root before launch - the only registration route that exists, since `concept toggle` flips a shipped rule rather than adding one; the concept triggers on a marker the shell builds at runtime (the trigger demands the appended digit, so no typed line can match it), and the step asserts the routed `{type: concept, name, target}` event on the event socket. That is the Windows proof for the ConPTY parser fix: the event can only come from a committed *output* line, which is exactly what ConPTY's cursor-move line breaks used to suppress. The final step seeds a plugin record into the sandboxed state store and asserts `layout list` offers the plugin's profile and `layout load` restores its tile, which is the live proof of the profiles migration's read path: store → `installed_plugin_profiles()` → `ProfileManager` → `layoutList`/`layoutLoad`. Every one of those steps is also a CLI teardown sample, and the pane-status stage adds one deliberately: 100 throwaway `pane-status` processes (≈ 200 connections - each process opens the best-effort `version` probe and then its command), the amplifier for the one Windows `STATUS_HEAP_CORRUPTION` (`0xC0000374`) the smoke saw on an `inject`; a nonzero exit fails there with its hex status, and it is never retried.
- The fuzz harness is `fuzz/`: its own cargo-fuzz workspace (nightly, own lockfile, not a repository member) with seven targets — the terminal grid and line parser, the IPC request framing, vault links, the Markdown renderer, the AI backend's bounded line reader, and the media probe. Run one with `cargo +nightly fuzz run <target>` after `source dist/ffmpeg/linux-x86_64/env.sh` if the media target is in the set. `ci.yml`'s `fuzz-build` job compiles every target on each pull request, so a target that stops compiling fails the change that did it; `.github/workflows/fuzz.yml` runs each for five minutes nightly and on dispatch with `-max_len=65536 -timeout=10 -rss_limit_mb=2048`, and uploads `fuzz/artifacts` on failure. LeakSanitizer is on — its report on the media target found the AVIO buffer leak fixed in v0.7.2 — so a new leak is a red run, not a silent one. It is not part of `ci-check` (nightly plus minutes per target); the local gate for a harness change is `cargo fuzz build` plus a short run of the affected target.
- Dependency policy is two tools with separate owners: `cargo audit --deny warnings` covers advisories (RustSec), and `cargo deny check` covers everything in `deny.toml` - the licence allow-list plus named exceptions, crates.io-only sources, `yanked = "deny"`, duplicate versions as a warning, and `[graph] all-features` so the checked graph matches CI. Both run in `ci-check`; CI runs cargo-deny through `EmbarkStudios/cargo-deny-action` (SHA-pinned) in its own job. A new dependency outside the policy fails with the crate named; the fix is a decision, not a config edit - allow the licence if the project can ship it, add a named exception with its reason (the FFmpeg bindings' WTFPL), or drop the dependency. The supply-chain posture is also read back by the `Scorecard` workflow (`.github/workflows/scorecard.yml`): weekly, on a default-branch push and on a protection-rule change, it uploads SARIF to the Security tab and publishes to the OpenSSF API; the first run after a push is the baseline. `dependabot.yml` keeps the SHA-pinned actions and the two lockfiles moving.
- The audit re-check is `scripts/audit-probes.py` (`--list`, `--only <name>`): one probe per proof of concept from the October 2026 security audit, each printing the observation it judged (exit codes, byte counts, RSS growth) and a PASS/SKIP/FAIL verdict, so the next review starts from a script instead of prose. It imports the smoke's harness rather than duplicating it (sandbox, launch, CLI, raw RPC), and it is not part of `ci-check` - it launches the GUI several times and is a review tool, not a gate - while the Linux-only steps SKIP on Windows instead of failing. It serves the v0.7.1 roadmap row "Re-run the audit on the fix build and cover what it did not reach"; a new proof of concept belongs there as a probe, not as a paragraph.
- `rust-windows` runs two test binaries, not one: the DACL suite below, and `cargo test -p gpty-ipc` for the named-pipe arm. The pipe-claim test is written `#[cfg(any(windows, test))]`, so it also runs on Unix - the claim sequence is two atomics - but the Windows job is what proves the arm compiles there and the suite passes on the platform it protects.
- Windows process hardening (`crates/gpty-core/tests/windows_hardening.rs`) is its own integration-test binary, run by the `rust-windows` job (`cargo test -p gpty-core --test windows_hardening`): it drops `SeDebugPrivilege` first (an enabled privilege overrides any process DACL, so it models a normal pane rather than an elevated debugger), asserts the default process DACL grants `PROCESS_VM_READ` (the before state a pane program uses), that `harden_process()` turns that same open into `ERROR_ACCESS_DENIED`, that the installed DACL read back through `GetSecurityInfo` has one owner ACE without memory or thread-injection rights, and that `PROCESS_QUERY_LIMITED_INFORMATION` (the control socket's peer-check mask) and `PROCESS_TERMINATE` still open. It prints the token SID and privilege state, and a separate binary is required because the DACL is process-wide; the GUI and a `gpty mcp` client are covered end-to-end by the smoke's Windows branch.
- Media backend tests (`crates/gpty-media/tests`): committed fixtures generated from FFmpeg's `lavfi` sources cover every allowed container/codec (H.264/HEVC/VP9/AV1/Theora video; Vorbis/Opus/FLAC/MP3/AAC/PCM audio). They assert probe metadata, packed RGBA/PCM output at the requested rate/channels, seek landing at or after the target, the path gate, clean refusal of garbage/truncated files, close-while-queued (no deadlock), and the two seam checks - `build_recipe.rs` (components.txt ↔ runtime allowlists) and `binding_rules.rs` (banned FFmpeg APIs). The close *bound* is a unit test in `src/session.rs` instead, because it arms a `#[cfg(test)]` seam that stands in for a libavcodec call which never consults the stop flag and an integration test cannot see a `cfg(test)` item; it times the drop at ~2 s while the worker is still inside the seam, then releases the call and checks the detached thread exits by itself; the same seam holds a *seek* under 500 ms while the worker is parked (measured: 1 µs, where the old acknowledgement wait hit its 5 s deadline), then releases the call and asserts the seek applies and no pre-target frame is delivered - the two tests share the global seam through `stuck::lock()` because `cargo test` runs them on parallel threads. They link the pinned FFmpeg: run `./scripts/media-deps` first (every CI job that compiles or loads the extension does).
- Seam contract tests: a contract written in one module and implemented in another needs a test that reads both sides, never a copy of the other side written into the test - the copy passes while the shipped code drifts. `crates/gpty-cli/src/commands/mcp.rs` parses the real IPC registrations (`ipc.rs`), the real dispatch (`ipc_handlers.gd`'s `handle` arms plus the `method ==` intercepts in its `dispatch_request`) and every `client.call` literal under `src/commands/`, and asserts they agree with the advertised MCP tool names; `crates/gpty-cli/src/commands/wire.rs`'s `wire_keys_are_the_keys_the_handlers_read` translates one sample call per tool and checks every emitted key against the `params.get(...)` keys its handler reads (the GDScript arms, the `paneWait`/`pluginInstall` branches in `dispatch_request`, and the native vault handlers), which is the seam that let `new-pane`'s `pane_type` be dropped while both sides' tests stayed green; `godot/tests/integration/test_ipc_dispatch_contract.gd` drives `WorkspaceIpcHandlers.handle` and a whole drained batch through `dispatch_request` against a real `Workspace` (one instance for the script: each schedules a deferred concept push that must land while it is alive) instead of reimplementing the handlers, and `scripts/smoke_pane_api.py` proves `pane-read`'s scrollback claim live, where output timing is real.
- A docs-class push runs no code CI. `ci.yml` ignores `docs/**`, `**/*.md`, `godot/knowledge.json`, `LICENSE` and the two scripts that are the docs gates themselves (`scripts/docs-check`, `scripts/build-wiki`) (`paths-ignore` skips only when every changed path matches, so a mixed commit still runs the full suite); the Docs workflow is that push's gate - it builds the site, runs `scripts/docs-check` and verifies the knowledge bundle with `scripts/build-wiki --check`, which is the only CI job that checks the bundle is current. A script joins that list only when the Docs workflow runs its gate; every other script builds the app, drives Godot, or runs a gate, so it needs the code jobs. Everything else - workflows, any other script, crates, `godot/`, the smoke - still gets the full eight-job run (~4 minutes warm, longer when the Windows vcpkg tree rebuilds). Rust and Godot are never split: the GDExtension is one boundary, so a change on either side runs both suites. `scripts/ci-check` makes the same split locally: a docs-class change runs just `docs-check` and the knowledge-bundle check, because the pre-push hook hands it the pushed range (a manual run falls back to the unpushed commits, `--fast` to the index, and an unknown range to the full suite); `CI_CHECK_FULL=1` forces everything, and `./scripts/ci-check --classify` prints the changed set, each path's class and the suite it selects without running anything. The pre-push hook runs that check *before* the ref moves, so an interrupted or timed-out hook aborts the push and the commits stay local: allow several minutes for a code change and run no second Godot suite (GUT, a benchmark, the smoke) while it works - both spawn real panes and timing-sensitive tests share the machine.
