- **UI/UX assessment method** - used by the UI re-baselines (v0.8.0 and v0.8.5) and the terminal fidelity probes (v0.9.1 and v0.9.2). Run the real app (the actual main scene, autoloads and Rust extension) in a private sandbox with a fresh first-run state, so no existing settings or layouts influence it; drive it through the committed capture harness (`scripts/ui-capture <state> <out-dir>`, staging table `godot/tests/bench/ui_capture.gd`), which seeds a named state through the real autoloads with synthetic clicks and key events and saves the app's own rendered viewport as PNG - never a desktop capture; `scripts/ui-capture --list` prints the states - the table is the owner, so this page does not count or copy them, and a state added or renamed shows up there; a state may also carry `"tab": "<name>"` to open a Settings state on that tab rather than System (`light-settings` uses it for the Appearance tab, where the theme and UI-scale controls live), and a surface that needs auditing becomes a state in that table rather than another scratch driver. Keyboard reachability is part of the method: `scripts/ui-capture --audit-focus <state>` stages the same state and prints the focus owner, the visible dialog's own focus owner, whether Escape closes the surface, every visible `FOCUS_NONE` button, and the Tab order; a visible control with no keyboard path is a finding even when a shortcut or a mouse path exists, and a `FOCUS_NONE` control whose action is reached from somewhere else declares itself with `KeyboardFocus.declare_mouse_only(control, reason)` - the audit prints it as a `mouse-only button` with that reason and counts only the undeclared ones as `unaccounted=`. An open overlay's controls are snapshotted before the Escape that closes it, so its own rows are named instead of counted as zero. The Tab-order walk follows explicit `focus_next` rings and stops at the first one it enters, so on a surface whose first stop is inside a ring it prints that ring and not the rest - read `focusable=` and the mouse-only lines for the whole surface, and stage a state whose first focusable control is the surface you mean (the BUILD row *The focus audit stops inside the first keyboard ring* widens the walk). A capture needs a real display driver (`--headless` has no redraw pass), each launch is bounded (`CAPTURE_TIMEOUT`, default 120 s: a launch that never presents a frame is killed and fails its state instead of hanging the run or leaving a blank window behind), two runs of one state must be pixel-identical, and `scripts/ui-capture-check` asserts that plus that a perturbed control changes exactly one image (it needs a display, so it is not in `ci-check`) - a state that stages something animated must pin it for the same reason (`agent-badges` re-applies the badge and stops the pane's per-frame work: the spinner cycles at 8 fps and the attention pulse at 1.2 Hz, so a live one never repeats); small windows (800×500, 560×340) resize the root viewport, so the image is the layout at that size, not OS window behaviour; read the UI code to explain what the captures show and to count hard-coded styling; compute contrast as WCAG ratios from colour constants in the code or from sampled pixels. Mark each finding **verified** (reproduced in the running app, with a control where one mattered), **observed** (seen once or without a control) or **code** (read in the source, not exercised); roadmap rows use these words, plus *not tested* and *measured*. List what the assessment did not examine, and queue that list as a row instead of dropping it. Do not modify project files while assessing. `scripts/ui-capture-check`'s perturb target defaults to `settings` when the list has it, else the first named state (`--perturb` overrides); a state with neither overlay nor pane cannot be the target (exit 2, so `ui-capture-check empty-workspace` cannot run alone), and each state costs three launches. Synthetic input is WINDOW space: `Input.parse_input_event` does not apply the content scale while a Control's `get_global_rect()` is layout space, so `ui_capture.gd`'s `_click` maps through `root.get_final_transform()` (unscaled, the `settings-terminal-150` state could not open Settings; the transform is identity at 100 %, so 100 % captures are byte-identical). A small-window state cannot stage its empty workspace through `close_all` - the click lands on the clipped pane section at 560x340 - so `empty-workspace-560x340` seeds the zero-pane store state instead.
- **Tests own their temp artifacts.** Any test that binds a socket or writes a database, store directory or fake script creates a `tempfile::TempDir` in the test body and lets it drop (a helper that hands back a path must hand back the guard too — a bare `PathBuf` whose `TempDir` dropped at return is a leak with extra steps). Bind it to a name: `let _ = …` drops it immediately. `tempfile` is a dev-dependency of every crate that needs it, `std::env::temp_dir()` is where the guard lives, and `scripts/ci-check` runs both cargo test passes under an empty `TMPDIR` and fails the run if anything is still in it — so an unguarded test is caught by the first full gate, not by a full `/tmp` months later. Shared `static` state is the same class: a test that mutates a queue or map must clear it on every exit path - timeout, error and panic included - through one `clear_state()` helper, or a stale entry breaks the next test. The process environment is the other global: `gpty-ipc`'s transport tests guard `GPTY_SOCKET`/`XDG_RUNTIME_DIR` through one `EnvVar` lock that restores the previous value on drop, and an unlocked `set_var`/`remove_var` pair failed a real `ci-check` parallel run.
- Tests live in `godot/tests/` - `unit/` for pure-logic classes, `integration/` for scene-tree tests. A test that needs a pane's shell sets `SettingsManager.cfg_shell_command = SettingsManager.default_shell_command()` (never a literal `/bin/sh`: on Windows that is refused by `validate_executable` and the spawn fails as an engine error, which GUT counts as a test failure), and a test that needs exact bytes from a *child* builds its command line with `ShellFixtures.print_text()` (`godot/tests/helpers/shell_fixtures.gd`) - and a test that needs a *mode* to come from the child rather than from its shell spawns its pane with `ShellFixtures.no_line_editing_args()` (`bash --noediting`; the default shell sets DECSET 2004 around every line its readline edits, which made `test_bracketed_paste.gd` pass 3/3 even with the fixture's command line replaced by a bare `sleep 30`) - spawning through `Workspace._spawn_pane`, not `TerminalManager.spawn_pane`, because only the former parents the wrapper so `_ready` runs the shell - and a transition (on, then off) in that file uses `ShellFixtures.print_text_pair()`, since a holding fixture cannot be typed into a second time - or, when its child is spawned as argv instead of typed into a shell (a `cli_view` pane), with `ShellFixtures.print_text_argv()`: `print_text()` returns a *cmd.exe* command line, and on Windows argv hands that line to `cmd.exe /c`, which re-parses it - `\"` is not cmd syntax, so PowerShell received the script as a quoted *string* and printed it rather than running it (measured on `windows-smoke`), which is why the argv form names PowerShell directly there and keeps the shell on POSIX - and, when it *waits* for those bytes, waits for the shell to be printing first (a nonzero `idle_ms` in `get_status()`: a line typed into a console app that has not attached yet is read by nothing), and a test that asserts a scroll *offset* waits for the child to stop printing first - a scrolled-back pane anchors its view to late output, so a line arriving between the scroll and the assertion moves the offset by that many lines (`windows-smoke` measured 44 → 88 while `cmd.exe` was still flushing, and the sentinel read as the defect under test) - and then gives the child's own startup a budget sized for a process launch rather than for the assertion. A cold `powershell.exe` on a Windows runner measured past the 10 s `test_bracketed_paste.gd` used to allow, which reported a cold start as "the mode never arrived" (`windows-smoke`).
- A test that compares a path **Rust produced** with a GDScript string must normalize separators: `std::fs::canonicalize` answers `\\?\C:\...` with backslashes on Windows while `user://`-globalized paths use `/`, so `ends_with("/name")` passes on Linux and fails on `windows-smoke` (measured 2026-11-01: `test_the_native_mirror_is_this_list`, one failing test of 902 while the mirror itself was correct). Compare the last component or replace `\` with `/` first - never the host's spelling. The same Windows-only class of failure is a multi-line string literal: the repo sets no `eol` attribute and the runner checks out with `core.autocrlf` on, so a `"""…"""` expectation carries CRLF while the code under test emits `"\n"`, and the two print identically in GUT's `[Failed]` block (`test_feedback_text.gd` failed `windows-smoke` this way while Linux passed). Build expectations by joining lines with `"\n".join(...)`. The third member of the class is a path a **child process printed**: Godot's own paths use `/` even on Windows (`path_join`, `OS.get_user_data_dir`) while `cmd` reports its cwd with `\`, so `get_text().contains(workspace_cwd)` compared two spellings of the same directory and failed `windows-smoke` while the payload proved the child had started in the right place (`test_the_child_starts_in_the_panes_directory`, 2026-11-15). Normalize both sides (`path.replace("\\", "/")`) and put the expected value plus the pane's `start_error()` in the assertion, so the message says which half was wrong.
- Mocking autoloads: Use `MockAutoloads.setup()` / `teardown()` in `before_each`/`after_each`. `setup()` also seeds the integration baseline the old first run produced: one `Workspace 1` holding one terminal. The app's own first run has no workspace and no pane (the first pane creates `Default`), so a test of that state overrides `WorkspaceStore.FILE` with `{"active": 0, "workspaces": []}`, and a test that clears the store adds a workspace before touching `_workspaces[0]` (see `test_layout_restore._make_workspace`). `MockAutoloads` hands out the live store, so a "the store did not change" assertion can compare an array against itself (`get_store` returns the stored Dictionary and a manager returns its array by reference); snapshot with `.duplicate(true)` in any test that claims a refused call left a store unchanged, and never hand a live member to a save (`_save_settings_file` passing `cfg_sidebar_folded` itself meant a later `.clear()` emptied the stored list).
- Persistence managers (`SettingsManager`, `ProfileManager`, `WorkspaceStore`) are mocked via `set_script()` on the existing autoload node, redirecting `_read_file`/`_write_file` to an in-memory Dictionary - avoids touching disk and preserves Godot 4 global name bindings. (`SettingsManager` etc. are static constants - never `free()` autoload nodes).
- Signal testing: GDScript lambdas cannot capture outer primitives. Use GUT's `watch_signals(node)` + `assert_signal_emitted(node, "signal_name")` instead of `node.signal.connect(func(): captured_var = true)`.
- Editor tests must *type*, not assign: a `TextEdit`/`CodeEdit` programmatic `text = …` goes through `_set_text(p_text, /*emit_signal=*/false)` and emits only `text_set` - `text_changed` is emitted for edits (`insert_text_at_caret`, `remove_text`, undo) and is **deferred, one frame later** (`call_deferred`; Godot 4.7.2, `scene/gui/text_edit.cpp`). So a test that assigned `text` and asserted a live preview or a dirty marker would assert nothing, and code that trusts the signal's timing would break on both counts - `wiki_pane.gd` recomputes its dirty state from the buffer instead, and `test_wiki_pane.gd`'s `_type_into()` driver (`select_all` + `insert_text_at_caret` + one process frame) is the way edits reach it in a test.
- A test that asserts a terminal pane's title or tooltip must set and read it in one call. A tile follows its child's OSC title while the child runs, and cmd.exe reports `Administrator: C:\Windows\system32\cmd.exe` as soon as ConPTY starts, so a test that sets a name, awaits frames and then reads it can read the shell's title instead - `windows-smoke` run 43617896053 failed exactly that way, and `test_small_window.gd` now sets and reads synchronously (the assertions are the label's layout, not title precedence).
- Type checks: `body is SomeClass` requires a compile-time class name. For runtime type discrimination, use `body._pane_type()` string discriminators.
- A perf claim about an interaction needs a **windowed** run, and one repetition is not a number: the synchronous GDScript cost plus the frame it delays does not exist headless, and the first workspace switch after launch measured 551 ms against a 63-75 ms steady state (2026-11-09, five workspaces; that comparison is `switch_bench`'s `cold` sample now, and the one-shot turned out to be the arriving workspace's unstarted panes, not the switch path). Time the call with `Time.get_ticks_usec()` marks around each step and the frame after it with `await get_tree().process_frame`, repeat at least three times and attribute every step before theorising; the recipe is `skill://gpty-live-gui-smoke` (body at `.omp/skills/gpty-live-gui-smoke/SKILL.md`)'s "Timing an interaction", the pane's own `_fetch_ms`/`_draw_ms` (read them off the body; the status bar prints FPS only) cover the frame half, and `godot/tests/bench/draw_bench.gd` measures render cost alone - `forced_us` for a full repaint, `row_us` for one row's bands, `overlay_us` for the cursor layer, and `BENCH_FLOOD=1`/`BENCH_SPARSE=1` for a full-screen or one-line stream (`sync_us` = fetch + repaint per damage sync, `avg_rows` = rows repainted, `backoff_ms` = the pane's cadence back-off; the stream modes force no repaint, so the file also runs against a pre-split pane). The same shape is `godot/tests/bench/switch_bench.gd` for a workspace switch, with its two payloads behind `SWITCH_CMD_A`/`SWITCH_CMD_B` and the window behind `SWITCH_WINDOW`; it settles both panes (non-empty screen, quiet grid) before the measured loop and fails on a switch into an empty pane, which is how it read 37 ms for a switch whose real cost was 992 ms. A `-s` launch under `--headless` clamps the root to 64x64 and no pane starts its child, so the bench never exercises the path it means to time: a harness that needs real tiles runs windowed, as `godot/tests/bench/spawn_bench.gd` does (per-spawn `sync_us` and child-resolved `total_us` as the grid fills to 64 panes, the slope between them, RSS and `children` per milestone, and one attribution line per whole-window pass).
- A GPU shader effect's cost is a **frame time, not a delta**: under `--disable-vsync` a Godot run is bound by `max(CPU, GPU)`, so at 1080p the harness itself floors at ~215 µs and a cheaper shader cannot be isolated by subtracting a plain run - that subtraction understates the effect whenever only the plain run is CPU-bound. Drive the shader at 4K (or a larger offscreen `SubViewport`) so the GPU is the limiter and read the frame time as the GPU cost; measured 2026-11-15 on the RTX 5070 Ti (Vulkan, offscreen): the CC0 smoke/FBM tree at 8 octaves cost 0.29 ms at 1080p and 1.02 ms at 4K, a 4-octave sin-free variant 0.33 ms at 4K. `godot/tests/bench/effect_bench.gd` is that measurement for the shipped terminal effects (`BENCH_EFFECT=crt|grain|none`, `BENCH_SIZE`, `BENCH_FRAMES`): it prints the plain-rect baseline and the effect's median frame time on the same rect, and it must run on a real GPU - a session that falls back to llvmpipe measures software cost only and cannot replace a declared budget.
- **The README's cost table is a published claim with an owner.** `scripts/measure-cost` re-measures the five rows the README prints (idle one pane, zero panes, first launch, OpenGL3 warm, the 30,000-line scrollback delta) by launching the built app in a `scripts/ui-sandbox` sandbox and sampling `VmRSS` from its own `/proc/<pid>/status` at steady state - median of five readings after the control socket answers a `list-panes`, with the spread printed to stderr beside each row's pane count. `--check` fails past 10% on a row (`MEASURE_TOLERANCE`), past that run-to-run noise on the scrollback delta, and when the Forward+/OpenGL3 ratio drops below the "Nx lighter" ratio the prose claims, because a table that moves while the sentence does not leaves the README contradicting itself. It needs a Linux GPU session - under `--headless` there is no renderer, so the figures do not exist there - and a `./scripts/build` output, never a debug build. `--stamp` is the half `ci-check` and a docs-class push run: it compares the table's "measured on the shipped vX.Y.Z" line against the crate version and needs no GPU, so a release bump cannot leave the table naming the previous release. Taking the measurement is a release step (`skill://release`, body at `.omp/skills/release/SKILL.md`); the figures also appear on gpty.dev, because the docs build mirrors `README.md` (its `readfile` shortcode rewrites `docs/static/images/` to `/images/`, so a README image works on both surfaces). The README's chart is generated, not drawn: `docs/data/cost-history.json` is the ledger (`--record` appends one entry per release) and `scripts/render-cost-chart` renders it to `docs/static/images/cost-history.svg`, with `--check --require-current` failing in `ci-check` when the SVG is stale or the ledger lacks the version being released - no display needed, so the picture cannot drift from the table it sits under. **An attribution needs an A/B**: before calling a release-to-release delta a regression, build the previous tag and measure it on the same machine with the same harness - the v0.8.1-vs-v0.8.2 investigation (2026-11-13) traced the OpenGL3 row's apparent 25% growth and the scrollback row's 31% to a capture that did not reproduce on either build, and found the real change was 7 MB of startup cost (649 to 656). Inspect a chart edit with `rsvg-convert -o /tmp/chart.png docs/static/images/cost-history.svg`: the sandboxed image reader draws shapes but no text, so it cannot answer a layout question. `--release-dir` measures a shipped archive the same way, and `scripts/backfill-cost-history` walks a folder of them; two eras need handling there - v0.7.0+ ships `gpty-gui` beside a separate `gpty` CLI, earlier releases ship one GUI binary (`godopty` at v0.1.0) with no CLI, and v0.1.0/v0.2.0 predate the control socket entirely, so those measure the launch as it opens rather than a pane count. A pre-0.3.x socket is bound with the caller's umask and the current CLI refuses a 0644 socket on purpose; the harness tightens the file (the sandbox is 0700) rather than weakening the client.
- A headless run cannot answer a UI question whose truth is a pointer or a paint. Under `--headless` Godot has no display driver: `Viewport.gui_get_hovered_control()` is null even over a plainly visible `Button` (measured 4.7.2), no tooltip ever appears, and `frame_post_draw` never fires. So a test of a hover, a tooltip or a popup asserts the inputs the engine reads rather than the outcome - the control's `mouse_filter` (a `MOUSE_FILTER_IGNORE` label is never a hover target), its `tooltip_text`/`get_tooltip()`, its `accessibility_name`, its `accessibility_live` - and the visible half is proven on a headed launch or by a `scripts/ui-capture` image of the state. The cursor shape itself is readable on a headed run without a human: a throwaway `-s` probe moves the pointer with `Input.parse_input_event` and reads `Input.get_current_cursor_shape()` after each step - that is how the v0.8.3 resize row was proven (HSIZE over the divider's band, still HSIZE immediately after a drag, ARROW over the pane body), and the probe is deleted afterwards. This is why the agent-state badge's tooltip is pinned by `mouse_filter` plus the string in `test_agent_badges.gd` and its rendering by the `agent-badges` capture, while the pointer landing on the badge was verified once on the headed build.
- A headless layout probe starts at a 64×64 viewport, and a headed launch's size is not `--resolution`: `godot --headless -s res://script.gd` instantiates the real `main.tscn` into a root viewport of `(64, 64)` (measured 4.7.2, 2026-11-08), so a probe of pane geometry measures a 38×38 tile and a terminal keeps its spawn grid rather than the fitted one - set `root.size = Vector2i(1920, 1080)` and `await process_frame` before adding the scene. The windowed app sizes itself from `SettingsManager.cfg_window_size`/the project setting instead of the flag: `--resolution 1600x900` still laid out a 1920×1080 workspace (the pane rects were 1738×1030, then 868×1030 after a split), so a probe that needs one window size sets it through the setting. That is the `-s` probe's viewport; the headless **app's own** root viewport is 0×0, so a size or layout claim made there is a claim about `_apply_layout`'s zero-rect fallback, not the real window (see the headless-GUI bullet in `pitfalls.md`).
- Accessibility is measured in two halves, because headless can prove neither the tree nor the reader: GUT asserts the metadata the app produces (`test_accessibility.gd`: `A11y.publish`'s node shape, pane identities, the terminal's `visible_text()`, and that no glyph-only button lacks an `accessibility_name`), `scripts/ui-capture --audit-accessibility <state>` prints a staged state's names/live modes/recorded values and the glyph buttons that have none (`unnamed=0` is the pass), and `scripts/accessibility-probe` walks the exposed AT-SPI tree of a rebuilt export (`./scripts/build` first; the Arch editor build has no AccessKit driver, and `A11y.screen_reader()` is false-unknown headless). The probe needs a display, a live at-spi bus and `org.a11y.Status.IsEnabled` (it sets and restores it), so it is not in `ci-check`. It also prints a report-only `a11y-values:` line (`text-interfaces`, `value-interfaces`, `marker-in-value`, `role-names`) that never gates the run: that line is how a later engine is graded on whether an element's value reaches AT at all. One thing in that log does gate it: the probe fails a run whose app output carries `Accessibility updates are only allowed` - the engine's refusal of a write made outside the control's own accessibility update. The `file-dialog` capture state walks the workspace row's **More → Set Directory**, so the picker's own frame is a captured surface; `--audit-focus file-dialog` covers its Escape and traversal. The probe's `REQUIRED` names are the current chrome's controls, and a menu item is only published while its popup is open - that is why the title bar contributes `More pane actions` and not the `Minimize pane` item inside that menu. The probe injects its marker through a `gpty` CLI (`GPTY_CLI`, else `gpty` on `PATH`, else `target/release/gpty`) and exits 3 without one - a run that cannot type the marker cannot assert the half it exists for - and it prints its first non-empty `Text` answers as `a11y-text:` lines. GUT reaches the gated push path through `A11y.force_enabled`, because headless has no accessibility driver.
- Headless resource leaks: GUT warnings about unfreed children and GDExtension `RID`/`ObjectDB` leaks are benign in headless mode - the dummy render server doesn't track GDExtension resources. Production renderer handles these correctly. The exception is a cycle the app itself owns: a `RefCounted`/`GDScript` entry in the list (not a `Node`, not a RID) survives a plain `godot --headless --quit-after N` run with no test harness at all, and that is a real defect, not headless noise - reproduce it there and read `pitfalls.md`'s owner/helper rule before dismissing it.
- A new `class_name` needs `godot --headless --path godot --import` before `gut-check` can see it: headless runs resolve global classes from `godot/.godot/global_script_class_cache.cfg`, which only the importer refreshes (that is why `ci-check` imports before GUT) - running `gut-check` alone right after adding a class fails with "Could not find type".
- The GUT gate is `./scripts/gut-check`, never the bare `godot -s addons/gut/gut_cmdln.gd` command (`ci-check` and `ci.yml` both call the script; CONTRIBUTING and the testing docs point at it). To run scoped tests while developing, pass a script filter directly (e.g. `./scripts/gut-check test_test_paths.gd`, `./scripts/gut-check -s <script> -t <test_name>`, or `./scripts/gut-check --dir unit`), which runs inside the full sandbox (`XDG_*` and `GPTY_TEST_USER_DIR` redirection) with stall and parse-error monitoring. If a bare invocation is unavoidable, pair `-gtest=` with `-gconfig=`: `.gutconfig.json`'s `dirs` still apply, so `-gtest=<one file>` alone runs the whole suite (measured 2026-11-08: 9 tests in 1.2 s with `-gconfig=`, 87 scripts / 1071 tests in 140 s without), while `gut-check`'s own stall message prints the `./scripts/gut-check --select <name>` recipe that narrows correctly. Use `-gdir=res://tests/unit -gselect=<filename substring>`: `-gselect` matches *script* names, so a test name there fails with "Could not find script matching" and runs nothing - narrow to one test with `-gunit_test_name=<test function>` beside it - and a bare invocation needs the same sandbox (the endpoint, user-root and secret variables below), or the run meets a developer's live GUI on the socket. GUT exits 0 after a parse error aborts the run - measured 4 of 40 scripts, 1.3 s instead of 57 s, no Run Summary - so the script owns the command and judges the output instead: Godot parse/script-error lines fail it, the Run Summary must be present and end in `All tests passed!`, the reported script count must equal the `test_*.gd` files the gdirs hold, and every script must contribute at least one test. The script also owns the clock: it ends a run the moment a script/parse error appears **before any test has started** (after that, a runtime error is GUT's to attribute and the run finishes so its failing-test list can be printed; measured 2 s from launch to a FAIL that prints the line, where a doomed run spent the whole timeout), and the deadline itself (default 600 s) escalates SIGTERM to SIGKILL, because Godot does not die on SIGTERM while a script waits - `timeout 300` was still alive with its Godot child after seven minutes (2026-11-02), which is how runs survived a 600 s cutoff. A run that produces no output for `GUT_STALL_TIMEOUT` (default 120 s) is a hang rather than a slow test - the suite starts a test every ~0.15 s and the longest single test waits 2.1 s - so it is killed well before the deadline and the failure names the last test started, its script, and the `-gselect` command that re-runs just that file (`GUT_STALL_TIMEOUT=0` disables the check). Adding a test directory means adding it to that script, not just to a command line: GUT does not recurse (`include_subdirectories` is off), and a `test_*.gd` nested below a gdir is reported as never-run rather than quietly skipped. The script also owns a **private endpoint and profile for the run**, which is not hygiene but the gate working at all: the suite spawns real panes, every instance binds the control *and* event endpoints, and one instance owns each - so a developer's open workspace used to make every pane-spawning test refuse its bind, set the test instance's shutdown flag and quit it mid-suite (measured 2026-10-14: 12 scripts, no Run Summary, which reads as a crash rather than as "close the app"). `GPTY_SOCKET` moves both listeners at once (the event path is derived from the control one; on Windows it is the pipe name), `XDG_RUNTIME_DIR`/`XDG_DATA_HOME`/`XDG_STATE_HOME` point at one 0700 temp dir the trap removes, and `GPTY_SECRET` is cleared so a developer's shell cannot make the test instance demand a secret no test client has. The suite's **user root** is the same sandbox: `GPTY_TEST_USER_DIR` is set on every platform, and it is the one seam both halves read - `BasePersistenceManager.resolve_store_path` redirects every `user://` store through it and the gdext `history_db_path` redirects the scrollback database the same way. Setting it on Unix too is deliberate (the XDG dirs already cover Godot's `user://` there): the normal Linux gate exercises the seam, so a Windows-only path cannot drift unnoticed. On Windows, where the XDG variables do nothing because Godot resolves `user://` through the Known Folder API, `LOCALAPPDATA`/`APPDATA` are sandboxed as well (the Rust state/data directories read them directly). The GUT run does **not** use `--log-file`: Godot's file logging is off by default (`debug/file_logging` is unset), so there is no engine log to move, and the gate's own log capture already holds stdout for its judgment. The smoke does use it (it needs a failure-time engine log); adding it to the GUT command was the only difference from the known-good Windows run and the step hung with both the MSYS and `cygpath` spellings, so it stays out until a Windows run pins that down. `GUT_TIMEOUT` (600 s) caps the Godot process so a hung suite fails the gate instead of holding the runner to the six-hour job cap; the script enforces it itself (SIGTERM, then SIGKILL), so it no longer depends on a `timeout` binary and stock macOS is bounded too. `-d` is not passed: Godot parses it as `--debug`, and a runtime error in a test then breaks into the interactive debugger - measured on Windows as a 1.7 GB flood of the same `Debugger Break` that stalled the suite until the timeout; without it GUT records the failure and the gate's own checks fail the run. Tests that need a filesystem path use `TestPaths.user_path(...)`, never `ProjectSettings.globalize_path("user://...")`: a bare `user://` path bypasses the seam and on Windows writes the developer's real profile. Do not add a second rule - `BasePersistenceManager.resolve_store_path` is the store half, `history_db_path` the gdext half, and `TestPaths.user_dir()` asks the same `user_root_override()` for the directory. A fixture directory whose name is the same on two runs is created with `TestPaths.fresh_dir("name")`, never `user_path()` plus `make_dir_recursive_absolute`: it deletes the leftover first, so a teardown that was refused (or an interrupted run) cannot make a fixed name inherit another test's files. `TestPaths.is_safe_path_under(path, root, windows)` is the bounds rule the helper and `remove_tree` share, and `normalize_path` unifies the Windows drive separator before comparing: a `C:\` root from `GPTY_TEST_USER_DIR` and a `/`-joined child must normalise to the same spelling, because `String.simplify_path()` keeps the drive separator as written - `test_a_windows_drive_root_accepts_its_children` pins that on Linux, and a comparison must never edit a real path's bytes (a root that ends in a space is the same class).
- A harness that waits for work done off the frame must wait on wall time, never on a frame count: `scripts/ui-capture` runs Godot with `--disable-vsync`, where 120 frames can be ~0.2 s, so a capture state that waits for a `WorkerThreadPool` build polls `Time.get_ticks_msec()` against a deadline (~10 s) and the owner's own task id (`ui_capture.gd`'s `wiki-graph` state waits on `body._graph_task`) - a 120-frame loop failed while the build was still running. The same class of trap is script mode: `godot -s <script>` compiles that script's dependencies *before* the project's autoloads are registered, so a script that references another script naming an autoload (even through a typed field, e.g. `WikiPane` -> `KnowledgeStore`) fails to load with `Identifier not found: <Autoload>`; load it by path after `await process_frame` and keep the field untyped, as `godot/tests/bench/graph_bench.gd` does. Resolve an autoload through `root.get_node("SettingsManager")` - the nodes are present under `root.get_children()`, only their names as identifiers are missing - and never annotate a `-s` bench with an app class: `var tm: TerminalManager` or `body is TerminalPane` compiles that file into the load, where its autoload-dependent field fails and takes the whole script with it. `ui_capture.gd` duck-types (`"_terminal" in body`) and finds autoload-dependent nodes by script path for this reason; the v0.8.4 row **The capture harness compiles before autoloads, so pane-bearing states capture bare pane bodies** removed the last typed app class (`AgentBadge`) from it, and `scripts/ui-capture` now fails a capture whose log contains `SCRIPT ERROR` or `Failed to load script`, because such a run still writes a PNG.
- An engine error raised inside a test fails it: GUT reports it under `Unexpected Errors`, and passing assertions elsewhere do not save the test. A test that deliberately feeds invalid input must therefore avoid a logging API - `JSON.parse_string("")` logs `Condition "error != Error::OK"`, which failed `test_backend_choice.gd` on 2026-11-12 - and use the checked form instead (`JSON.parse` plus its error code, as `BackendChoice.roster` does). An assertion is not a guard: `assert_eq`/`assert_not_null` return void and the next line runs even when the assertion failed. Index or dereference only behind an explicit return - `var dialogs := _dialogs_of(pane)`, `assert_eq(dialogs.size(), 1, "…")`, `if dialogs.is_empty(): return`, then `dialogs[0]` - and guard a cast the same way (`if x == null: return`, as `test_inverse_paint.gd` does). `scripts/check-test-guards` fails a suite file that indexes a call's result directly (`_list_meta(pane)[0]`, `get_signal_parameters(...)[0]`): that shape cannot be guarded in place, and it is how three `dialogs[0]` reads raised `Out of bounds get index '0'` on `windows-smoke` run 44648884305. `gut-check` now lets an error GUT has attributed to a test finish the run and reports it as that test's failure with Godot's `at:` location and GUT's own per-test list; a run it cannot judge (collection-time parse error, no Run Summary, a stall) is reported separately as "not trustworthy". Comparing values of different types is the same class (`value == "@terminal"` on an `int` raises `Invalid operands`), and Godot 4 names `Range`'s bounds `min_value`/`max_value`. Rust's `godot_error!` **and** `godot_warn!` also arrive at GUT as engine errors (`PrintLevel::Warn` goes through `push_warning`'s logger arm), so a Rust-side refusal that is a handled outcome logs with `godot_print!`; warn/error is reserved for conditions the app does not handle.
- The live pane-API smoke is `scripts/smoke_pane_api.py` - one harness for every platform, because the transport is the only difference between them (Unix socket vs named pipe; the event client is the same file over `open()`). `ci-check` and the Linux CI job run it with `python3`; the `windows-smoke` job on `windows-2025` runs the same file with `python`, which is the only place the Windows named-pipe control/event listeners and a real Windows pane (default shell `%COMSPEC%`) are exercised. GUT runs on both: the suite starts panes with `SettingsManager.default_shell_command()` and asks `ShellFixtures.print_text()` for a command line that emits exact bytes on either platform (POSIX `printf '%b'`, Windows PowerShell `[Console]::Write`), so the `windows-smoke` job runs `scripts/gut-check` too (under Git Bash - the gate is one bash script for both platforms). Windows gaps pend rather than fail, and each pend names its gap (a fake adapter written as a POSIX shell script; a world-writable file mode, which is not a Windows notion; the three `gpty_state` declaration tests, where ConPTY consumes the OSC): `gut-check` prints every pending test and fails on `[Risky]` (a test that ran without asserting), so an explicitly-pended platform gap cannot hide a suite that stopped asserting. A platform-gated test therefore calls `pending("<the gap>")`, never a bare `return`: a return with no assertion is `[Risky]`, which fails the gate (`test_a_real_terminal_child_starts_in_the_pane_directory` did exactly that on 2026-11-15 and reddened `windows-smoke` with every test passing). Pending is a Windows-only allowance: outside Windows `gut-check` fails on any `[Pending]` test, because there it can only mean a skip nobody decided on (the extension is a build requirement, so a test that needs `GptyAi` or `GptyCliView` asserts it is present instead of standing down). A step that waits for a program the pane has to *launch* sizes its budget for that launch, not for the round trip the step is about: `node` outran the 10 s the extension step used to allow on `windows-smoke` (the pane tail held the echoed command line and nothing else, `idle_ms` ~9.8 s), so the step reported "the event never arrived" for a Node.js that was still starting - the same lesson as the GUT fixture's cold `powershell.exe`. The `cli_view` step runs in the same harness: it creates a pane through `new-pane --type cli_view --command <program> --arg …` and asserts the child's stdout arrives in `pane-read`, which is what proves the argv spawn surface live on whichever platform runs the smoke. The concept step seeds one concept into the run's sandboxed user root before launch - the only registration route that exists, since `concept toggle` flips a shipped rule rather than adding one; the concept triggers on a marker the shell builds at runtime (the trigger demands the appended digit, so no typed line can match it), and the step asserts the routed `{type: concept, name, target}` event on the event socket. That is the Windows proof for the ConPTY parser fix: the event can only come from a committed *output* line, which is exactly what ConPTY's cursor-move line breaks used to suppress. The final step seeds a plugin record into the sandboxed state store and asserts `profile list` offers the plugin's profile and `profile load` restores its tile, which is the live proof of the profiles migration's read path: store → `installed_plugin_profiles()` → `ProfileManager` → `profileList`/`profileLoad`. Every one of those steps is also a CLI teardown sample, and the pane-status stage adds one deliberately: 100 throwaway `pane-status` processes (≈ 200 connections - each process opens the best-effort `version` probe and then its command), the amplifier for the one Windows `STATUS_HEAP_CORRUPTION` (`0xC0000374`) the smoke saw on an `inject`; a nonzero exit fails there with its hex status, and it is never retried.
- The fuzz harness is `fuzz/`: its own cargo-fuzz workspace (nightly, own lockfile, not a repository member) with seven targets — the terminal grid and line parser, the IPC request framing, vault links, the Markdown renderer, the AI backend's bounded line reader, and the media probe. Run one with `cargo +nightly fuzz run <target>` after `source dist/ffmpeg/linux-x86_64/env.sh` if the media target is in the set. `ci.yml`'s `fuzz-build` job compiles every target on each pull request, so a target that stops compiling fails the change that did it; `.github/workflows/fuzz.yml` runs each for five minutes nightly and on dispatch with `-max_len=65536 -timeout=10 -rss_limit_mb=2048`, and uploads `fuzz/artifacts` on failure. The repository `rust-toolchain.toml` pins stable 1.96.0, so a bare `cargo fuzz` resolves stable and fails with `-Z is only accepted on the nightly compiler`; select nightly explicitly for every fuzz command (`cargo +nightly ...` locally, and `RUSTUP_TOOLCHAIN=nightly-2026-11-01` on the `fuzz-build` and scheduled-workflow steps). LeakSanitizer is on — its report on the media target found the AVIO buffer leak fixed in v0.7.2 — so a new leak is a red run, not a silent one. It is not part of `ci-check` (nightly plus minutes per target); the local gate for a harness change is `cargo fuzz build` plus a short run of the affected target. The lockfile is its own: a workspace crate addition also changes `fuzz/Cargo.lock`, so run `cargo metadata --format-version 1 --manifest-path fuzz/Cargo.toml` before the gate or `ci-check` fails its drift check (observed 2026-11-12 when `gpty-plugin` was added).
- A fuzzer built with `cargo fuzz build` aborts at startup under ASAN's default options: `AddressSanitizer: odr-violation` naming `aiOff` in `libsqlite3-sys`'s SQLite amalgamation (measured 2026-11-20 on `fuzz/target/x86_64-unknown-linux-gnu/release/*`). The duplicate registration is benign, and OSS-Fuzz's runner already sets `detect_odr_violation=0`; run one locally with `ASAN_OPTIONS=detect_odr_violation=0` or it stops before the first input.
- Dependency policy is two tools with separate owners: `cargo audit --deny warnings` covers advisories (RustSec), and `cargo deny check` covers everything in `deny.toml` - the licence allow-list plus named exceptions, crates.io-only sources, `yanked = "deny"`, duplicate versions as a warning, and `[graph] all-features` so the checked graph matches CI. Both run in `ci-check`; CI runs cargo-deny through `EmbarkStudios/cargo-deny-action` (SHA-pinned) in its own job. A new dependency outside the policy fails with the crate named; the fix is a decision, not a config edit - allow the licence if the project can ship it, add a named exception with its reason (the FFmpeg bindings' WTFPL), or drop the dependency. The supply-chain posture is also read back by the `Scorecard` workflow (`.github/workflows/scorecard.yml`): weekly, on a default-branch push and on a protection-rule change, it uploads SARIF to the Security tab and publishes to the OpenSSF API; the first run after a push is the baseline. `dependabot.yml` keeps the SHA-pinned actions and the two lockfiles moving. Both lockfiles are audited — the workspace's and `fuzz/Cargo.lock` — and each is preceded by a `cargo metadata --locked` sync check so a stale file fails instead of being silently re-resolved: GitHub's dependency graph reads both, and a stale fuzz lock is how `RUSTSEC-2026-0459` (`libsqlite3-sys` 0.28.0) scored Scorecard's Vulnerabilities check down while the root audit was green.
- The audit re-check is `scripts/audit-probes.py` (`--list`, `--only <name>`): one probe per proof of concept from the October 2026 security audit, each printing the observation it judged (exit codes, byte counts, RSS growth) and a PASS/SKIP/FAIL verdict, so the next review starts from a script instead of prose. It imports the smoke's harness rather than duplicating it (sandbox, launch, CLI, raw RPC), and it is not part of `ci-check` - it launches the GUI several times and is a review tool, not a gate - while the Linux-only steps SKIP on Windows instead of failing. It serves the v0.7.1 roadmap row "Re-run the audit on the fix build and cover what it did not reach"; a new proof of concept belongs there as a probe, not as a paragraph.
- `rust-windows` runs two test binaries, not one: the DACL suite below, and `cargo test -p gpty-ipc` for the named-pipe arm. The pipe-claim test is written `#[cfg(any(windows, test))]`, so it also runs on Unix - the claim sequence is two atomics - but the Windows job is what proves the arm compiles there and the suite passes on the platform it protects.
- Windows process hardening (`crates/gpty-core/tests/windows_hardening.rs`) is its own integration-test binary, run by the `rust-windows` job (`cargo test -p gpty-core --test windows_hardening`): it drops `SeDebugPrivilege` first (an enabled privilege overrides any process DACL, so it models a normal pane rather than an elevated debugger), asserts the default process DACL grants `PROCESS_VM_READ` (the before state a pane program uses), that `harden_process()` turns that same open into `ERROR_ACCESS_DENIED`, that the installed DACL read back through `GetSecurityInfo` has one owner ACE without memory or thread-injection rights, and that `PROCESS_QUERY_LIMITED_INFORMATION` (the control socket's peer-check mask) and `PROCESS_TERMINATE` still open. It prints the token SID and privilege state, and a separate binary is required because the DACL is process-wide; the GUI and a `gpty mcp` client are covered end-to-end by the smoke's Windows branch.
- Media backend tests (`crates/gpty-media/tests`): committed fixtures generated from FFmpeg's `lavfi` sources cover every allowed container/codec (H.264/HEVC/VP9/AV1/Theora video; Vorbis/Opus/FLAC/MP3/AAC/PCM audio). They assert probe metadata, packed RGBA/PCM output at the requested rate/channels, seek landing at or after the target, the path gate, clean refusal of garbage/truncated files, close-while-queued (no deadlock), and the two seam checks - `build_recipe.rs` (components.txt ↔ runtime allowlists) and `binding_rules.rs` (banned FFmpeg APIs). The close *bound* is a unit test in `src/session.rs` instead, because it arms a `#[cfg(test)]` seam that stands in for a libavcodec call which never consults the stop flag and an integration test cannot see a `cfg(test)` item; it times the drop at ~2 s while the worker is still inside the seam, then releases the call and checks the detached thread exits by itself; the same seam holds a *seek* under 500 ms while the worker is parked (measured: 1 µs, where the old acknowledgement wait hit its 5 s deadline), then releases the call and asserts the seek applies and no pre-target frame is delivered - the two tests share the global seam through `stuck::lock()` because `cargo test` runs them on parallel threads. They link the pinned FFmpeg: run `./scripts/media-deps` first (every CI job that compiles or loads the extension does).
- Seam contract tests: a contract written in one module and implemented in another needs a test that reads both sides, never a copy of the other side written into the test - the copy passes while the shipped code drifts. `crates/gpty-cli/src/commands/mcp.rs` parses the real IPC registrations (`ipc.rs`), the real dispatch (`ipc_handlers.gd`'s `handle` arms plus the `method ==` intercepts in its `dispatch_request`) and every `client.call` literal under `src/commands/`, and asserts they agree with the advertised MCP tool names; `crates/gpty-cli/src/commands/wire.rs`'s `wire_keys_are_the_keys_the_handlers_read` translates one sample call per tool and checks every emitted key against the `params.get(...)` keys its handler reads (the GDScript arms, the `paneWait`/`pluginInstall` branches in `dispatch_request`, and the native vault handlers), which is the seam that let `new-pane`'s `pane_type` be dropped while both sides' tests stayed green; `godot/tests/integration/test_ipc_dispatch_contract.gd` drives `WorkspaceIpcHandlers.handle` and a whole drained batch through `dispatch_request` against a real `Workspace` (one instance for the script: each schedules a deferred concept push that must land while it is alive) instead of reimplementing the handlers, and `scripts/smoke_pane_api.py` proves `pane-read`'s scrollback claim live, where output timing is real.

- A pane-type swap in a *workspace* test goes through `Workspace._swap_pane_now`, never `TerminalManager.swap_pane`: the manager replaces the tile's body and frees the old wrapper, while the grid surgery that removes and re-attaches it lives in the workspace transaction - the manager alone left the grid holding a freed wrapper and the next swap raised `Condition "p_child->data.parent != this" is true` from `remove_child` (2026-11-08). A bare `TerminalManager` with no workspace, as `test_pane_spawning.gd` uses, is fine.
- A pane close is not a one-frame event: the transition layer removes the tile at once (the sidebar, IPC and `tiles` report the pane gone) but frees the body when its exit finishes. A test that closes a pane waits for the body by polling `is_instance_valid` against a deadline instead of awaiting one frame - `test_pane_close_guard.gd`'s `_wait_for_close` is the pattern, and `test_inspector_state.gd` carries the same loop. Set `SettingsManager.cfg_motion = UiMotion.OFF` only when the test's subject *is* the close; otherwise the wait covers both settings. A test that samples *mid-transition* - a slide ghost's position, a crossfade's outbound alpha - polls the live property frame by frame against a deadline, never a fixed `wait_seconds`: one stalled frame expires the timer and the tween together, and windows-smoke run 44919008575 freed a 200 ms slide ghost before a 150 ms wait returned, then read `position` off the freed wrapper (a script error, not a failure) - `test_pane_motion.gd`'s `_wait_for_transitions` is the helper. There is a second edge on the close path: `_finish` erases the entry (so `playing()` is 0) a frame before `queue_free` lands, so a ghost's removal is waited on by polling `is_instance_valid`, not the counter.
- A GUT helper cannot identify a freshly opened `PopupMenu` by its node name: a second sibling with the same name makes the engine rename the new node (`@PopupMenu@715`, measured on 4.7.2), so a lookup by the builder's class name can return the stale menu or nothing. Have the builder return the instance (`TerminalManager.show_pane_actions_popup` and `show_switch_type_popup` do) and hold that reference; a `begins_with` scan is not a fix.
- A drain-level IPC test passes `params` as the JSON **string** the wire carries (`"params": JSON.stringify({...})`): `request_params` answers `{"params": {}}` for a Dictionary, after which the handler falls back to every default (measured 2026-11-10 - `newPane {"command": …}` spawned a plain shell and the test asserted against a pane it had not configured). `handle(ws, method, {...})` is the direct-call form and takes a Dictionary.
- **The capability catalogue is a gate, and every record is a claim.** `docs/data/capabilities/<AREA>.json` holds one entry per capability: `statement` (what is true, genericized), `mechanism` (how it is done), `status` (`done`, `partial`, `planned`, `rejected`, `undecided`), optional `spec` (the normative anchor), `evidence` (a path into this repo) and `row` (the roadmap row it advances). `scripts/check-capabilities` enforces the shape: id grammar and uniqueness across areas, the status vocabulary, every evidence path resolving at HEAD, every `row` matching a roadmap bold title byte-for-byte, no URLs, and no unknown key a paragraph or a vendor name could grow in. It is 27 ms, so it runs with the docs gates in `ci-check` and as a step in the `Docs` workflow; the code workflow ignores it through `paths-ignore`, and `docs/data/*` is gitignored except this directory. `scripts/render-capabilities` is the view: the table (gaps first), `--public` (status and statement only) and `--vault DIR` (one note per capability, per area index and per joined row, which is what the wiki pane, the link graph and the planned 3D view consume). Add an area by writing the file and running the gate - never by hand-editing a rendering.
- A tooling-class range - `scripts/measure-cost`, `scripts/render-cost-chart`, `scripts/backfill-cost-history`, `scripts/fix-forensics`, `scripts/install-cli`, `scripts/check-secrets`, `scripts/bot-token`, `scripts/bot-push`, `scripts/bot-pr`, `scripts/git-askpass-token`, `scripts/check-github-settings` - is handled by the local gate alone: `ci-check` runs the docs gates, the two GPU-free cost gates, `bash -n` on the shells (including the installer), a compile of the Python scripts and a planned (not executed) backfill, then stops. The class is two lists in `ci-check` that have to agree: `tooling_class_path` decides what narrows the gate, `run_tooling_scripts` is what executes. It is an explicit allow-list, not a folder rule, because those scripts have no test suite: a script joins it only when `run_tooling_scripts` executes it. No workflow invokes them, so a tooling-only push runs CI jobs that cannot observe the change - which is why the class exists. The narrowing is skipped whenever `CI` is set without a `CI_CHECK_RANGE_FROM`, because a CI checkout is shallow and detached and its auto-detected paths are not trustworthy: the pre-push hook always passes the range, but a hand run in a shell that exports `CI` takes the full suite - `CI= ./scripts/ci-check --fast` gets the fast path (measured 2026-11-13: 300 s vs 0.9 s for the same tooling-class tree). A docs-class push runs no code CI. `ci.yml` ignores `docs/**`, `**/*.md`, `godot/knowledge.json`, `LICENSE` and the three scripts that are the docs gates themselves (`scripts/docs-check`, `scripts/build-wiki`, `scripts/check-capabilities`) (`paths-ignore` skips only when every changed path matches, so a mixed commit still runs the full suite); the Docs workflow is that push's gate - it builds the site, runs `scripts/docs-check` and verifies the knowledge bundle with `scripts/build-wiki --check`, which is the only CI job that checks the bundle is current; its deploy is a separate `deploy` job behind `concurrency: pages` (`cancel-in-progress: false`), so a second docs push queues behind the first run instead of racing it, and a `--failed` rerun re-runs the deploy alone because the upload lives in `build`. A script joins that list only when the Docs workflow runs its gate; every other script builds the app, drives Godot, or runs a gate, so it needs the code jobs. Everything else - workflows, any other script, crates, `godot/`, the smoke - still gets the full eight-job run (~4 minutes warm, longer when the Windows vcpkg tree rebuilds). Rust and Godot are never split: the GDExtension is one boundary, so a change on either side runs both suites. `scripts/ci-check` makes the same split locally: a docs-class change runs just `docs-check`, the capability-catalogue gate and the knowledge-bundle check, because the pre-push hook hands it the pushed range (a manual run falls back to the unpushed commits, `--fast` to the index, and an unknown range to the full suite); `CI_CHECK_FULL=1` forces everything, and `./scripts/ci-check --classify` prints the changed set, each path's class and the suite it selects without running anything. The pre-push hook runs that check *before* the ref moves, so an interrupted or timed-out hook aborts the push and the commits stay local: allow several minutes for a code change and run no second Godot suite (GUT, a benchmark, the smoke) while it works - both spawn real panes and timing-sensitive tests share the machine.

`scripts/check-secrets` is the static secret gate: it scans the git index for private-key blocks, cloud access key ids and provider token prefixes, prints file and line only, and runs in `ci-check --fast` (so the pre-commit hook runs it) and in the full gate. The full-history scan is gitleaks in `.github/workflows/secret-scan.yml`.

`scripts/lint-workflows` is the workflow gate: valid YAML, a top-level `permissions` block, every `uses` pinned to a full commit SHA (a local `./` path or a `docker://...@sha256:` digest is allowed), every `actions/checkout` with `persist-credentials: false`, no `pull_request_target`/`workflow_run`, a positive `timeout-minutes` on every job that is not a reusable-workflow call (GitHub rejects the keyword on a call job; the called workflow's own jobs carry theirs) and a `concurrency` group on every workflow. `ci-check` and the `lint-workflows` CI job call it; `GPTY_WORKFLOW_DIR` points it at a fixture. The `main` PR gate also requires the `docs` job (docs-check + capability catalogue + the knowledge and docs bundles) and `commit-lint` (the `githooks/commit-msg` policy over human commits, `[bot]` authors exempt).

`scripts/bot-token`, `scripts/bot-push`, `scripts/bot-pr` and `scripts/git-askpass-token` are syntax-checked with `bash -n`; they need the gpty-bot private key at run time, and `scripts/bot-token --check` verifies the app installation and permissions before a release.
