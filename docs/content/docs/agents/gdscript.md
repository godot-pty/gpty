- Indentation: tabs
- Chrome has one owner: `ui/ui_palette.gd` (every colour, in a complete `DARK` and a complete
  `LIGHT` set, read through `UiPalette.active()`), `ui/ui_tokens.gd` (the mode-independent tokens:
  the `FS_*` type scale, the `SPACE_*` steps, `RADIUS`, `contrast_ratio()`, and `MIN_LAYOUT` - the
  layout floor the applied UI scale is capped against and the Settings card sizes itself to) and
  `ui/ui_theme.gd`
  (`build()`, applied on the `Workspace` root and rebuilt whenever the palette switches; every pane,
  overlay, popup and dialog inherits it). Read a colour **at draw time** — never cache a token in a
  field, an `@export` initializer or an `add_theme_*_override`: the mode switches at runtime, and a
  cached copy keeps the palette it was built under. A widget that needs a colour its type's default
  does not carry names a `Theme` type variation (`UiTheme.MUTED_LABEL`/`DANGER_LABEL`/`WARNING_LABEL`
  for labels, `ACCENT_BUTTON` for a link-style button); `grep -rn "add_theme_color_override"
  godot/scenes` must print nothing, and `grep -rn "add_theme_" godot/scenes` is the census of what is
  left (fonts, sizes, constants - and two deliberate `0` separations). Rule 1 of that paragraph and
  the palette-read rule are enforced: `./scripts/check-theme-tokens` (run by `ci-check`) fails an
  `add_theme_color_override` and a `UiPalette.active()` read at class-body level, with
  `# theme-ok: <why>` as the reviewed exception. A colour used as text on a
  surface belongs in `UiPalette.CONTRAST_PAIRS`; `tests/unit/test_ui_palette.gd` grades every pair
  against both sets under 4.5:1, and `TEXT_DISABLED` is exempt on purpose. Modals go through `ui/app_dialog.gd` (`confirm`/`alert`/`content`/`text`/`set_body`),
  never a bare `ConfirmationDialog.new()`: it parents the dialog, groups the buttons at the right
  edge and puts read-and-copy text in a selectable body. Dialogs are borderless with their own
  header because Godot paints an embedded window's title band from its own default theme (see
  `pitfalls.md`). A file or directory picker is `AppDialog.picker(parent, title, file_mode, access)`
  for the same reason: it sets `borderless`, hides the engine label, and inserts its header at the
  top of the picker's own internal column, so none of the picker's controls move.
- Icons: All glyphs live in `icons.gd` as `const` strings (Phosphor Regular PUA codepoints via `\uXXXX`). To add: pick from phosphoricons.com, get the codepoint, add a `const`. An icon-only button is built with `Icons.icon_button(btn, glyph, name, variation := &"")`: it leaves `btn.text` empty, applies the one `UiTheme.ICON_BUTTON` variation (no box at rest, an accent wash on hover/press, the 1 px accent focus ring), floors `custom_minimum_size.x` at `UiTokens.BUTTON_MIN_WIDTH`, and draws the codepoint in a child `Label` named `Glyph`. That is why the button's exposed name is the words alone: the engine composes `"<accessibility_name>: <button text>"` (measured on 4.7.2), and a codepoint left in `text` trailed the words into the tree. `name` is a required argument because a `Button` is named from its `text` before its `tooltip` (`grep -rn "Icons.style_button" godot/scenes` must print nothing). `Icons.glyph(btn)` reads the codepoint back (`""` for a text button); a glyph that changes at runtime calls `Icons.set_glyph(btn, glyph)` after setting `accessibility_name`, which it mirrors onto the Label (`WindowChrome._sync_max_button`, `TerminalManager._toggle_minimize`). A glyph-plus-text action is a filled `Button` with a child `HBox` (see Sidebar layout), not this treatment.
- Outbound links: every URL handed to the OS goes through `ui/external_link.gd` (`ExternalLink.open(url, fallback_text, message, source)`), never `OS.shell_open` directly: a refusal copies the text (the URL by default) and raises a WARN toast naming the URL (shortened for the toast only), so a press never looks dead. The sidebar's catalogue hint and Feedback row, Markdown's confirmed external link, the Settings About line and the file tree's confirmed system open are the callers (the file one passes `ExternalLink.refused_file_message(uri)`, because its refusal copies a `file://` URI rather than a browser link); `open_external`/`copy_text` are the seams a test replaces.
- Accessibility: `ui/accessibility.gd` (`A11y`) owns names, values and published text. A glyph-only `Button` is named through `Icons.icon_button`; every `PaneBody` names itself from its label plus type or user name; a custom `_draw()` surface records its visible text with `A11y.set_text` and publishes text nodes with `A11y.publish(host, slot, text, live)` on the host `A11y.announce_host(control)` returns (the tile's title bar - a pane body is a leaf in the exposed tree, and a node's name is a snapshot taken at element creation, so dynamic text is a replacement node, never an edit). Gate the work on `A11y.enabled()`; a live region states one line, never a buffer. Prove the metadata with `scripts/ui-capture --audit-accessibility <state>` and the exposed tree with `scripts/accessibility-probe` against a rebuilt export. An element's value and role have no path to the 4.7.2 adapter (`AccessibilityServer.update_set_value`/`update_set_role` never reach the node, and a custom `Control` carries no `Text`/`Value` interface): the name is the creation snapshot, so `A11y.publish` replaces a slot only when its text or live mode changed - an idle pane republishes its last line every second and must not take the node a reader is on. The probe prints an `a11y-values:` line (`text-interfaces`, `value-interfaces`, `marker-in-value`, `role-names`) for exactly that re-test.
- Sidebar layout: the sidebar owns every persistent switcher (workspaces, profiles, panes) as vertical sections in its VBox - never add full-window top strips or overlays, they cover sidebar chrome (the window-mode dropdown sits at the sidebar's top). Sidebar content lives inside a `MarginContainer` (8px left/right ≈ scrollbar width, 6px vertical) so rows never touch the sidebar's edges. Icon+text actions are a single `Button` with a child `HBox` (icon `Label` + text `Label`), both labels at the same font size, a 6px `offset_left` breathing gap, plus an explicit `custom_minimum_size.y` (a textless Button does not size from its children and collapses). Section lists share one pattern: `SECTION_MAX_VISIBLE_ROWS` (5) caps visible rows; `_measured_section_height` sizes the scroll container from `get_combined_minimum_size()` (never hard-coded row heights - they drift from theme metrics and truncate the last row); `_apply_row_accent` marks the active row (`Palette.ACCENT_COLOR` + pressed look) and is used identically by workspace, profile, and pane rows. Active-row state: workspaces by index, profiles by name (cleared on `_do_reset` and on deleting the active profile), panes by `_tm.last_body` via `set_active_pane` (no list rebuild on focus change). The pane list absorbs leftover height via `SIZE_EXPAND_FILL`.
- A section whose header is glyph-only carries the shared Help affordance: `ui/section_help.gd` (`SectionHelp.attach(header, host, title, intro, rows_of)`) adds one question-mark `Button` (tooltip and accessible name "Help") that opens an `AppDialog` table of `{glyph, action, chord}` rows. The provider is called on press, never at attach time, because a chord is only spelled once the workspace has registered its bindings; `host` must be an unclipped Control (the sidebar sets `clip_contents`, so its popups are parented to the background rect) and a header whose text changes with state keeps `clip_text` set, or the renaming Label resizes the 164 px section. Any user-facing string that names a chord reads `ShortcutManager.chord(action)` - never a literal, and never the pane registry's own `shortcut` field.
- Profiles: named terminal-layout snapshots, in `ProfileManager.get_all_profiles()` order: shipped built-ins (`res://profiles.default.json` - two, "Agent Workspace" and "Knowledge Base"; both name no program, so first-run onboarding opens no dialog: Agent Workspace is pure terminal geometry, Knowledge Base is a wiki tile that names the bundled-vault token instead of a machine path. Tool presets stay in plugin repos.), **installed-plugin profiles**, then the user's own (`user://profiles.json`). Shipped files are never written back, and plugin profiles are not either - they belong to the plugin and vanish with it (their store records keep them out of `user://profiles.json`; the sidebar gives them no delete/rename affordance, and their tooltip names the plugin and pinned revision). Dedupe follows `add_profile`'s convention with the user winning: a user or builtin profile keeps the bare name and a colliding plugin profile takes ` (n)`; among plugin profiles the first wins, and the naming re-runs whenever a user profile takes or frees a name (`_derive_plugin_profiles()`, called by `add_profile`/`update_profile`/`rename_profile`/`delete_profile`), so the winner does not depend on which side arrived first - without that re-run the two rows share one name for the session and `find_profile` resolves the collision to the *plugin's* row (plugin profiles are listed before user ones), so a click on the user's row or a `layoutLoad` by that name would activate the plugin's profile. `refresh_plugin_profiles()` is the only *store reader* and the only emitter: it parses `GptyTerminal.installed_plugin_profiles()` (the `plugin_profiles_source` Callable is the test seam), skips malformed entries instead of raising, re-derives the block and emits `profiles_changed`; it runs at init and (deferred 2 s) after an install review is accepted, because the CLI only moves the clone into place after it reads that answer. The CLI's admin actions (`uninstall`/`enable`/`disable`) are not visible to a running GUI until one of those runs (queued in the roadmap). The sidebar appends a catalog hint row as the section's last row (→ the registry's docs page), even once plugin profiles are installed. Everything downstream is unchanged: `layoutList` lists these names, `find_profile` resolves them for `layoutLoad`, and activation clears the workspace (`_reset()`) then rebuilds tiles (`_restore_into()`), rebuilt for the remaining built-ins and covered by `test_the_shipped_builtins_are_program_free` + `test_each_preset_tile_passes_sanitize_tile`. A profile row offers two destinations and keeps them separate: the label activates in the active workspace (`_do_profile_activate`, which asks before replacing panes) and the trailing `Icons.NEW_WORKSPACE` glyph opens it in a workspace of its own (`_do_activate(profile, ask_running, open_in_new)` → `_create_workspace_for_profile`: named after the profile through `WorkspaceStore.unique_name` (a second one gets " 2"), inheriting the active workspace's cwd, switched to before the restore, refused at `MAX_WORKSPACES` before the trust prompt, and with no replace confirmation because nothing live is lost). The Workspace Trust dialog carries `open_in_new` through, so an approval cannot redirect the click to the other destination; the two sidebar signals (`request_profile`, `request_profile_in_new_workspace`) are emitted by their own gesture and never both.
- Attachment IDs: persist `attachment_id` (`[a-z][a-z0-9_-]{0,31}`) on panes. Companion panes (Reasoning) attach by this stable id, not ephemeral labels like `T1`. `pane_label` is reassigned on restore and must not be used as a saved link. It is also the **public IPC id**: every pane has one (auto-generated `pane-XXXXXXXX` via `PaneTypes.generate_attachment_id()` when none was saved - `PaneBody.apply_settings` is the choke point), `newPane` returns it and `listPanes` reports it as `id` alongside the display `label`. A Pane Settings rename retargets the followers in that pane's own workspace (`Workspace._retarget_companions` calls each follower's `retarget_source`), so a companion never keeps an id its terminal no longer has; a pane whose link should survive a rename implements `retarget_source` rather than resetting on every `apply_settings`. IPC pane targeting accepts either the `id` or a `label`, resolved by `Workspace._resolve_pane_target`: an `attachment_id` always resolves (ids are globally unique across workspaces); a label resolves only when exactly one pane carries it, and a label several workspaces share (`T1` in each, since labels restart per workspace) is **refused** with an error naming every candidate's workspace and attachment id - never resolved to whichever workspace happens to be active, because an agent working in one workspace must not act on another workspace's pane by accident. `listPanes` and `broadcast` stay inside the active workspace. Restoring a tile set (a workspace restore, or the same profile activated in a second workspace) resolves every id **before** any body exists: `_resolve_tile_ids` renames duplicates against the panes already live in other workspaces and against earlier tiles (first one keeps a repeated id), rewrites the set's `source_attachment_id` references through the old→new map so a Reasoning pane follows the terminal restored beside it, and copies the user-owned `PaneEnvStore` entry to the new id (the entry still belongs to the logical pane id the first instance holds).
- JSON → typed arrays: `JSON.parse()` returns untyped `Array`. Assignment to `Array[Dictionary]` fails at runtime. Always iterate and build the typed array element-by-element: `for item in raw: if item is Dictionary: typed.append(item)`.
- Private members: underscore prefix (`_cell_w`, `_settings_panel`)
- Config vars: `_cfg_` prefix (`_cfg_cursor_shape`)
- Persistence: Managers extend `BasePersistenceManager` - provides `_read_file(path)` / `_write_file(path, data)` for JSON stores and `_read_text(path)` / `_write_text(path, text)` for text assets, and sets `PROCESS_MODE_ALWAYS`. Subclasses override `_on_init()` instead of `_ready()`. Loads read through the typed accessors (`_as_int`/`_as_bool`/`_as_array`/…) rather than a raw `d.get(key, default)` assigned to a typed variable: GDScript raises on a wrong-typed JSON value, which aborts the loader and drops every key after it (and the next save writes that reduced state back). Never inline `FileAccess.open()` - use `_read_file`/`_write_file` for JSON stores and `_read_text`/`_write_text` for text assets. Writes go to a sibling temp file and are renamed into place: `FileAccess.WRITE` truncates the target as soon as it opens, and `_read_file` reads a truncated file as empty, so an in-place write that fails costs the entire store. That temp name is random (`_temp_suffix()`, 64 bits) and the file is created 0600 (`STORE_UNIX_MODE`): `FileAccess.open(..., WRITE)` **follows a symlink**, so a fixed `<store>.tmp` let anything able to write in `user://` point the next save at a file of its own choosing. Do not go back to a predictable name, and do not drop the explicit mode - the umask decides otherwise, and a 0644 store hands every pane environment and window geometry to any account that can read `user://`.
- Godot paths vs real paths: `String.is_absolute_path()` is true for `res://` and `user://` as well as a filesystem path (measured on 4.7.2), so it is not the guard at a boundary that leaves Godot. `FileAccess`, `DirAccess` and `DirAccess.*_absolute` accept the schemes; Rust (`std::path`, a PTY `cwd`), FFmpeg and a desktop handler do not — and a scheme that slips through fails one layer later with a message about the layer, not the setting (v0.7.1's knowledge base resolved to `user://knowledge/<hash>` and failed as "not an absolute path" inside the vault index). Use `BasePersistenceManager.is_real_absolute_path()` wherever a data value must be a real absolute path, and `BasePersistenceManager.real_path()` to turn a scheme into the directory it names. `FileAccess.file_exists()` stays the regular-file gate; it answers only the path-type question.
- Directory layout: Scripts are grouped by role: `autoloads/` (shared managers and the persistence base), `terminal/` (core terminal), `ui/` (sidebar, settings, toast), `panes/` (specialty pane types). `project.godot` autoload paths and `preload()`/`load()` calls use the full `res://scenes/<dir>/<file>.gd` path.
- Pane settings from a file are a closed table: `PaneTypes.settings_schema(type)` lists every key a pane type accepts with a rule (`text`, `int`/`float` with a range, `bool`, `color`, `id`, `tags`, `argv`, `shell`, `font_path`) and `file: false` for keys only the app may set (env, scheme paths, the three chrome colors). `PaneTypes.sanitize_tile` runs it with `SOURCE_FILE` - unknown and app-only keys are dropped and `Workspace._restore_into` reports them once - and `PaneBody.apply_settings` runs it again with `SOURCE_RUNTIME`; it is the only *generic* assignment path - a pane's own override assigns its named keys explicitly, which is why every one of those keys is in the table (the old `_set_typed` assigned *any* exported String/int/float/bool, which is how a layout chose a font path). A new pane property that must survive a layout needs a rule, and `test_pane_settings.gd::test_every_pane_type_accepts_the_settings_it_saves` fails when one is missing. Data paths never reach a resource loader: a `.tres` with an embedded GDScript runs during `load()`, so `TerminalFonts` builds a font from bytes (absolute regular file, extension gate, 32 MiB cap, magic + face check) and only the bundled `res://` constants go through `load()` (an export carries their imported `.fontdata`, not the source `.ttf`); a color scheme is a capped `TextRead`. `font_size` is clamped to `PaneTypes.FONT_SIZE_MIN/MAX`, which the pane panel's spinbox also uses.
- Settings pipeline: `_cfg_*` → `_save_settings()` → `user://settings.json`. Read-only rows are allowed (not every row is a setting): the Terminal tab's "On disk:" label reports what scrollback costs, from the static FFI `GptyTerminal.history_store_stats()` → `gpty_core::history::store_size_on_disk()` (the store file plus SQLite's `-wal`/`-shm` siblings). It cannot be derived from `History lines` - the store is bounded by rows *and* bytes, so the real footprint depends on how long the lines were - and it is refreshed on `NOTIFICATION_VISIBILITY_CHANGED` rather than once, because the panel outlives a visit while scrollback keeps growing. To add a new setting: (1) add `_cfg_` var, (2) add UI control, (3) add one line to `_apply_settings_to()`. `TerminalManager.spawn_pane()` calls it automatically - no other wiring needed. Pane-local settings that are NOT terminal settings (e.g. `cfg_reasoning_max_turns`, `cfg_reasoning_max_turn_bytes`) are read by the pane from `SettingsManager` at `_ready` with clamps - changes apply to panes created afterward; no `_apply_settings_to` wiring.
- First-run shell: `SettingsManager.default_shell_command()` - `/bin/bash` on Unix, `%COMSPEC%` (falling back to `cmd.exe`) on Windows. The Windows branch exists because a POSIX path is not absolute there and `validate_executable` refuses it, so every pane of a fresh Windows install failed to start. `pane-run` picks the "run this and exit" flag from the shell family with `PaneTypes.shell_run_args()` (`/c` for `cmd.exe`, `-c` otherwise) - the pane API runs through the user's configured shell, so the flag cannot be hard-coded.
- Terminal spawning: `TerminalManager.spawn_pane()` (builds the body and auto-splits) and `create_body()` (a body for `_restore_into`'s own geometry) are the two constructors; a *live* pane only ever arrives through `Workspace._spawn_pane_into`, which is what `newPane`, `paneRun`, the palette, the sidebar, a `request_pane` and a profile activation all call. A terminal's child is **not** started by `_ready`: `TerminalPane._start_child_if_ready` is the one `start_shell` call site, and it runs on the first size the pane is drawn at (`_grid_for_size`, shared with the resize debounce, which opens the pty at that size). So a new spawn path has to let `Workspace._apply_layout` position the tile (`PaneBody.mark_tile_laid_out`) - a body added without going through it has no child, by design - and every pane that must know its drawn size waits for that hook instead of reading `size` in `_ready`. The corollary for the control surface: a pane-creating IPC answer is only true once the child exists, so `WorkspaceIpcHandlers.dispatch_request` holds any answer carrying a `pane_id` through `Workspace._hold_pane_answer` until the pane reports its start — `TerminalPane.child_started` (answer the document) or `child_start_failed` (answer `start_shell`'s sentence, toast it, close the tile) — and a new pane type that starts asynchronously must emit the same pair rather than answering a claim it cannot keep.
- Pane ceiling: `Workspace.MAX_LIVE_PANES` (96) bounds live panes for the whole window - every workspace, because a pane in a workspace that has been shown keeps its PTY, child process and grid while the workspace is hidden, and a restored pane starts holding a slot the moment its tile exists (its child starts when the workspace is first shown) - and `Workspace._pane_ceiling_refusal()` is the one decision that says no, carrying the limit in its text. Two creation paths consult it: `_spawn_pane_into` (nothing is built when it refuses; `_live_pane_room()` is the shared room check), and `_restore_into` (a layout, profile or workspace store restores what fits and toasts `Restored N of M panes.` plus that same text). A new pane-creation path that skips it reintroduces the unbounded spawn the ceiling closed; the constant's doc comment carries the measurement behind the number.
- Layout Constraints: The tiling grid relies on Godot `Control` nodes. Prefer using Godot's built-in Size Flags (Expand/Fill) inside containers (`HBoxContainer`/`VBoxContainer`) over manual pixel math. When manual math is absolutely required (like terminal cell reflows), hook into `_notification(NOTIFICATION_RESIZED)`.
- Pane activation & keyboard routing: clicking any pane (body, titlebar, or inner widget) makes it the active pane - workspace `_input` hit-tests tile wrappers with `event.position` (raw input, because inner RichTextLabels/ScrollContainers consume clicks before `_unhandled_input` ever fires). Only terminals take keyboard focus: activating a non-terminal pane releases the previous focus owner so keystrokes stop flowing to the terminal the user just left (read-only panes swallow keys by design - uniform click-to-activate, no fall-through; the one deliberate exception is the wiki pane's Escape-to-Back, which reads the input stage and scopes itself to its own focus owner, traps in `pitfalls.md`). That rule lives in exactly one place, `Workspace.activate_pane(body)` (records `last_body` in the body's own workspace, then `_take_focus()` for a terminal and a focus release otherwise) - the three activation paths (click, sidebar row, IPC `focusPane`) all call it, because the copies had already drifted: `focusPane` called `grab_focus()` unconditionally, so focusing a read-only pane raised an engine error and activated nothing while still answering `success: true`. A focusable child (Inspector input) re-resolves its owning pane each frame in `_refresh_status_bar` via `_body_of_focus_owner`. Profile activation must end with `_apply_active_workspace_view()` - the same refresh path as workspace switching - or restored wrappers stay unlaid-out and the sidebar pane list stale. That refresh is also where a workspace with no remembered active pane resolves one: launch, a restored workspace never visited, and a profile rebuild all leave `last_body` null, because it is only set by a click, a spawn, or a focus event. `_fallback_active_body()` picks the first terminal (only terminals take keyboard focus), falling back to the first pane so a read-only workspace still has an active row, and the result goes through `activate_pane` like every other path - without it the first keystroke after launch reached nothing until the user clicked a pane (UX-01).
- Overlay keyboard ownership: the four workspace overlays (Settings, Pane Settings, the command palette, the concept graph editor) extend `OverlayPanel` and own the keyboard while visible. `Workspace._keyboard_overlay()` is the one predicate, in stacking order (palette, concept editor, settings, pane settings), and Escape is handled in `Workspace._input` - before GUI - because a focused terminal consumes every key in `_gui_input` and would turn Escape into the raw ESC byte its child expects; no overlay may handle Escape in `_unhandled_input` (all four copies were dead while a terminal held focus). An overlay is shown with `open()` (never a bare `visible = true`): it remembers the focus owner and focuses a control inside (`_initial_focus()` or the first reachable descendant), so a typed character lands in the overlay instead of the shell. `close()` hides it and emits `keyboard_released` only when it still owned the keyboard, so a click that already moved focus is never overridden; the workspace then focuses the overlay underneath (the concept editor over Settings; when that overlay's remembered control is gone it takes a control again through `grab_keyboard()`, never leaving the keyboard to the terminal behind a visible overlay) or the active pane. While an overlay is open, `_activate_pane_under_mouse` does nothing: the raw stage runs before GUI picking, so without that rule a click on a panel would re-focus the pane behind it. A new overlay joins `OverlayPanel` and `_keyboard_overlay()`; `test_overlay_focus.gd` is the contract test (typing never reaches the PTY, Escape closes without writing the ESC byte, focus returns). `ShortcutManager` asks `overlay_owns_keyboard` (injected by `Workspace` from `_keyboard_overlay()`) before it acts; `register(..., survives_overlay = true)` is only for window actions, so a refused chord is consumed instead of spawning or resetting behind the panel. The palette's entries are data (`ui/palette_model.gd`); its rows are `FOCUS_NONE` buttons under one field, the arrow keys move a `UiTheme.SELECTED_ROW` cursor, and a row's chord is `ShortcutManager.chord(action)` - never a repeated literal.
- Pane chrome is a keyboard toolbar: a pane's title-bar buttons are `FOCUS_ALL` with an explicit `focus_next`/`focus_previous` ring (`TerminalManager._wire_chrome_keyboard`), so Tab moves through the three controls and wraps instead of leaking into the next tile, and the body's own `focus_next` points at the first of them. There are three, not five - **pane settings**, the **actions menu**, **close** - because the type list alone used to cost a whole button (122 px of bar reserved, 74 now). `TerminalManager.show_pane_actions_popup` is the one definition of what a pane can do: minimize/restore, swap position, and the eight types with the current one marked (`add_radio_check_item` + `set_item_checked`), built per open and freed on close. The sidebar's pane row opens the same builder, so the two surfaces cannot list different actions or disagree about a pane's type, and choosing the current type is a no-op (`swap_pane` does allow a same-type swap, which would silently rebuild the pane). A focused terminal consumes Tab for its child, so the way in is the `Ctrl+Shift+E` shortcut (`Workspace._focus_active_pane_chrome`, which does nothing while an overlay owns the keyboard) and the way out is Escape (`Workspace._escape_pane_chrome`). A chrome action that leaves the pane on screen hands the keyboard back (`TerminalManager._return_focus_to_body`): a mouse click focuses the clicked button, and a focused button swallows the next keystroke. A terminal takes the keyboard itself; another pane may name its own entry point (`PaneBody.keyboard_entry` - a wiki pane with an open note aims at its buffer, not at the top row's Back), and a pane without one gets its first reachable control (`KeyboardFocus.first_reachable`, the same walk an overlay uses on open). Read Escape at an input stage with a focus-owner check, never in `_gui_input` - on 4.7.2 `_gui_input` is delivered to the focused control only and does not bubble to ancestors (measured: a focused Button under an `outer.gui_input` delivered nothing to the outer control).
- Pane surfaces are shared, not per-pane: `PaneBody.CONTENT_INSET` (6 px) is the margin every text pane keeps from the tile's own 1 px border, applied with `PaneBody._fill_content(root)` - not a `MarginContainer` wrapper, which would move node paths the panes and tests already address - and the panes whose surface is its own pixels edge to edge (the terminal grid, the media video) do not call it. `PaneBody.empty_state(content, glyph, title, hint, font_px)` is the one "nothing to show" surface (centred hero glyph, title, and a sentence naming the fix; the title clips at a 200 px minimum so file-supplied text cannot widen the pane): media, the code viewer and the file tree use it, and a pane that owns its wording rewrites the returned `{host, title, hint}`. The wiki pane's single centred sentence is a deliberate exception - its toolbar stays live above it and its messages are one-line diagnostics.
- Every chrome toolbar is a keyboard ring entered by a chord: `KeyboardFocus.reachable_children(row)` picks the row's stops and `KeyboardFocus.ring(...)` wires `focus_next`/`focus_previous`, so Tab wraps inside the bar instead of leaking into the next tile. A focused terminal or `CodeEdit` keeps Tab for its child, so a chord is the way in and Escape is the way out, one level per press: the window's own bar (`Ctrl+Shift+A` → `WindowChrome.focus_controls`, Escape → `_escape_window_chrome` → `_return_focus_to_body`), a pane's own action row (`Ctrl+Shift+L` → `PaneBody.focus_toolbar`, Escape → `Workspace._escape_pane_toolbar` → `leave_toolbar`), and the wiki note toolbar (`Ctrl+Shift+K` → `WikiPane.focus_note_toolbar`, Escape → the same shared step; `WikiPane._wire_note_toolbar` still builds that row from the same pair). A view pane joins by assigning `PaneBody._action_bar` (`CodeViewerPane` rings Reload/the view toggle from `_refresh_view`, `CliViewPane` Restart/Stop from `_sync_buttons`) and overriding `keyboard_entry()` with the surface a reader continues in - the base `leave_toolbar()` returns there and never back into the bar, and a pane whose buffer is not on screen (wiki `preview`) answers Back instead of null. Chords that resolve "the pane" do it from the focus owner and only then fall back to `last_body` - `last_body` alone was measured wrong, because a wiki pane opened from its own list kept the startup terminal as the active pane, so the chord did nothing from the very buffer it exists for - and they are inert while an overlay owns the keyboard. Two rules the engine forces, both in `pitfalls.md`: a button that becomes disabled must also lose its focus mode, and a ring rebuilt from what is on screen must be allowed to shrink to one member (`KeyboardFocus.ring` then clears both paths instead of writing a `"."` self-path). `Workspace._input` is the one Escape ladder - overlay, pane chrome, window bar, pane toolbar - and each step is scoped to its own focus owner.
- The link graph is the same pattern one surface over: the canvas and its three actions are one ring with the canvas first (`VaultGraphView._build_chrome`), so Tab cycles the map's own controls and never leaks into the sidebar. `VaultGraphView` draws its own focus frame and crosshair (a custom-drawn Control has no stylebox to do it), arrows pan, `+`/`-` zoom about the centre, and Enter acts on `cursor_hit()` - the node under the crosshair, else the edge under it - so the keyboard and the pointer share one `VaultGraphModel.hit_test`/`hit_test_edge` answer instead of a second navigation model. Labels are a placement problem, not a per-node draw: `VaultGraphView.label_placements` orders candidates by what the user is aiming at then by degree, `VaultGraphModel.cull_labels` drops any box that would print over an accepted one, and `fit_to_view` reserves the widest label so the fitted map's right-hand labels stay inside the view - without that, a 52-note vault prints its titles on top of each other (measured, and the row that closed it).
- List cursors and mouse-only declarations live in the same module: `KeyboardFocus.next_index(current, count, delta)` is the one clamped cursor step (the ends are stops, and `-1` means nothing is selected yet), used by the command palette's rows and by the search strip's History results; and `KeyboardFocus.declare_mouse_only(control, reason)` records why a `FOCUS_NONE` control leaves its action to a chord or to a field - `mouse_only_reason` reads it back, and `scripts/ui-capture --audit-focus` prints a declared control with that reason and counts only undeclared ones as `unaccounted`. A new mouse-only button in the app's own chrome declares one, or the audit reports it as an oversight.
- Capture Bridge: Rust never calls into Godot. GDScript polls the backend from `_process()` - `drain_concept_events()` for completed captures and `drain_agent_events()` for Tier 1 agent state.
- Agent-state observation contract: `PaneBody.agent_state_source_id()` names the terminal a pane observes by stable `attachment_id` (a terminal returns its own id - the tiered tracker it reads *is* that terminal's state; empty = observes nothing, the base default) and `PaneBody.on_agent_state_changed(state)` receives that terminal's state. `workspace.gd` is the only dispatcher: `TerminalPane.agent_state_changed` (emitted from the slow poll on a real transition) calls `_dispatch_agent_state`, and a per-frame `_prime_new_pane_observers` scan delivers the current state once, to the new pane alone, through `_tell_observer` - any pane-entry route (spawn, restore, swap, a future pane SDK), a follower whose terminal appears later (retried), and a pane re-pointed at a different source (the stored record is the source it was primed for plus the state it was last told), all without re-priming a settled pane. A change dispatch reaches only panes already settled for that source - delivering to an unsettled one would make the scan's entry the duplicate - and `_tell_observer` drops a value the observer already holds, the dispatcher-side mirror of the terminal's own `_badge_state` rule, so no observer hears the same state twice whichever path carried it. Panes are found through the `panes` group, so hidden workspaces keep observing their own; the source terminal is resolved **inside the observer's own workspace** (`_workspace_for_body` then `_terminal_for_agent_state`), so a companion left pointing at another workspace's id observes nothing instead of that terminal. Agent events follow the same rule: `_route_agent_events` groups receivers by workspace and delivers only inside the emitting terminal's own (`_poll_agent_events` is just the FFI drain). The titlebar badge is the first implementation and runs *through* this path (`TerminalPane.on_agent_state_changed` applies it), not beside it: the hook also records the delivery (`_badge_state` is what the pane was last told), and the slow poll reports only deltas against it - its first read before any delivery is adopted silently, so the entry prime stays the single delivery of the spawn state instead of the poll re-announcing it as a change. Display only: a Tier 2 declaration is spoofable by anything that prints and Tier 3 is a heuristic, so a hook must never feed a decision, an action, a capture, or IPC.

- Pane status contract: `PaneBody.status_document() -> Variant` is the generic `paneStatus` hook (null when the pane has no primitives). `TerminalPane` returns its process/grid document unchanged; `MediaPane` returns `{kind,file,state,position_us,duration_us,paused,loop,volume_db,muted}` while a file is open. `ipc_handlers.gd` uses the hook for both the aggregate (a pane without primitives keeps `status: null` rather than disappearing) and a targeted request (a generic "no status primitives" error, never "not found"). Any future pane that has observable state implements the override; do not add a per-type branch in the IPC handler.
- Close contract: `PaneBody.request_close(answer)` asks before a pane is destroyed, and `PaneBody.has_unsaved_state()` is its state half. `answer` receives a bool - `true` proceeds with the teardown, `false` cancels the whole action - and it may arrive **deferred** (the wiki pane opens a Save/Discard/Cancel dialog), so a caller passes a continuation, never destroys the pane itself, and must honour the bool it gets back (a continuation that ignores it turns a Cancel into a go-ahead - measured: the Back button closed the note it had just been told to keep). The base answers `true` at once, so a pane with nothing to lose never asks. Every destruction path goes through it: `Workspace._kill`/`_kill_now` (the titlebar X, the sidebar's close button, `Ctrl+Shift+W`, the palette, IPC `killPane`), `_swap_pane` (the old body dies), `_reset`/`_do_reset`/`_do_activate` (reset, profile activation) and `_close_workspace`/`_restore`, plus `request_quit()` - the app's only quit path, reached from the window manager's close request (`auto_accept_quit` is off), the titlebar's close button and the Rust shutdown flag (`daemon stop`, a refused socket bind) - which walks every pane of every workspace through the same ask (a Cancel cancels the quit; `quit_action` is the seam the tests replace, and the `_quit_asking` flag is cleared on both answers so a canceled quit can be asked again). `_ask_close_then(bodies, next, declined, ask_running, action, qualify_entries)` is the one walk, in two phases: stopping **running processes** is the action's hazard, so `_ask_running_then` asks once for the whole set - `PaneBody.has_running_work()` - and the consent text is the caller's action phrase plus the busy/total pane counts (`running_ask_intro`) and one line per busy pane naming its label and `PaneBody.display_name()` (`running_ask_entry`), qualified by its workspace unless the action phrase already named it (`qualify_entries`) - and only then does each pane answer for work only it can describe (the wiki's Save/Discard/Cancel) through `request_close`; a bulk close of sixteen terminals must not raise sixteen dialogs. A refusal at either phase stops the walk, so panes it had not reached are never asked. `TerminalPane.has_running_work()` reads the status document's `foreground_job`: Unix is exact (`portable-pty`'s `process_group_leader()`/`tcgetpgrp` on the master compared with the spawned child, so `cmd &` does not count and a pane whose configured program *is* the child reports none), while Windows/ConPTY has no foreground-group notion and answers `null`, which the pane must treat as busy while the shell runs - the conservative fallback. The sample is exact only for a live task: `running` is `exit_code.is_none() && task_alive` (`engine.rs`), so a pane whose I/O task ended while its child survived reports idle — that pane closes nothing by itself, and the status document's `child_alive` (the task's last `try_wait` answer) is what makes it ask, since teardown still SIGKILLs the surviving process group. `TerminalPane.running_work_from_status` is that decision in one pure function, unit-tested against every document state (`tests/unit/test_terminal_running_work.gd`). `_kill`/`_swap_pane` route through the same two-phase walk, so a titlebar X, `Ctrl+Shift+W`, the palette, a type swap and a workspace close all ask the same way. A caller that cannot answer a dialog - IPC - must not ask: it checks `has_unsaved_state()` and refuses with an error naming the pane (`killPane`, `layoutLoad`, the rule `layoutLoad` already applied to an untrusted profile). Stopping processes is not refused, because naming a kill or a load is consent to it: `killPane` calls the `_kill_now` primitive and `layoutLoad` activates with `ask_running: false`.

- Pane request contract: panes never spawn panes. A body that needs another pane emits `PaneBody.request_pane(type, settings)`; the workspace connects it in `_attach_pane_into` (so every entry route - spawn, restore, swap - carries it) and answers through `_spawn_pane_into` followed by `activate_pane`, holding `type` to `PaneTypes.ALL` so the spawn surface stays closed. The workspace may answer with an existing pane: a `code_viewer` request for a file some viewer in that workspace already shows is focused and not duplicated (a viewer's scroll, selection and rendered/source mode belong to its document, so silently repointing one is rejected; a second view is a deliberate second viewer), which is why an emitter must not assume its request created anything and why the viewer needs the explicit Reload action. The file tree's `open_in` is per-tree state (`viewer` default, `system` optional), saved in the tile like `root_path`; the origin owns the choice rather than a global setting.
