## v0.14.1 - Agent Observability

What a terminal-hosted `omp` publishes about itself, and what gPTY still does not show. Surveyed 2026-11-06 against OMP 18.17.0: 53 public extension events (`omp://hooks.md`, `~/.omp/.../@oh-my-pi/pi-coding-agent/dist/types/extensibility/extensions/types.d.ts`), the versioned RPC surface (`omp://rpc.md`), and the on-disk session artefacts (JSONL, `stats.db`, `history.db`, `agent.db`). The extension forwards nine event names today; the rows below take the rest of the cheap tap - numbers and lifecycle, never message text - add the two read-only session views, and add one channel back into the TUI. Hosting an `omp` session in a pane instead is recorded under Future. Three rows below widen the same surface past agents that publish nothing gPTY can authenticate: a manifest-driven Tier 3 for harnesses with no integration, a state subscription for consumers outside the app, and one attention queue for the user.

## v0.14.2 - Program Status (OSC 7501)

The Program Status Protocol is a generic, pty-native way for any program to say what it is doing — idle, working, done, blocked with a kind, or failed — and why, with a message, a progress percentage, and a tree of records under ids. It is the first agent-state channel gPTY can share with programs and harnesses it does not integrate with, and it rides the pty that already crosses SSH and containers, so it needs no socket or manifest; like `gpty_state`, it is spoofable by design and may only paint display state. On Windows it needs the v0.13 ConPTY passthrough row, because ConPTY re-renders the stream and drops unknown OSCs.

The implementation spec for these rows - the wire parsing, the limits, the record model, the exact JSON and FFI shapes, the UI constants and the test list - is a local working note at `TEMP/osc-7501-program-status.md` in the repository root. It is gitignored (the `TEMP*` entry in `.gitignore`) and never shipped; it exists so a row can be picked up without re-running the research.

| Done | Area | Item |
|:---:|:---:|---|
| ⬜ | TERM | **Program status reports (OSC 7501) are parsed, bounded and projected onto the badge** - the Program Status Protocol (spec rev 0.4, `superlogical.com/rex/docs/build/program-status`) is the generic terminal answer to "what is this program doing": `idle`/`working`/`done`/`blocked`/`error`/`clear`, a `kind` with `blocked`, a `progress`, an `app` slug, a base64 `title`/`msg`, and a tree of records under hierarchical ids. Both parsers drop it today: the line parser interprets only `gpty_state` (`crates/gpty-core/src/parser.rs:239`) and alacritty's vte Performer ignores every OSC number it does not know, so no program can reach the badge with the protocol. Fix: a new `crates/gpty-core/src/program_status.rs` (grammar, record store, projection; no `vte` dependency) plus one `osc_dispatch` branch and a `program_status` field on `TermGrid` beside the tracker (`crates/gpty-core/src/term.rs:192`). Enforce the spec's limits before touching a record - 4096-byte sequence, 16-byte key, 32-byte `app`, 128-byte id with 32 per segment and 8 levels, 2732/2048 `msg` encoded/decoded, 256/192 `title`, 64 records with least-recently-updated eviction; skip a malformed pair but discard the whole report on a limits break, undecodable base64, or a control character in decoded text. Each report replaces its record completely; `clear` removes a subtree or everything; RIS (`ESC c`) clears every record while DECSTR does not; OSC 133 `A` and child exit drop `working`/`blocked`/`idle` and keep `done`/`error`; gate application on capture only, never on alt-screen or the post-resize window, because agent TUIs live on the alt screen; strip bidi/invisible formatting from `msg`/`title` before display. Project attention-first `blocked` > `error` > `working` > `done` > `idle` onto `AgentState` at Tier 2, and ignore `gpty_state` for that terminal from its first 7501 report until RIS. This is the second OSC the parser interprets, so the row carries the security review `docs/content/docs/agents/security.md:41` requires: display only, no report field ever written back or logged, limits checked first. Tests in the note (discard-vs-skip rules, id grammar, base64 caps, lifetimes, LRU, projection, a 4096/4097-byte boundary) plus the existing `gpty_state` tests unchanged. |
| ⬜ | TERM | **A program that asks whether gPTY speaks OSC 7501 gets no answer** - the spec says a supporting terminal MUST reply to `OSC 7501;?` with `?` and MAY list its `states` and `kinds`; a reply without them means exactly the five states and three kinds. Nothing answers today, so a probing program treats gPTY as unsupported and shows no status at all even though the parser work lands. Fix: `OSC 7501;?` queues `\x1b]7501;?:states=idle,working,done,blocked,error:kinds=permission,question,auth\x1b\\` (byte-exact, pinned in the note), coalesced to one reply per `feed` and one per 100 ms per terminal. The line parser has no PTY writer, so the reply must ride the existing emulator-reply queue (`crates/gpty-core/src/term.rs:167`): the parser collects it, the engine queues it, and the existing tail drain writes it with the rest of the DSR/mode replies (`crates/gpty-core/src/engine.rs:1034`); a new `TermGrid.queue_reply` bounds the queue at 32. Tests: BEL and ST forms, one query in a multi-report feed, the reply bytes and rate limit at parser+grid level; no report field is ever written back. |
| ⬜ | TERM | **Primary device attributes go unanswered, so the protocol's fallback probe waits out its timeout** - the spec's detection recipe tells a program to send primary device attributes (`CSI c`) right after the 7501 query and treat a DA reply that arrives first as "protocol unsupported", so a program that cannot read replies still gets a bounded answer. vte 0.15's Performer has no `c` arm and alacritty does not answer DA1, so nothing comes back and a probing program spends its full timeout before falling back - the terminal is the one part of the recipe that is missing. Fix: answer a bare `CSI c` (and `CSI 0 c`) with `\x1b[?1;2c` (VT100 with advanced video) from `LineParser::csi_dispatch` through the same bounded reply queue as the 7501 query. Tests: one raw-grid feed of `CSI c` yields exactly one reply; the existing CSI handling is untouched. Contingency in the note: if a future alacritty starts answering DA1, the one-reply test fails and the parser's arm is deleted, so the terminal never double-answers. |
| ⬜ | IPC | **`paneStatus` says the state but not what the program says it is doing** - `StatusDocument` (`crates/gpty-core/src/engine.rs:135`) carries `agent_state` and `agent_state_tier` only, so a script or an orchestrator can see `needs-attention` but not which kind, how far a job got, or the program's one-line reason; a GUI must scrape the titlebar for it. Fix: a nested `program_status` object with `{revision, state, kind, progress, app, title, msg, records, blocked}`, where `state` is the primary record's state (not the merged tier result), `msg` is the full decoded value (2048-byte protocol limit), and counts are per-terminal; `unstarted_status_json` returns the empty view so a pane's first frame still parses. Add `get_program_status` beside `get_agent_state` (`crates/gpty-gdext/src/lib.rs:489`) for the 4 Hz pane poll, with the message capped at 160 bytes for display and the display JSON cached until a mutation; `get_agent_state` stays the one string the dispatcher compares. Tests: the engine's unstarted/started document tests, the workspace status contract, and the wiki `ipc.md` field list. |
| ⬜ | GUI | **A blocked pane's title bar never says what it is waiting for** - the badge shows one of four silhouettes and a fixed label, so a `blocked` pane cannot say whether it needs permission, an answer, or a sign-in, and a `working` job cannot show 40 percent even though OSC 7501 supplies both. Fix: the badge gains `set_detail` and a pure `detail_text` - kind words for `needs-attention` ("Needs permission", "Needs an answer", "Needs sign-in"), then `app`, then `title`, then the one-line `msg`, truncated at 200 chars and used as both tooltip and accessible name - and a new `StateStrip` (`godot/scenes/ui/state_strip.gd`) draws a 2 px determinate bar on the titlebar's bottom edge (`ACCENT` working, `WARNING` blocked, hidden without a `progress`). `TerminalPane` reads `get_program_status` in its existing 250 ms poll (`godot/scenes/terminal/terminal_pane.gd:1048`), applies detail only when the primary record's state equals the displayed badge state (a Tier 1 state must never be captioned with a stale message), and exposes `agent_state()`/`program_detail()` on `PaneBody` for the workspace surfaces. A compact 16×16 badge mode serves the sidebar. Tests: detail composition, kind labels, truncation, compact geometry, strip visibility and width, accessibility names. |
