Follow-ups to the v0.6.0 knowledge base that were parked as unscheduled work: two heading-anchor defects, derived related-note suggestions, templates and daily notes, and shared graph nodes in the concept editor.

## v0.12.0 - Knowledge Base Follow-ups

| Done | Area | Item |
|:---:|:---:|---|
| ⬜ | WIKI | **A heading whose text also appears in the body can land the preview on the body line** - `MarkdownView.scroll_to_heading` searches the *rendered text* for the heading's line (that is what makes source lines and rendered lines agree), so a paragraph that says exactly the same thing and appears first wins the search. Found while closing the fragment item (2026-10-18); the renderer emits no anchors, so text matching was the chosen approach. Display-only - a wrong scroll inside the right note, never a wrong note. Fix direction only if it is noticed in use: have `GptyMarkdown.render` track each heading's plain-text offset while emitting events and map that offset with `get_character_line`, or emit an invisible marker the view can find. |
| ⬜ | WIKI | **Setext headings have no anchor** - `MarkdownAnchors` recognizes ATX (`#`) headings only, so `[[note#Title]]` does not land on a `Title` over `===` heading, and a source line under one derives no anchor (it lands at the nearest ATX heading above, or the top). The preview renders setext headings (pulldown-cmark does), so the gap is navigation, not display. Found while closing the fragment item (2026-10-18); rare in Obsidian-shaped notes, which is why it was scoped out. Fix direction: add the two-line `===`/`---` form to the scanner - carefully, because a leading `---` is frontmatter and a thematic break is not a heading. |
| ⬜ | WIKI | **Suggested related notes from the FTS index** - score a note's own top terms against the rest of the vault (`notes_fts` already holds them, porter-stemmed) and surface the neighbours as *suggestions*: fully derived, no store, no authoring, no trust question, display-only like everything else in the graph. This is the middle layer between measured mention counts and declared weights (v0.6.0), and it answers "what else is about this" without an LLM; queue it once the link layer has settled. |
| ⬜ | WIKI | **Templates** - a designated folder whose contents are inserted into the open note with a **closed token table** (`{{date}}`, `{{time}}`, `{{title}}`, `{{vault}}`) expanded in Rust and inserted as an *edit*, so the user still saves and templates open no second write path into the vault. Parked off-release by the owner's call (2026-10) because nothing depends on it; scheduled here by the roadmap restructure, and it still adds no trust surface. The scripting half of this on the Obsidian side is its Templater plugin - the ecosystem this project stays out of. **Daily notes are a cron-job on a template** (open or create `<folder>/<pattern>.md` for today, then apply one) and can ride along when this is built, reusing the create-note verb; they are not worth an item of their own. |
| ⬜ | CONCEPT | **Shared graph nodes (free DAG)** - the visual editor's rules are chains because a compiled entry's identity is the trigger's name: one trigger = one rule, and a shared condition or action would compile two entries under one name. Fan-in/fan-out needs OR'd triggers (`triggers: [regex…]`) and a rule id independent of the trigger name in the vocabulary. Deferred from v0.5.4 - revisit with demand evidence, not before. |
| ⬜ | DOCS | **Capability catalogue: AGENT** - record the agent surface the way TERM, IPC, GUI and WIKI are recorded: the event socket's vocabulary and its capability scoping (`crates/gpty-gdext/src/omp_events.rs`), the four badge silhouettes and what each is derived from (`godot/scenes/ui/agent_badge.gd`), capture routing (`crates/gpty-core/src/concept.rs`, `crates/gpty-gdext/src/capture_api.rs`), the private Inspector bridge (`crates/gpty-gdext/src/ai.rs`, `godot/scenes/panes/inspector_pane.gd`) and the Reasoning projection. Schema, statuses and gate are in `docs/content/docs/agents/testing.md`; acceptance is `./scripts/check-capabilities` green with the new area. |
| ⬜ | DOCS | **Capability catalogue: CONCEPT** - the concept engine is the one place gPTY acts on program output, and no record states its contract: trigger matching and capture routing as pure functions (`crates/gpty-core/src/concept.rs`), the capture state machine and its modes (`crates/gpty-core/src/engine.rs`), the default concept set (`godot/concepts.default.json`), the routing that decides which pane receives a capture (`godot/scenes/terminal/concept_router.gd`) and the `gpty_state` OSC as the declaration path (`crates/gpty-core/src/parser.rs`). |
| ⬜ | DOCS | **Capability catalogue: MEDIA** - the media backend's properties are its allowlists and its bounds, not its features: the path gate and component allowlists (`crates/gpty-media/src/lib.rs`), stream selection and demuxer aliases (`probe.rs`), the decode thread's bounded queues and seek epochs (`session.rs`), the packed RGBA/PCM wire (`crates/gpty-gdext/src/media_api.rs`) and what the pane refuses (`godot/scenes/panes/media_files.gd`). Several of these are security properties, so the record is the place a regression would show up as a missing capability rather than a silent widening. |
| ⬜ | DOCS | **Capability catalogue: CLI** - the command surface is a published contract (27 MCP tools, a skill printed by `gpty --skill`) with no inventory behind it: argv-only spawn and the stale-binary check (`crates/gpty-cli/src/main.rs`), the argument translation and its refusals (`commands/wire.rs`), the tool-name gate (`commands/schema.rs`), daemon start/stop/status, plugin verbs and the layout verbs. |
| ⬜ | DOCS | **Capability catalogue: PLUGIN** - record what a plugin may and may not do: manifest validation and its caps (`godot/scenes/terminal/plugin_review_text.gd` and the shipped validator), the clone-review-consent handshake and the trust store (`godot/scenes/autoloads/trusted_store.gd`), the registry index and its policies (`godot/assets/registry.json`), and the per-plugin config/state/log directories. The record is the audit surface for the next `plugins.md` change. |
| ⬜ | DOCS | **Capability catalogue: SEC** - the trust boundaries are currently described in prose in `SECURITY.md` and `docs/content/docs/agents/security.md`, so a control can be weakened without a record noticing: workspace trust, the plugin review, the vault root registry, the OSC 52 write policy, owner-only store files (`crates/gpty-core/src/owner_only.rs`) and the log-hygiene rule. Each becomes a record whose `mechanism` names the enforcement point and whose `evidence` is the code, so deleting the enforcement breaks the gate rather than the documentation's accuracy. |
| ⬜ | DOCS | **Capability catalogue: CORE** - the engine's own contract: PTY spawn and validation (`crates/gpty-core/src/pty.rs`), the vte-to-grid feed and damage tracking (`term.rs`), capture modes and the capture state machine (`engine.rs`), scrollback store plumbing and damaged-file recovery (`store.rs`, `history.rs`), and the keymap. This is the area where a `partial` record is a fidelity bug with a name. |
