Depth work on platforms and media the project already supports: a narrower Windows media build, hardware decode, `libdav1d` for AV1, and fuzzing through the GDExtension boundary.

## v0.12.0 - Platform & Media Depth

| Done | Area | Item |
|:---:|:---:|---|
| ⬜ | MEDIA | **Narrow the Windows media build** - the `vcpkg` FFmpeg carries a wider internal codec set than the pinned Unix configure. Either pin a vcpkg baseline with a curated feature set, or build the same 9.0.2 tarball under `MSYS2`/`clang-cl`; the runtime allowlist already refuses unlisted codecs, so this is surface and size, not behavior. |
| ⬜ | MEDIA | **Media hardware decode** - VAAPI/VideoToolbox/D3D11VA through FFmpeg hwaccel. The software path is deliberate for the first backend; hardware frames need a transfer step, a per-platform fallback and the same bounded-queue discipline. |
| ⬜ | MEDIA | **Use `libdav1d` for AV1** - the pinned build currently uses FFmpeg's native AV1 decoder. dav1d is the faster, standard implementation (BSD; no GPL concern), so this is a build-recipe + CI change behind the same `Id::name()` allowlist, not an API change; measure first. |
| ⬜ | BUILD | **FFI fuzz testing** - fuzzing *through* the GDExtension boundary itself (the binary interface and its Godot-side callers) and a continuous run on an external fuzzing service. The Rust-side targets (grid `feed`, line parser, IPC decode, Markdown and vault code) are built in v0.7.1; this is what that leaves. |
| ⬜ | GUI | **An X11 `BadMatch` from `X_SetInputFocus` is logged after an overnight run or suspend/resume** - observed 2026-10-28 while gPTY was hosted by `godot -e` and left running overnight (a sleep cycle is suspected but unconfirmed): `ERROR: Unhandled XServer error: BadMatch (invalid parameter attributes)`, major opcode 42 (`X_SetInputFocus`), serial 0, current serial 86239367, at `default_window_error_handler` (`platform/linuxbsd/x11/display_server_x11.cpp:1335`). Unknown and to establish: whether the app stayed usable or lost focus, whether it repeats per resume, and whether the failing request came from the editor window or the project window - `-e` puts both on one X connection, so the first split is editor-only versus project-only overnight runs. Repro: a real X11 session (not headless) with a VM suspend/resume or lock/unlock, the project run both from the release GUI and through `godot -e`, with `xtrace`/an Xlib error handler and Godot `--verbose` capturing the request; then check gPTY's focus and window paths (`window_chrome.gd`, `grab_focus`, `DisplayServer.window_request_attention`, `window_set_mode`) and whether focus is restored on `NOTIFICATION_WM_WINDOW_FOCUS_IN`/`NOTIFICATION_APPLICATION_FOCUS_IN` before the window is mapped. If the request is Godot's, check the 4.7 upstream and document or pin a workaround; if it is gPTY's, defer focus restoration until the window is viewable and do not call `grab_focus`/`window_move_to_foreground` on a stale window. Impact: log noise and possible focus loss after resume; no crash observed. Low priority, platform robustness; a suspend/resume checklist is the test (a GUT notification-level test covers a gPTY-side guard, but an X error needs the real display). |
