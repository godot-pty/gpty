Every IPC row, by ID and in allocation order. The queue and its priority live on the release chain pages; this page is the evidence behind each row.

## IPC-1

**MCP server** - Model Context Protocol integration. Run `gpty mcp` to expose terminal workspace control as tools for AI agents (Claude, Gemini, etc.). Agents can spawn panes, inject text, and manage layouts.

Commits: d17bac7

## IPC-2

**JSON Schema** - `gpty schema` outputs a JSON Schema describing all CLI commands and their parameters. `--format mcp` produces an MCP tools manifest. Enables AI tool discovery without hardcoded manifests.

Commits: d17bac7

## IPC-3

**IPC bridge** - Rust `IpcServer` on a background tokio task accepts Unix socket connections, parses JSON-RPC, and queues requests. GDScript polls `drain_ipc_requests()` each frame and dispatches to workspace methods, then responds via `respond_ipc()`.

Commits: d17bac7

## IPC-4

**Windows named-pipe IPC** - per-connection named-pipe instances on the server (v0.3.0 never compiled on Windows); local cross-check via xwin/clang-cl plus the CI `rust-windows` job keeps it green

Commits: d17bac7

## IPC-5

**Stable public pane IDs** - every pane auto-generates a persisted `attachment_id` (`pane-XXXXXXXX` via `PaneTypes.generate_attachment_id()`, `PaneBody.apply_settings` choke point); `newPane` returns it and `listPanes` reports `id` alongside the display `label`. AGENTS.md attachment-id bullet documents the public-id semantics.

Commits: d17bac7

## IPC-6

**Pane env markers** - `GPTY_ENV=1` + `GPTY_PANE_ID` injected as trusted runtime vars at spawn (`start_shell` pane_id param; `GPTY_PANE_ID` falls back to the per-PTY session id); both keys blocked from untrusted env. AGENTS.md env-sanitization bullet updated with the new trusted vars.

Commits: d17bac7

## IPC-7

**Pane read/status/run/wait IPC** - `paneRead` (plain text from grid + scrollback, capped), `paneStatus` (pid / running / exit_code / idle_ms primitives), `paneRun` (command spawn; exit via `paneStatus`), `waitForOutput` (`paneWait`: server-held response, Rust `regex` scan of a 512-line ring buffer, 60 s deadline). Substrate primitives only - no agent state machine in core.

Commits: d17bac7

## IPC-8

**Event subscription** - `subscribe` / `eventsPoll` on the event socket (never the control socket); bounded per-subscriber queues fed by `GptyTerminal.emit_event` from concept matches and pane spawn/kill. Push transport deferred.

Commits: d17bac7

## IPC-9

**IPC version sourcing** - the IPC `version` response now comes from the crate via the static `GptyTerminal.get_app_version()` (`env!("CARGO_PKG_VERSION")`, `crates/gpty-gdext/src/lib.rs`); `workspace.gd` no longer hardcodes "0.3.0".

Commits: d17bac7

## IPC-10

**MCP expansion** - `pane-read`, `pane-status` (no-arg = agent-status-list), `pane-run`, `pane-wait`, `broadcast` (tagged fan-out) auto-generated from the new CLI commands; pane tags persist and sanitize like `attachment_id`. AGENTS.md MCP list updated (14 → 19).

## IPC-11

**Generic event vocabulary** - adapter-neutral event names (`agent.started`, `turn.started`, `tool.call`, `thinking.delta`) mapped from the OMP extension's allowlist at the event-socket boundary; Reasoning and Tier 1 agent-state detection consume the generic contract. Same commit: update the AGENTS.md OMP-only data-flow diagram.

## IPC-13

**MCP tool allowlist** - `tools/call` mapped *any* name to an IPC method, reaching methods that were never published as tools (e.g. `shutdown`). It now rejects anything outside the advertised schema.

## IPC-14

**Event-channel hygiene** - (a) subscriptions no longer leak: `SUBSCRIPTION_IDLE` (120 s without an `eventsPoll`) releases the slot and its queued events on the next subscribe/emit, so the 64-slot cap cannot be exhausted by abandoned clients; unit-tested in both directions (a stale slot is released, a freshly-polled one survives) and end-to-end (a subscribe at the cap reuses an abandoned slot instead of failing). (b) `reasoning.delta` rendering is coalesced: `_append_live_text` and `_refresh_turn_layout` now use `MarkdownView.set_markdown` (at most one re-parse per 75 ms per view) instead of `render_now`, which re-parsed the whole accumulated turn - and every other turn - for every token; a new `rendered` signal re-syncs fold heights once the coalesced text lands, and a settling turn still finalizes synchronously. GUT: a 30-delta burst leaves the view unrendered until the debounce, then shows the whole turn. (c) The OMP translation boundary is a per-event **field allowlist** (`ALLOWED_FIELDS`, built field-by-field with caps) instead of a rename-and-pass-through, so prompts, answers, tool arguments/results or any future extension field cannot ride along; unit-tested with a hostile payload (forbidden fields dropped, wrong types and over-cap values dropped, unknown events rejected). Live probe against the real socket: subscribe/poll round-trip, wrong capability → `-32001`, oversized `thinking` text → `-32602`, and a `tool.finished` carrying `prompt`/`tool_args`/`answer` was accepted, translated and delivered - the allowlisted `is_error` set the terminal's Tier 1 state to `needs-attention`. (Deferred from v0.5.3.)

Commits: d17bac7

## IPC-15

**A second GUI instance hijacks the control socket** - `IpcServer::serve()` unlinks an existing socket after checking only that it *is* a socket owned by this UID (never that anything is still listening), so a second instance silently takes the path and orphans the first: both windows keep running, every CLI command goes to the newest one, and the older instance's control surface is gone with no message anywhere. Measured on the v0.5.5 download: two `gpty-gui` processes, two listeners bound to `/run/user/1000/gpty.sock`, the older one's inode unlinked (`ss -xlp` shows both pids; `ls` shows one path entry). The trigger is on the CLI side - `daemon::ensure_running()` probes with a **one-second** `version` call and spawns a GUI on *any* failure (`_ => spawn`), so a transient stall during the probe, not a dead GUI, produces the second instance: `./gpty new-pane` from the extracted bundle created a new GUI instead of adding a pane to the running one. Fix: (a) in `serve()`, distinguish stale from live before replacing - try `UnixStream::connect` and refuse to bind when a server answers (the existing checks already fail closed for a non-socket or another user's file; a live one is the same rule); (b) a GUI whose control server refuses to bind must not keep running as a window with no API - log and quit, which makes the spawned-instance case self-correcting, since the CLI's wait loop then reconnects to the original; (c) in `ensure_running()`, spawn only when the socket is genuinely dead (refused / no such file) and retry once on a timeout, so a busy GUI is never duplicated. Tests: binding over a live listener must fail *and* leave that listener reachable; a stale socket must still be replaced (the planted foreign-file case is already covered); a successful probe must never spawn. Also apply the rule to the **event socket** (`gpty-events.sock` was stolen the same way - two listeners on that path too): one instance, both sockets, or neither. Recovery is manual until this lands: the orphaned instance cannot rebind (its path entry is gone), and closing the *newer* one leaves a stale socket the CLI reads as dead and answers by spawning again - close both, start one. **Closed:** `serve()` now probes the path and refuses a socket a server answers on (`AlreadyExists`), replaces only a refused one (a crash leftover - still covered by a test), and fails closed on anything else; the event socket takes the same path and the Windows pipe branch refuses a taken name instead of spinning. An instance that cannot bind records why and sets the existing shutdown flag, so it quits through the scene tree with a toast (`OS.alert` blocks on zenity - measured - so headless quits at once). Tests: the probe decision table, a refused bind leaving the live server reachable, a stale socket still replaced, the refused-bind flag/reason in gdext, and a live smoke step (a second GUI must exit with the first still answering) that runs on Windows too. That step found a second defect the Unix tests cannot see: the `FILE_FLAG_FIRST_PIPE_INSTANCE` claim was process-global, so whichever of the two servers created a pipe first consumed it and the other created a *second instance* of a name another GUI owned (Windows allows that) - it is per endpoint now. Verified: `windows-smoke` green (GUT 491 + the new step), Linux green.

Commits: d17bac7

## IPC-16

**Agent access** - vault search/read exposed via CLI and MCP so agents can query the knowledge base through the public pane-API primitives. the knowledge base is now a primitive pair over the control socket - `vaultSearch` / `vaultRead`, reached by `gpty vault search <vault> <pattern> [--limit]` and `gpty vault read <vault> <path>`, and advertised as the `vault-search` / `vault-read` MCP tools (21 tools total). Both are answered **natively in Rust** (`crates/gpty-gdext/src/vault_ipc.rs`, registered in `ipc.rs` beside `version`/`shutdown`) rather than through `ipc_handlers.gd`: a vault is a directory, not workspace state, so no handler has a workspace to consult, and the walk plus SQLite run on the blocking pool (`spawn_blocking`) so an agent's query cannot stall the frame that polls IPC - the wiki pane's own synchronous calls stay as they were, user-driven and bounded. **Search re-indexes before it queries** (`index_vault`; only notes whose mtime/size changed are re-read), so a note edited outside gPTY - Obsidian, an editor, another agent - is searchable without any pane reopening the vault; its answer is `{results: [{path, title, snippet}], total, truncated}`, and `truncated` reports the 2000-note walk cap so a partial index never looks complete. **Read** reuses `read_vault_note` unchanged: the vault-relative `.md` vocabulary, the regular-file gate and the 1 MiB cut with the torn UTF-8 tail dropped, and neither method writes to the vault (the only write is the derived index in gpty's state directory). Refusals are JSON-RPC errors - `-32602` for a malformed request (missing param, relative/non-directory vault), `-32000` with `NoteError::code()` in `data.code` for a refusal - so `not_found` and `bad_path` are distinguishable without parsing prose. A vault command is a query, so `may_autospawn` returns false (the v0.5.6 rule). Tests: five Rust unit tests in `vault_ipc.rs` (index-on-search, externally edited note, title/snippet, string `limit` from MCP, read containment, malformed params - all on unique temp vaults, no shared state), a CLI roundtrip pinning both parameter spellings, schema assertions for the two tools, the existing seam contract tests (native methods parse as local registrations; the CLI literals cover them), and a live smoke step that seeds a temp vault, searches, edits a note outside gPTY and searches again, reads a note, and asserts the `not_found` code - run by `ci-check`/CI on Linux and `windows-smoke` on Windows. Docs updated: AGENTS.md (tool count/list + the native-API bullet), README, `skills/gpty/SKILL.md`, the CLI, IPC and gdext crate READMEs, the testing doc and manual checklist, and the CHANGELOG.

Commits: d17bac7

## IPC-17

**The 30 s connection timeout caps every deferred-answer method** - `IpcServer::serve` wrapped the whole `handle_connection` future - read, dispatch, handler, response write - in `CONNECTION_TIMEOUT` (`server.rs`, 30 s), so a method whose answer is deliberately held could never outlive it: `paneWait` publishes a 60 s ceiling (`PANE_WAIT_TIMEOUT` is 70 s so the fallback covers it) and `pluginInstall` waits up to 300 s for a human reading the review dialog, yet the server dropped both connections at 30 s. The client then read an empty socket while the fallback still believed the request was alive. Found 2026-10 while giving `vaultSearch` a read budget (its re-index pass can outlast a default 5 s call). the deadline is split. `IpcServer` keeps a 30 s `IO_TIMEOUT` on the two phases a client controls - the request read and the response write, shared through one `write_response` helper so a stalled client still cannot hold one of the 16 slots - and each registration now carries its own **dispatch budget** (`register_with_timeout`, with `register` defaulting to the new `DEFAULT_DISPATCH_TIMEOUT` of 30 s). The GUI registers every GDScript-routed method at `fallback_timeout(method) + DISPATCH_SLACK` (`dispatch_timeout` in `gdext/src/ipc.rs`): 75 s for `paneWait` and 305 s for `pluginInstall`, so the handler's own fallback answers a clean JSON-RPC error first and the server budget only frees a connection from a wedged handler. An overrun is now `-32000 handler timed out after N ms` rather than a dropped socket. Tests: a new `gpty-ipc` case runs a 2 s handler under a 50 ms budget and asserts the client receives the timeout error (and that a held handler inside its budget still succeeds), and `deferred_methods_get_contract_covering_fallbacks` asserts every routed method's dispatch budget outlives its fallback, with `paneWait`'s past the published 60 s and `pluginInstall`'s past the 300 s review window. Verified live against a headless GUI: `gpty pane-wait … --timeout-ms 33000` (never matching) answered `{matched: false, timed_out: true}` at **33.0 s**; before the fix the server dropped the connection at 30 s. Docs updated: the `gpty-ipc` README connection-limits bullet, AGENTS.md's IPC-hardening bullet, and the CHANGELOG.

Commits: d17bac7

## IPC-18

**One malformed request drops the rest of the queued batch, and the dropped callers wait out their timeout** - **reproduced** at the audit and **re-run** in isolation today. The GUI's drain loop (`Workspace._process`) parses each request's `params` with `JSON.parse_string` and guards only the `null` result; valid JSON that is not an object (`[1,2]`, `"x"`, `5`) becomes `params`, then `params.get(...)` (the `paneWait` branch) or the typed `ipc_handlers.handle(ws, method, params: Dictionary)` raises a call error that aborts the whole function. The requests were already taken off the Rust queue (`drain_ipc_requests`), so everything after the bad one is neither handled nor answered; probe: three requests, the middle one `"[1,2]"`, handled one and lost the third. Any client that gets through the socket checks can do it, which includes any pane until the v0.10.1 permission item lands. Fix, at both ends: the Rust server rejects `params` that is neither absent nor an object with a JSON-RPC invalid-params error before queueing (the IPC crate owns the request edge, and a daemon will keep it, so this is not throwaway work next to the v0.10.1 Rust-side validation item, which covers per-method shapes and can build on it), and the GDScript drain keeps a `params is Dictionary` guard that answers an error and continues with the next request - defence in depth, because GDScript has no try/catch and the loop must never trust its queue. Tests: a Rust server test (an array `params` gets an error response and the next request is served); a GUT test of the drain with a non-object between two valid requests, both answered. **Shipped 2026-10-30, both ends:** `IpcServer::handle_connection` answers a `params` that is not an object (absent and explicit `null` still mean "no arguments") with `JsonRpcError::INVALID_PARAMS` before it is dispatched or queued, naming the JSON type it saw rather than echoing the value; `WorkspaceIpcHandlers::request_params` is the drain's second layer, and the loop answers the same `-32602` and continues with the next request, so a client sees one contract whichever layer refused. Tests: `server::tests::unix::non_object_params_are_refused_and_the_server_keeps_serving` (array, string, number and boolean each answered `-32602` and the server still serving, absent and explicit-null params still dispatched with a null value); `godot/tests/unit/test_ipc_request_params.gd` walks a valid → array → valid batch through the drain's decision and asserts only the middle one is answered and skipped, that every non-object kind is refused, and that an object passes through unchanged. Live: the pane-API smoke gained a `malformed params` step that sends a raw `[1,2]` `params` over the control socket between two `listPanes` calls; measured on the fixed build it answers `-32602` and both neighbours answer, and with both guards removed the same step reproduces the audit's symptom - `-32000 timeout waiting for GUI response` after the 5 s fallback, because the aborted drain never answered it. Docs: the control-socket bullet in SECURITY.md and the IPC params contract in `docs/content/docs/agents/security.md`.

Commits: d17bac7, d8c38a9, 6cecfd6

## IPC-19

**A program can create panes without limit through the control socket** - **measured first** (headless GUI, 2026-10-30): a pane costs about 6 MB in its shell and the GUI grows by under 1 MB per pane, and a profile with 300 tiles restored **300** live panes (GUI 353 MB, children 1.1 GB, `list-panes` then answering in 3-5 s); 128 tiles overran the CLI's 5 s timeout, while 96 took 3.9 s and 0.9 GB total. Closed by one window-wide ceiling, `Workspace.MAX_LIVE_PANES = 96` - counted across every workspace, because a hidden workspace's pane keeps its PTY, child process and grid, so a per-workspace allowance would multiply by the eight tabs instead of bounding the window - and one decision, `_pane_ceiling_refusal()`, whose text every creation path shares: `_spawn_pane_into` (which is where `newPane`, `paneRun`, the palette, the sidebar, a pane's `request_pane` and profile activation all arrive) refuses before a body or a tile exists, `_spawn_bulk` clamps to `_live_pane_room()` and says why when it stops short, and `_restore_into` - the file path, reached by a profile, `layoutLoad` and the workspace store - restores what fits and toasts `Restored N of M panes.` followed by the same refusal text. A refusal names the limit rather than dropping: the control socket's error carries that text (the grid's own "Grid is full" stays for a workspace with no room below the ceiling) and the GUI shows it as a toast. Tests: `godot/tests/integration/test_pane_ceiling.gd` asserts the count spans workspaces (a hidden workspace's pane counts), the boundary is the constant (one short is not a refusal, filling it is, and the message states `MAX_LIVE_PANES`), `newPane` and `paneRun` at the ceiling return the limit error and add no tile (nothing starts), a 5-tile restore into a 2-pane room creates 2 and toasts the exact remainder, two restored workspaces share the one room, and closing a pane frees a slot - the suite pads the count in a subclass so no test starts 96 shells. Docs: SECURITY.md's "Hardening in place" and the wiki's `security-model`/`control-api` bounds state the ceiling and the measurement. The spawn cost it exposed is its own row in v0.8.2.

Commits: d17bac7, 3823302, 6cecfd6

## IPC-20

**`new-pane` through MCP ignores the pane type and always creates a terminal** - closed 2026-10-31 by one translation between the two vocabularies. Reproduced on the 0.7.0 debug build against a sandboxed headless GUI: `tools/call` `new-pane` with `{"pane_type":"wiki"}` answered `{"type":"terminal"}` and `list-panes` then showed two terminal panes. The MCP server forwards `arguments` verbatim as IPC params (`mcp.rs` `tools/call` passes `arguments` through unchanged), but the GUI handler reads the CLI's wire names (`ipc_handlers.gd:143`, `params.get("type", "terminal")`), so every clap argument id that differs from the wire name is dropped: `pane_type` here, and the array-shaped `args`/`tags` that `schema.rs` declares as `"string"` (every property is typed string) while the handler consumes arrays (`sanitize_shell_args` returns `[]` for a string, `sanitize_tags(raw: Array)` raises on one). The same generation drops value types, so `pane-read`'s `lines` is a string and `focus` is an enum of two strings. Fix: one translation, `commands/wire.rs`, derived from each tool's clap definition. It reads the shape from clap itself (`Append` is a string array, a flag a boolean, an integer value-parser an integer), renames the ids whose wire key differs through one `RENAMES` table (`pane_type`->`type`; `title` keeps its name and the handler turns it into the pane's internal `title_label`), turns the one non-1:1 tool inside out (`vault-weight`: `clear` becomes `weight: null`, and naming neither is refused as the CLI refuses it), and just as deliberately refuses what it cannot honour: an unknown key names itself and its nearest valid neighbour ("unknown argument 'paneTipe' for tool 'new-pane' - did you mean 'pane_type'?"), a wrong JSON type names the type it needed ("argument 'lines' must be an integer, got a string"), and a non-object `arguments` is refused - all `-32602`. Integers and booleans still accept the strings the old schema advertised, so a client built against it keeps working. The manifest stopped lying the same way: `lines`/`timeout_ms`/`limit`/`weight` are `integer` with their clap defaults, `focus`/`clear` `boolean` (not an enum of "true"/"false"), `args`/`tags` `array of string`, `split` an enum of the four sides, and `clap_command_to_json_schema` reuses the same derivation, so `gpty schema` stopped calling an integer a string too. Every tool now declares `readOnlyHint`/`destructiveHint` from two closed sets (`READ_ONLY_TOOLS`, `DESTRUCTIVE_TOOLS`), so a tool that kills panes and one that lists them no longer look alike to a client deciding whether to ask first. The receiving half: `newPane` reads `title` (turned into the spawn option `title_label`, sanitized by `PaneTypes.sanitize_title` - one line, 64 characters, U+FFFD refused) and `focus` (a bool; `"false"` is truthy in GDScript, so a non-bool is refused rather than coerced), applies focus with `activate_pane`, and `sanitize_tags` lost its `Array` parameter type - a string reached it as a call error that aborted the whole IPC batch, which the string-typed schema invited. `--title` and `--focus` now parse as the values the handler consumes (`--focus false` used to be rejected by clap), and `--split` is an optional enum rather than a `bottom` default no code read. **Verified end to end** on a sandboxed headless GUI: `tools/call new-pane {"pane_type": ...}` created code_viewer, file_tree, inspector, reasoning, wiki, media and cli_view (each answering its own type, previously every one a terminal), `{"tags":["agent","ci"]}` landed on the pane, `{"focus":false}` left the active pane alone where `{"focus":true}` took it, and both mistake classes answered the `-32602` sentences above. Tests: `wire_keys_are_the_keys_the_handlers_read` (every translated key is one the handler reads - the arms, the drain loop and the native vault handlers parsed from source), `pane_type_reaches_the_handler_as_type`, `every_advertised_argument_is_translated`, `an_unknown_argument_names_the_key_and_the_nearest_valid_one`, `lists_accept_arrays_and_a_joined_string_only_where_clap_joins`, `scalars_refuse_the_wrong_json_type`, `vault_weight_asks_for_exactly_one_of_weight_and_clear`, `arguments_that_are_not_an_object_are_refused`, `the_rename_table_only_names_arguments_that_exist`, `argument_types_are_the_ones_clap_parses`, `every_tool_declares_its_hints`, `new_pane_flags_parse_into_what_the_gui_honours`, and the wiring pair `an_mcp_tool_call_translates_its_arguments_first` / `an_mcp_tool_call_with_a_bad_argument_never_reaches_the_gui` (a real temp IPC server: the handler sees `type`/`title`, and a refused call never opens a connection to it); GUT `test_new_pane_creates_the_type_the_caller_names`, `test_new_pane_applies_the_display_title_it_is_given`, `test_new_pane_honours_focus`, `test_sanitize_tags_degrades_a_non_array_to_no_tags`, `test_sanitize_title_keeps_one_line`. The one advertised argument still inert (`split`) is named in `wire.rs`'s `INERT_ARGUMENTS` so the contract test cannot quietly grow a second, and it is the row below. The spec's `isError` half is queued separately (**An MCP tool failure is a protocol error, not a tool result**).

Commits: f460c31, 6d297b5

## IPC-22

## IPC-23

**An MCP tool failure is a protocol error, not a tool result** - closed by classifying the three outcomes. `dispatch_tool` returns `ToolCallError::{Malformed, Transport, Refused}`: a translation refusal stays `-32602`, a dead endpoint `-32603`, and a handler's refusal becomes a *successful* `tools/call` response whose result is `{content: [{type: "text", text: <the handler's sentence>}], structuredContent: {error: {code, message}}, isError: true}`. A success wraps the value the same way (compact JSON in `content.text`, the object in `structuredContent`), and a daemon command reporting `status: "error"` is `isError: true`. Tests: `a_handler_refusal_is_a_tool_result_with_a_readable_sentence`, `a_successful_tool_result_agrees_with_its_structured_content`, `a_malformed_call_and_a_dead_endpoint_are_protocol_errors`. AGENTS.md's MCP section and the bundled `gpty` skill now describe the result shape
