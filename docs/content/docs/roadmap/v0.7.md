The next task in the roadmap is the first unchecked row below.

| ✅ | CLI | **The Windows smoke's CLI occasionally exits `0xC0000374` (`STATUS_HEAP_CORRUPTION`) on `inject`** - one occurrence so far: run 39262704860 / job 118094242727 on commit `0a6c940`, at the `gpty state` step's first `inject` (`--text "\"…\\gpty.exe\" state needs-attention"`). The CLI printed no stdout and no stderr, so the corruption happened during the call, not at exit; the same SHA's rerun of the same job passed that step, and the command has passed on every earlier commit. Each CLI command is a fresh process and makes two named-pipe connections (the best-effort `version` probe, then the command itself), so the plausible class is a Windows named-pipe client teardown race (mio/tokio), not a logic error in `inject`. Fix direction: keep the failure diagnosable (the smoke now tails the `--log-file` engine log and carries the pane tail plus the hex status), then reproduce with a Windows-only loop of throwaway `pane-status`/`inject` processes (N runs ≈ N connection teardowns) before changing anything; if it reproduces, test the CLI's runtime shape (`process::exit` from `#[tokio::main]` skips a clean runtime shutdown; a current-thread runtime removes worker-thread teardown entirely) and the mio client path. Do not add a retry around the step: the crash is the signal. it did not reproduce before changing anything - no Windows host is reachable from this workspace - and it has not been seen again in the four windows-smoke runs after the recorded failure (39276550729, 39305294761, 39307240548, 39308596924; 39275354197 and 39272179130 failed in GUT, not here). The runtime-shape half was applied rather than left waiting for a second occurrence: `crates/gpty-cli/src/main.rs` is now `#[tokio::main(flavor = "current_thread")]`. Every command is one request in a process that exits as soon as it has an answer, and nothing in the CLI or `gpty-ipc` uses `spawn_blocking`, `block_in_place` or `tokio::process`, so the multi-thread flavor's workers bought no parallelism - they were the only concurrency around `process::exit`, which is exactly what a worker torn down mid-allocation needs to corrupt the heap. It also removes the worker pool's startup from every invocation: measured on Linux, 300 `gpty version` runs went from 1.037 s to 0.599 s (3.46 → 2.00 ms each). The loop the item asked for is permanent now: `scripts/smoke_pane_api.py` runs 100 throwaway `pane-status` processes right after the pane-status checks - ≈ 200 connections, because each process opens the best-effort `version` probe and then its command - and a nonzero exit fails with its hex status, the pane tail and the engine-log tail, with no retry. Verified live: the Linux smoke passes with the new step, `cargo test -p gpty -p gpty-ipc` passes, and `./scripts/ci-check --fast` is green. The mio client path was not implicated: the only known heap-corruption class there is tokio#6369 (a `ScheduledIo` use-after-free when a named-pipe client disconnects), fixed by mio#1760 and released in mio 0.8.11, while this tree pins mio 1.2.2 / tokio 1.53.1. The Windows run after this commit is the first live exercise of the stress step; if it ever reports `0xC0000374` again, that step is the amplifier, and a WER `LocalDumps` crash dump (or Application Verifier's heap checks on the CLI) is the next evidence to collect before touching the client path. |

## v0.7.1 - Trust Boundary Hardening

The October 2026 security audit (a read-only review at commit `97eec6b`: the Rust crates, the GDScript GUI, `cargo audit`, semgrep and proofs of concept in an isolated sandbox) found no remote-code-execution or memory-safety bug in the Rust core; its weaknesses are trust boundaries around the control socket and around files the GUI loads. Every item below was re-checked on 2026-10-19 against `5cf373a` plus the working tree, and each item says how: **re-run** (the probe was executed again), **measured**, or **re-read** (the code is unchanged and the original proof of concept was not repeated). None had been closed since the audit; two (the profile-consent item and the release-token item) turned out narrower than first reported, and the text says so. The audit also left two memory-growth concerns untested; both are measured here, and one of them (an unterminated escape string) is unbounded and became an item.

This is a patch release ahead of v0.8.0's UI work because most of these are reachable from data gPTY is documented to treat as untrusted (SECURITY.md: terminal output, files, other panes), and the first two were the project's own stated boundaries. Items are ordered by reachability and impact. The control-socket finding is split: its documentation half is closed here (the owner decided that gPTY's goal is for a pane not to be able to drive other panes without permission, so SECURITY.md now says plainly that this is not enforced yet), and its enforcement half is queued in v0.9.0, where the daemon's client model is decided. The threat model they are judged against is SECURITY.md's, and where an item changes behaviour that document changes in the same commit. Four build/CI rows were split into v0.7.2 on 2026-10-28 so this release's reachable fixes do not wait on repository policy; that section carries no runtime change.
