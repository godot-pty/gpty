## v0.7.1 - Trust Boundary Hardening

The October 2026 security audit (a read-only review at commit `97eec6b`: the Rust crates, the GDScript GUI, `cargo audit`, semgrep and proofs of concept in an isolated sandbox) found no remote-code-execution or memory-safety bug in the Rust core; its weaknesses are trust boundaries around the control socket and around files the GUI loads. Every item below was re-checked on 2026-10-19 against `5cf373a` plus the working tree, and each item says how: **re-run** (the probe was executed again), **measured**, or **re-read** (the code is unchanged and the original proof of concept was not repeated). None had been closed since the audit; two (the profile-consent item and the release-token item) turned out narrower than first reported, and the text says so. The audit also left two memory-growth concerns untested; both are measured here, and one of them (an unterminated escape string) is unbounded and became an item.

This is a patch release ahead of v0.8.0's UI work because most of these are reachable from data gPTY is documented to treat as untrusted (SECURITY.md: terminal output, files, other panes), and the first two were the project's own stated boundaries. Items are ordered by reachability and impact. The control-socket finding is split: its documentation half is closed here (the owner decided that gPTY's goal is for a pane not to be able to drive other panes without permission, so SECURITY.md now says plainly that this is not enforced yet), and its enforcement half is queued in v0.10.1, where the daemon's client model is decided. The threat model they are judged against is SECURITY.md's, and where an item changes behaviour that document changes in the same commit. Four build/CI rows were split into v0.7.2 on 2026-10-28 so this release's reachable fixes do not wait on repository policy; that section carries no runtime change.

## v0.7.2 - Build & CI Hardening

The hygiene half of the October 2026 audit, split out on 2026-10-28 so the reachable fixes in v0.7.1 did not wait on a GitHub setting or a CI job: a fuzz harness, a `v*` tag ruleset, dependency-source policy and fencing `unsafe`. It was scoped as build, CI and repository policy with no runtime delta; on 2026-11-01 the owner folded in runtime fixes found on the v0.7.1 download and by the new fuzz harness (the shipped knowledge base would not open; the media probe leaked its read buffer per open) rather than cutting a release of its own, so the release carries those two fixes and the rest stays hygiene. The audit re-run stays in v0.7.1 deliberately: that release carries every audit fix, so its verification claim is whole.
