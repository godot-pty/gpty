v0.7.0 (2026-10-20) released the media pane, a Rust media backend over a pinned, minimal FFmpeg build. v0.7.1 is the release in progress: a trust-boundary hardening pass that came out of the October 2026 security audit, placed ahead of v0.8.0's UI work because most of its findings are reachable from data gPTY is documented to treat as untrusted. The next task in the roadmap is the first unchecked row below.

The CLI printed no stdout and no stderr, so the corruption happened during the call, not at exit; the same SHA's rerun of the same job passed that step, and the command has passed on every earlier commit. Each CLI command is a fresh process and makes two named-pipe connections (the best-effort `version` probe, then the command itself), so the plausible class is a Windows named-pipe client teardown race (mio/tokio), not a logic error in `inject`. Fix direction: keep the failure diagnosable (the smoke now tails the `--log-file` engine log and carries the pane tail plus the hex status), then reproduce with a Windows-only loop of throwaway `pane-status`/`inject` processes (N runs ≈ N connection teardowns) before changing anything; if it reproduces, test the CLI's runtime shape (`process::exit` from `#[tokio::main]` skips a clean runtime shutdown; a current-thread runtime removes worker-thread teardown entirely) and the mio client path. The runtime-shape half was applied rather than left waiting for a second occurrence: `crates/gpty-cli/src/main.rs` is now `#[tokio::main(flavor = "current_thread")]`. Every command is one request in a process that exits as soon as it has an answer, and nothing in the CLI or `gpty-ipc` uses `spawn_blocking`, `block_in_place` or `tokio::process`, so the multi-thread flavor's workers bought no parallelism - they were the only concurrency around `process::exit`, which is exactly what a worker torn down mid-allocation needs to corrupt the heap. It also removes the worker pool's startup from every invocation: measured on Linux, 300 `gpty version` runs went from 1.037 s to 0.599 s (3.46 → 2.00 ms each). The loop the item asked for is permanent now: `scripts/smoke_pane_api.py` runs 100 throwaway `pane-status` processes right after the pane-status checks - ≈ 200 connections, because each process opens the best-effort `version` probe and then its command - and a nonzero exit fails with its hex status, the pane tail and the engine-log tail, with no retry. Verified live: the Linux smoke passes with the new step, `cargo test -p gpty -p gpty-ipc` passes, and `./scripts/ci-check --fast` is green. The mio client path was not implicated: the only known heap-corruption class there is tokio#6369 (a `ScheduledIo` use-after-free when a named-pipe client disconnects), fixed by mio#1760 and released in mio 0.8.11, while this tree pins mio 1.2.2 / tokio 1.53.1. The Windows run after this commit is the first live exercise of the stress step; if it ever reports `0xC0000374` again, that step is the amplifier, and a WER `LocalDumps` crash dump (or Application Verifier's heap checks on the CLI) is the next evidence to collect before touching the client path. |

## v0.7.1 - Trust Boundary Hardening

The October 2026 security audit (a read-only review at commit `97eec6b`: the Rust crates, the GDScript GUI, `cargo audit`, semgrep and proofs of concept in an isolated sandbox) found no remote-code-execution or memory-safety bug in the Rust core; its weaknesses are trust boundaries around the control socket and around files the GUI loads. Every item below was re-checked on 2026-10-19 against `5cf373a` plus the working tree, and each item says how: **re-run** (the probe was executed again), **measured**, or **re-read** (the code is unchanged and the original proof of concept was not repeated). None had been closed since the audit; two (the profile-consent item and the release-token item) turned out narrower than first reported, and the text says so. The audit also left two memory-growth concerns untested; both are measured here, and one of them (an unterminated escape string) is unbounded and became an item.

This is a patch release ahead of v0.8.0's UI work because most of these are reachable from data gPTY is documented to treat as untrusted (SECURITY.md: terminal output, files, other panes), and the first two were the project's own stated boundaries. Items are ordered by reachability and impact. The control-socket finding is split: its documentation half is closed here (the owner decided that gPTY's goal is for a pane not to be able to drive other panes without permission, so SECURITY.md now says plainly that this is not enforced yet), and its enforcement half is queued in v0.9.0, where the daemon's client model is decided. The threat model they are judged against is SECURITY.md's, and where an item changes behaviour that document changes in the same commit.

| ✅ | SEC | **SECURITY.md states the pane / control-socket position the code actually has** - the audit showed, by running it, that a program in any pane can read and drive every other pane: the CLI inside a pane derives the default socket path from the inherited `XDG_RUNTIME_DIR` (the PTY layer strips only `GPTY_*`), the server's only gate is the peer's user id, and `GPTY_SECRET` is readable from the GUI's `/proc/<pid>/environ` because the pane's shell is the GUI's child - so `inject`, `pane-run`, `broadcast`, `new-pane`, `kill-pane` and `pane-read` (another pane's output as well as its input) are open to any process that can run in a pane, root shells and SSH sessions included; the mechanism was re-read on 2026-10-19 with the code unchanged. | ⬜ | SEC | **A pane label that exists in more than one workspace is resolved to the active workspace's pane, not the caller's** - **re-read** (`Workspace._find_pane_by_label`, used by `inject`, `pane-run`, `pane-read`, `pane-wait`, `kill-pane`, `focus-pane`): it searches the active workspace first and then every other one, and its own comment says labels (`T1`) collide across workspaces and attachment ids do not. The caller is not part of the lookup, so an agent running in workspace A while the user has switched to workspace B and sending `pane-run --pane T1 "rm -rf build"` delivers it to **B's `T1`** - a pane the agent never meant, with no error and nothing to show it happened. Ordinary use triggers it (labels restart per workspace, and the user switches tabs while an agent works in the background), so this is a correctness and data-loss hazard before it is a security one, and it is why it leads the release. Fix: a label that matches exactly one pane across all workspaces still resolves; a label that matches more than one is refused with an error that names each candidate's workspace and attachment id ("`T1` exists in workspaces A, B - use a pane id"), and an attachment id always resolves, since ids are unique. Do not pick the active workspace silently any more. `list-panes` and `broadcast` already stay within the active workspace and are not changed here. A pane client that learns candidate ids from the error gains nothing it could not already guess from labels; the real boundary is the v0.9.0 workspace scope. Tests: two workspaces that each hold a `T1` - an ambiguous label is refused and neither pane receives text; a label unique across workspaces resolves; an id resolves from either workspace; the refusal names both candidates. Extends `test_ipc_dispatch_contract`. |
| ⬜ | SEC | **A layout, profile or settings file can make the GUI `load()` an arbitrary resource, and loading one runs its embedded script** - **re-run** (the load) and **re-read** (the path to it); the one link not run end to end is a real layout file through the whole GUI. A `.tres` whose sub-resource is a GDScript runs its `_init` during `load()` - shown again today on Godot 4.7.2 for both a `res://` path and an absolute filesystem path, and `ResourceLoader.exists()` is true for both, so the existence check in `_load_font` is not a gate. How a file reaches it: `sanitize_tile` clamps `rows`/`cols` and the attachment id and passes the rest of a tile's `settings` through; `PaneBody.apply_settings` handles a few named keys and sends *every other key* to `_set_typed`, which sets any existing String/int/float/bool property the file names; `font_path`, `font_bold_path` and `font_italic_path` are exported strings on `TerminalPane` (and `font_path` is written into saved layouts by `_get_layout_state`, so a shared layout carries it), their setter calls `_reload_fonts`, and `_load_font` does `load(path)`. `settings.json`'s `font_path` takes the same road through `cfg_font_path`.
