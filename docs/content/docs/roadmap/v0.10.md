Two releases that turn the GUI into a rendering client of a headless daemon. v0.10.0 extracts `gptyd`, defines the grid wire protocol and makes attach/reattach work; v0.10.1 puts the control surface behind a permission the user grants and validates IPC parameters in Rust before dispatch.

## v0.10.0 - Daemon Extraction & Reattach

| Done | Area | Item |
|:---:|:---:|---|
| ⬜ | CORE | **`gptyd` extraction spike** - move `WorkspaceEngine` + `IpcServer` + event socket into a standalone Rust daemon; the Godot app becomes a rendering client over the same JSON-RPC (Godot-headless mode is the interim only, not the destination). PTYs survive GUI close. |
| ⬜ | CORE | **Grid wire protocol** - `term_get_diff` / `term_input` over the socket, reusing `TermGrid`'s packed flat arrays as the wire format. |
| ⬜ | CORE | **Attach/reattach** - GUI close leaves the daemon running; reopen attaches to the live workspace; `gpty attach` over SSH; `HistoryStore` serves pane read and scrollback across restarts. |

## v0.10.1 - Control-Surface Permission & Validation

| Done | Area | Item |
|:---:|:---:|---|
| ⬜ | IPC | **A pane id from another workspace resolves, but `focusPane` cannot bring it into view and `listPanes` cannot see it** - found while closing **A pane label that exists in more than one workspace is resolved to the active workspace's pane, not the caller's**: that fix makes an `attachment_id` resolve across every workspace, so `gpty focus-pane <id>` returns `{success: true}` while the user is looking at a different workspace and nothing visibly happens (`Workspace.activate_pane` records the pane in its own workspace and never calls `_switch_workspace`, and a hidden terminal's `grab_focus` is dropped by the engine), and `listPanes` still lists only the active workspace, so a caller learns another workspace's ids from the ambiguity error it just triggered (or by guessing), never from discovery. For a **pane client** the permission item above already decides the answer - another workspace is "not found", so this row is only about the **outside client** (the user's own terminal), the one caller that keeps cross-workspace reach: either a target in another workspace switches the view, which means deciding whether an outside client may move the user's view at all, or it is refused with an error naming the workspace; and `listPanes` gains a `workspace` field (and the id stays its key across workspaces) so the list is a discovery surface rather than a guess. Design the activation rule and the list shape together: a `focusPane` that switches the view while the list stays silent makes the ids it needs undiscoverable. |
| ⬜ | SEC | **Panes are separated from the control surface by a permission the user grants** - the enforcement half of the control-socket finding; the documentation half is closed under v0.7.1. Today a program in any pane can read and drive every other pane (SECURITY.md, Known limitations, has the mechanism), and gPTY's stated goal is that it cannot do so without permission. It is sequenced here, after attach/reattach, because the daemon changes who the clients are: a headless daemon or `gpty attach` over SSH has no GUI to show a consent dialog, so the consent channel has to be designed with the client model, not before it. Design: (1) *classify the caller* - a connection whose peer process descends from one of this daemon's pane shells (a parent-chain walk: `/proc/<pid>/stat` on Linux, `proc_pidinfo` on macOS, a process snapshot on Windows; an unsupported platform keeps today's behaviour rather than failing closed) is a **pane client**, anything else is an outside client with today's authority. On Linux prefer **cgroup membership** to the parent walk: run each pane in its own cgroup scope (`systemd-run --user --scope`, or a delegated subtree) and classify the peer by `/proc/<pid>/cgroup`, which survives a process reparenting to init or to a `systemd --user` subreaper; keep the parent walk as the fallback where no scope can be created; (2) *tier every method* - an explicit table next to the method registry puts each IPC method in observe (`list-panes`, `pane-status`, the pane's own state declaration), read (`pane-read`, `pane-wait`, the vault verbs) or control (`inject`, `pane-run`, `broadcast`, `new-pane`, `kill-pane`, layout and concept changes, plugin install), and a test fails when a registered method has no tier, so a new verb cannot ship unclassified; (3) *a user-owned grant* - a pane client gets observe by default and needs a grant for the higher tiers, stored in a user-owned store keyed by attachment id (the `PaneEnvStore` pattern: a file, profile or plugin can never grant it), shown on the pane's row and in its settings and revocable there; (4) *a policy of `allow` (today), `ask` or `deny`* - `ask` raises a consent dialog naming the pane, the method and what it would reach, once, remembered per pane; for a headless daemon the grant is pre-set through the user's own settings, never answered by a pane client. Which policy is the default is the owner's decision at pickup; `ask` is the recommendation, because it keeps the agent workflow (an agent in a pane calling `gpty inject` or `gpty mcp`, v1.0.0's launch demo) one click away while ending silent cross-pane control. (5) *scope is the workspace, with no grant that widens it* - a pane client's reach is its own workspace and nothing else: a command that names a pane in another workspace is answered exactly as a nonexistent pane ("not found", so the other workspace cannot be probed), and there is deliberately no grant, setting or `ask` prompt that crosses the boundary. Rejected alternative: a cross-workspace grant. The workspace is the unit the user already reasons about ("root things here, ordinary things there"); a permission that crosses it is the confused-deputy path, and it multiplies the grant matrix from pane × tier to pane × tier × workspace, which is how a permission model becomes impossible to explain or audit. The legitimate cases do not need it: an agent that runs tests in a pane while the user watches does so inside one workspace, and anything that really spans workspaces is done by the user from the GUI, by an outside client (their own terminal's `gpty`), or by moving the pane (v0.9.5). Outside clients keep today's reach across workspaces. A workspace marked sensitive (v0.9.5) is excluded from the socket altogether, for outside clients too. State the limit in SECURITY.md when it ships: a process that double-forks and reparents to init (or to a `systemd --user` subreaper) escapes the parent walk, and on systems without restrictive ptrace defaults a same-user process can also attach to the daemon or read its memory, so this is a speed bump against opportunistic scripts and injected agents, not a boundary against a determined local attacker. Tests: a pane-descendant client is refused at each tier it has not been granted and served at each it has; an outside client is unaffected; `ask` prompts once and remembers; a revoked grant is refused again; every registered method has a tier; a pane client naming a pane in another workspace, by id or by label, gets "not found" and nothing is delivered; the audit's two-pane probe, kept as a script by the v0.7.1 re-audit item, now fails to inject. On landing, rewrite the Known limitations entry and the in-scope line in SECURITY.md to say what is enforced. |
| ⬜ | IPC | **Rust-side IPC param validation** - deserialize and validate IPC request params in Rust (`gpty-ipc`) before dispatch. Promoted from Future: the daemon refactor is the natural home (Rust owns the request path end-to-end), and validating the pre-daemon GUI queue would be throwaway work.
