Ideas and gated work that is not scheduled. An entry here is either an idea that is not designed yet, or work that says in its own text what evidence would start it. Anything concrete and committed belongs in a numbered release, and moves there when it is defined.

| ⬜ | TERM | **Re-test the AT-SPI element-value mapping when an engine release carries it** - the v0.8.0 row measured 4.7.2 (2026-11-05, the newest release): `AccessibilityServer.update_set_value` and `update_set_role` never reach the exposed node, an element's name is the snapshot taken when it was created, and the adapter serves `Name` as a property with no role method and no `Text`/`Value` interface on a custom `Control`, so `A11y.set_value`/`set_text` only record a value AT cannot read. The app-side cost is closed (an idle pane no longer republishes the node a reader is on, see the v0.8.0 row), so what remains is engine-gated. Evidence to start: an engine newer than 4.7.2 whose adapter exposes a value or role path - `scripts/accessibility-probe` prints an `a11y-values:` line (`text-interfaces`, `value-interfaces`, `marker-in-value`, `role-names`) that grades it in one command. If it changes, the follow-up is to stop publishing text nodes where the value now reaches AT, not to keep both. |
| ⬜ | TERM | **Terminal graphics protocols and font ligatures** - sixel and the kitty graphics protocol (image previews in `yazi`, `chafa`, `timg`) and programming-font ligatures. Evidence-gated: none of these is in any release, and the October 2026 assessment found no user demand for either, only that they are absent. Graphics decode untrusted image data, so the media stance applies (memory-safe decoders only, size caps, no sandboxing claim), and the grid's packed-array wire format has no image channel, so it is a protocol addition for after v0.10.0. Ligatures need shaping across cell runs, which conflicts with the per-cell run batching and the procedurally drawn box characters from v0.9.1. Revisit with a concrete tool or user asking for either. |
| ⬜ | TERM | **Instanced-quad renderer (alacritty-style glyph atlas + per-instance color)** - evidence-gated: the 0.9.0 instrumentation is the measurement that would start it - revisit only if render batching plus flood rate-limiting still shows frame-time pain. Godot already GPU-composites the canvas; a full Rust-side texture pipeline is deep custom work (atlas management, eviction, per-cell truecolor uploads) for a small incremental gain. |
| ⬜ | WIKI | **A note near the 1 MiB render cap still costs ~1.1 s per settle render** - v0.6.0 removed the superlinear shape term (list tags; minutes → ~1 s for the largest note a pane reads) and moved the render off the keystroke, so typing is smooth; what remains is the linear cost of the update itself, dominated by Godot's shape pass (0.97 s of the 1.10 s for 1 MiB in release - the v0.6.0 closure carries the full table). Evidence-gated: act only if editing a note near the cap in split mode still hurts. The item's own alternative is then a *paused* preview past a size threshold (a "preview updates when you ask" state with an explicit render action) - a UX decision, not a performance one - and `edit` mode already renders nothing. Not by lowering the render cap (the silent-prefix bug) and not by hiding the shape (the label has to lay out what it shows). |
| ⬜ | WIKI | **Declared link weights cannot follow a note moved outside gPTY** - the wiki pane's rename now re-keys both endpoints (2026-10, closed above), but a move made in a file manager looks exactly like a delete to the index: the next complete graph prunes the declarations as vanished, and an outside move cannot be told apart from a deletion, so guessing would attach authored data to a path the index never saw. Display-only loss with a small blast radius. Fix direction only if a user reports it: an explicit graph-side "re-link declarations from &lt;old path>" action seeded by the vanished endpoint, or a one-graph tombstone the prune respects - neither is worth building ahead of demand. |
| ⬜ | TERM | **Windows foreground-job detection** - the close confirmation's `foreground_job` is exact on Unix (`tcgetpgrp`) and `null` on Windows/ConPTY, so the GUI treats every live shell as possibly busy: closing or quitting with any terminal open raises the confirmation even at an idle prompt (the v0.7.0 item's documented fallback). If that proves noisy in use, the fix is a Windows-side direct-child snapshot (`CreateToolhelp32Snapshot` + `Process32NextW`, the raw-extern pattern `pin_library`/`win_peer` already use) compared against the shell pid - conservative in the other direction (a background child counts) but far closer than "any live shell". No change until it is observed to annoy; the safe half is already in place. |
| ⬜ | IPC | **The named-pipe client's mio path is the last unexamined suspect for the Windows CLI heap corruption** - evidence-gated on the v0.7.0 teardown stress loop reporting `0xC0000374` again: the runtime change removed the worker-teardown class (the CLI is single-threaded around `process::exit` now) and the smoke runs 100 throwaway processes per Windows run (≈ 200 connections), so a recurrence is the evidence that the client path itself is corrupting memory. Do not start by reading mio: collect a WER `LocalDumps` crash dump of the CLI process first (registry `DumpFolder`; `DumpType` 2 for a full dump), or run the loop under Application Verifier with heap checks, because the historical class here - tokio#6369, a `ScheduledIo` use-after-free on named-pipe disconnect - was fixed in mio 0.8.11 and this tree is on mio 1.2.2; a dump says whether it is that shape, a cancellation race on the eagerly-scheduled read (mio schedules a read at registration; teardown cancels it and the completion is processed later), or something outside the client entirely. |
| ⬜ | SEC | **On macOS a program in a pane can read `GPTY_SECRET` from the GUI's or a client's environment** - Linux closes this path with a non-dumpable process (v0.7.1, closed above), but macOS exposes every process's environment to same-user readers through `KERN_PROCARGS2` (`ps -E`, `pgrep`), and `ptrace(PT_DENY_ATTACH)` does not change that - it only denies a debugger, which is why the v0.7.1 row claims nothing for macOS. On macOS the secret therefore remains protection against other users only, and SECURITY.md says so. Evidence to start: a measurement showing a client can authenticate without the secret ever entering its initial environment (an inherited file descriptor or a broker handshake), because `unsetenv` only changes the `environ` array, not the initial block those APIs read. Without such a mechanism this stays a documented limitation rather than a task. |
| ⬜ | BUILD | **Desktop-control agents are not part of the capture pipeline** - evaluated `agent-sh/computer-use-linux` (2026-10-31) for release screenshots, UI-audit evidence and demo recordings; every job is already covered without a privileged input path. Evidence captures are the app's own viewport (`root.get_texture().get_image()`, `godot/tests/bench/draw_bench.gd:112`), which needs no compositor, portal, XWayland or window targeting, and `scripts/record-demo` records an X11/XWayland window with ffmpeg while driving it through the `gpty` CLI, so the tool's AT-SPI selectors and Wayland window targeting solve nothing here, its screenshots arrive bounded to 1920 px / 2 MiB and possibly JPEG (a KDE Wayland grab is either the same X11 root image or a portal capture cropped after the fact), and it has no video capture at all. Its real cost is `/dev/uinput` or the RemoteDesktop portal plus `destructiveHint` click/drag/type, which would repeal `record-demo`'s documented "never touches your keyboard, pointer, or input permissions". Reopening evidence: capture has to work on a pure-Wayland session without XWayland - the one gap both scripts carry, and the fix there is a native recorder (`wf-recorder`, KDE ScreenCast into ffmpeg), not an MCP - or a UI defect proves the OS input path itself, where `xdotool` against the XWayland client (`--display-driver x11`) is the one-probe tool. |
| ⬜ | BUILD | **Agent-config linters are not a CI gate (agnix evaluated)** - ran `agent-sh/agnix` 0.60.2 (2026-10-31) over `.omp/skills`, `crates/gpty-cli/skills/gpty/SKILL.md`, `AGENTS.md` and `mcp.json`: 0 errors on every real config, and 28 of the 32 whole-repo findings are false positives on the Hugo guide pages under `docs/content/docs/agents/` (CC-AG-002/CC-AG-019 read their `title`/`weight` frontmatter as a Claude Code subagent that is missing `description`), plus CDX-AG-002 firing on `id-token: write` in the licensing paragraph. The signal that survives is four rules, all satisfied today: frontmatter shape, name equals directory, description within 1024 chars, body under 500 lines and ~5000 tokens (`release` is the largest at 212 lines / ~4800 tokens). Learnings kept from it: (1) AS-020 wants the description to say when to load the skill - 10 of ours say only what it does, which matters only outside OMP, because OMP caches generated trigger descriptions in `~/.omp/agent/skill-descriptions.db` and injects those instead of the file text; (2) `$1`-`$9` and `$ARGUMENTS` are substituted into skill bodies by clients with skill arguments (OMP does it for slash commands, Claude Code for skills), so `gpty-live-gui-smoke`'s `awk ... $2` would lose its field if the skill ever leaves OMP; (3) the reusable artifact is the machine-readable rules catalog (`knowledge-base/rules.json`, with severity, normative level, source URL and good/bad example per rule) - the 26 Agent Skills rules were applied here from it without installing anything. Reopening evidence: a skill ships for a client other than OMP, or a skill approaches the body budget - then add a dependency-free `scripts/check-skills` instead of the linter. |
