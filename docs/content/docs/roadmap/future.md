| ⬜ | TERM | **Deleting a double-clicked word from the shell's input line** - requested 2026-11-17: double-click a word inside the command being typed, then delete it, instead of reaching for the shell's own `Ctrl+W` / `Alt+Backspace`. The idea is useful, but the terminal has no model of the line editor's buffer, so the naive "move the cursor to the selection's end, send Ctrl+W" has four correctness holes. (1) *No prompt boundary*: the grid knows the cursor cell (`get_cursor_row`/`get_cursor_col`, `crates/gpty-gdext/src/grid_api.rs:15-30`) but not where the command starts, and OSC 133 is not parsed (`crates/gpty-core/src/parser.rs:19-21` interprets only `gpty_state`), so a word highlighted in the prompt - which is not in readline's buffer - would send the edit to the command instead, deleting text the highlight never covered. (2) *Cells are not characters*: the grid stores a char per cell plus `wide` and zero-width spacers (`crates/gpty-core/src/term.rs:50-60`, `:368`), so an arrow count derived from columns lands in the wrong place in CJK, combining-mark or emoji text. (3) *Ctrl+W is the child's widget, not the highlighted span*: readline's `\C-w` is `unix-word-rubout`, which stops at whitespace (measured with `bind -p` on bash), while alacritty's semantic word splits on commas, colons, quotes, brackets, spaces and tabs but not on `/`, `.`, `-` or `_` - so a highlighted `foo:bar` and a kill-word disagree, and vi mode, fish and zsh widgets differ again. (4) *The child may not be a line editor*: `cat`, `read`, a REPL, a TUI, an SSH target or a password prompt takes the same bytes as data, so a "delete" can write a `^W` into a file or send it to a remote host - the first UI action that would synthesize control input from screen contents, which the paste filter in `docs/content/docs/agents/security.md:11` exists to prevent. Nothing verifies the result either: the app cannot tell whether the child removed the highlighted span or a different one, and there is no undo. A right-click `Delete word` item is the right form of the risky version - explicit, with no accidental-chord risk - but it is the same synthetic edit and inherits all four holes, so the context-menu row in v0.9.5 deliberately carries no Cut or Delete; Copy and Paste there are unaffected because neither edits the child's buffer. Clicking in the command to place the cursor is the same class with a lower risk - a move is non-destructive - but it still needs the command boundary and it must send Up/Down, whose meaning in a multi-line buffer is the child's binding, not a protocol, so a click can land the edit in a recalled history entry; it is not queued because the shells' edit-command binding (see the v0.9.5 Keybindings row) already edits the exact buffer. What would start it: the v0.9.5 shell-integration row's OSC 133 marks, plus a design where the action is explicit (a context-menu `Delete word`, not a bare chord), the selection lies wholly inside the command span, and the primitive is Backspace times the selected *characters* rather than a shell kill word - then a probe across bash, zsh and fish in emacs mode showing the delete removes exactly the highlight. Even then a program can echo the marks itself, so the action stays a heuristic and must be described as one. |
