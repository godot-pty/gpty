| ⬜ | TERM | **Re-test the AT-SPI element-value mapping when an engine release carries it** - the v0.8.0 row measured 4.7.2 (2026-11-05, the newest release): `AccessibilityServer.update_set_value` and `update_set_role` never reach the exposed node, an element's name is the snapshot taken when it was created, and the adapter serves `Name` as a property with no role method and no `Text`/`Value` interface on a custom `Control`, so `A11y.set_value`/`set_text` only record a value AT cannot read. The call side is fixed since v0.8.3: 4.7.2's server refuses `update_set_role`/`update_set_value` outside `NOTIFICATION_ACCESSIBILITY_UPDATE` (two engine errors per launch before), so `A11y` queues the pair and its host writes it from that notification - the re-test now grades the adapter's mapping rather than a refused call. The app-side cost is closed (an idle pane no longer republishes the node a reader is on, see the v0.8.0 row), so what remains is engine-gated. Evidence to start: an engine newer than 4.7.2 whose adapter exposes a value or role path - `scripts/accessibility-probe` prints an `a11y-values:` line (`text-interfaces`, `value-interfaces`, `marker-in-value`, `role-names`) that grades it in one command. If it changes, the follow-up is to stop publishing text nodes where the value now reaches AT, not to keep both. Re-measured 2026-11-13 on 4.7.2: the role write now reaches - a terminal pane's element answers `GetRole` and exposes `org.a11y.atspi.Text` - while `Text.GetText(0, -1)` on that element still answers `""` for a screen the app pushed, so an element value carries nothing and the published name remains the only channel that works. |
| ⬜ | TERM | **Terminal graphics protocols and font ligatures** - sixel and the kitty graphics protocol (image previews in `yazi`, `chafa`, `timg`) and programming-font ligatures. Evidence-gated: none of these is in any release, and the October 2026 assessment found no user demand for either, only that they are absent. Graphics decode untrusted image data, so the media stance applies (memory-safe decoders only, size caps, no sandboxing claim), and the grid's packed-array wire format has no image channel, so it is a protocol addition for after v0.10.0. Ligatures need shaping across cell runs, which conflicts with the per-cell run batching and the procedurally drawn box characters from v0.9.1. Revisit with a concrete tool or user asking for either. |
| ⬜ | TERM | **Translucent, optionally blurred window backgrounds** - evidence: the whole-environment theme kits the colour work targets pair their palette with a background opacity near 0.97 and compositor blur, and only the host window can honour either (a program in a pane can set an opaque colour, never an alpha or a blur). gPTY paints the terminal background in Godot, so the opacity half is a window flag plus an alpha on the palette background; blur is platform-native (a compositor rule behind a Wayland/X11 window, DWM acrylic on Windows, a visual effect view on macOS) and would sit behind a capability check with an opaque fallback. Not started because no row needs it and the cost is unmeasured; the probe that starts it: a transparent Godot window with the terminal drawn at 0.97 alpha on each platform, measuring text contrast on the composited result (WCAG, not the token's own ratio) and cost per frame. |
| ⬜ | TERM | **Instanced-quad renderer (alacritty-style glyph atlas + per-instance color)** - evidence-gated: the 0.9.0 instrumentation is the measurement that would start it - revisit only if render batching plus flood rate-limiting still shows frame-time pain. Godot already GPU-composites the canvas; a full Rust-side texture pipeline is deep custom work (atlas management, eviction, per-cell truecolor uploads) for a small incremental gain. |
| ⬜ | TERM | **The view cannot reach scrollback older than the grid's 10,000 lines** - the new chevron jumps to the oldest line the alacritty grid holds, and the grid is always built by `TermGrid::new` (`crates/gpty-core/src/engine.rs:341`, `scrolling_history: 10_000`), so rows past that cap exist only in the SQLite store (bounded by `History lines`, up to 100,000) and only the History search reads them; a restore feeds the newest `history_lines` rows back into the same 10k grid and drops the rest. Fix direction: a paged, read-only history surface that queries `HistoryStore` by line number - not a larger grid cap, which is the per-pane memory bound the cap exists to keep. Evidence to start: a user needs a line FTS finds but the viewport cannot scroll to. |
| ⬜ | WIKI | **A note near the 1 MiB render cap still costs ~1.1 s per settle render** - v0.6.0 removed the superlinear shape term (list tags; minutes → ~1 s for the largest note a pane reads) and moved the render off the keystroke, so typing is smooth; what remains is the linear cost of the update itself, dominated by Godot's shape pass (0.97 s of the 1.10 s for 1 MiB in release - the v0.6.0 closure carries the full table). Evidence-gated: act only if editing a note near the cap in split mode still hurts. The item's own alternative is then a *paused* preview past a size threshold (a "preview updates when you ask" state with an explicit render action) - a UX decision, not a performance one - and `edit` mode already renders nothing. Not by lowering the render cap (the silent-prefix bug) and not by hiding the shape (the label has to lay out what it shows). |
| ⬜ | WIKI | **Declared link weights cannot follow a note moved outside gPTY** - the wiki pane's rename now re-keys both endpoints (2026-10, closed above), but a move made in a file manager looks exactly like a delete to the index: the next complete graph prunes the declarations as vanished, and an outside move cannot be told apart from a deletion, so guessing would attach authored data to a path the index never saw. Display-only loss with a small blast radius. Fix direction only if a user reports it: an explicit graph-side "re-link declarations from &lt;old path>" action seeded by the vanished endpoint, or a one-graph tombstone the prune respects - neither is worth building ahead of demand. |
| ⬜ | TERM | **Windows foreground-job detection** - the close confirmation's `foreground_job` is exact on Unix (`tcgetpgrp`) and `null` on Windows/ConPTY, so the GUI treats every live shell as possibly busy: closing or quitting with any terminal open raises the confirmation even at an idle prompt (the v0.7.0 item's documented fallback). If that proves noisy in use, the fix is a Windows-side direct-child snapshot (`CreateToolhelp32Snapshot` + `Process32NextW`, the raw-extern pattern `pin_library`/`win_peer` already use) compared against the shell pid - conservative in the other direction (a background child counts) but far closer than "any live shell". No change until it is observed to annoy; the safe half is already in place. |
| ⬜ | IPC | **The named-pipe client's mio path is the last unexamined suspect for the Windows CLI heap corruption** - evidence-gated on the v0.7.0 teardown stress loop reporting `0xC0000374` again: the runtime change removed the worker-teardown class (the CLI is single-threaded around `process::exit` now) and the smoke runs 100 throwaway processes per Windows run (≈ 200 connections), so a recurrence is the evidence that the client path itself is corrupting memory. Do not start by reading mio: collect a WER `LocalDumps` crash dump of the CLI process first (registry `DumpFolder`; `DumpType` 2 for a full dump), or run the loop under Application Verifier with heap checks, because the historical class here - tokio#6369, a `ScheduledIo` use-after-free on named-pipe disconnect - was fixed in mio 0.8.11 and this tree is on mio 1.2.2; a dump says whether it is that shape, a cancellation race on the eagerly-scheduled read (mio schedules a read at registration; teardown cancels it and the completion is processed later), or something outside the client entirely. |
| ⬜ | SEC | **On macOS a program in a pane can read `GPTY_SECRET` from the GUI's or a client's environment** - Linux closes this path with a non-dumpable process (v0.7.1, closed above), but macOS exposes every process's environment to same-user readers through `KERN_PROCARGS2` (`ps -E`, `pgrep`), and `ptrace(PT_DENY_ATTACH)` does not change that - it only denies a debugger, which is why the v0.7.1 row claims nothing for macOS. On macOS the secret therefore remains protection against other users only, and SECURITY.md says so. Evidence to start: a measurement showing a client can authenticate without the secret ever entering its initial environment (an inherited file descriptor or a broker handshake), because `unsetenv` only changes the `environ` array, not the initial block those APIs read. Without such a mechanism this stays a documented limitation rather than a task. |
| ⬜ | BUILD | **Desktop-control agents are not part of the capture pipeline** - evaluated `agent-sh/computer-use-linux` (2026-10-31) for release screenshots, UI-audit evidence and demo recordings; every job is already covered without a privileged input path. Evidence captures are the app's own viewport (`root.get_texture().get_image()`, `godot/tests/bench/draw_bench.gd:112`), which needs no compositor, portal, XWayland or window targeting, and `scripts/record-demo` records an X11/XWayland window with ffmpeg while driving it through the `gpty` CLI, so the tool's AT-SPI selectors and Wayland window targeting solve nothing here, its screenshots arrive bounded to 1920 px / 2 MiB and possibly JPEG (a KDE Wayland grab is either the same X11 root image or a portal capture cropped after the fact), and it has no video capture at all. Its real cost is `/dev/uinput` or the RemoteDesktop portal plus `destructiveHint` click/drag/type, which would repeal `record-demo`'s documented "never touches your keyboard, pointer, or input permissions". Reopening evidence: capture has to work on a pure-Wayland session without XWayland - the one gap both scripts carry, and the fix there is a native recorder (`wf-recorder`, KDE ScreenCast into ffmpeg), not an MCP - or a UI defect proves the OS input path itself, where `xdotool` against the XWayland client (`--display-driver x11`) is the one-probe tool. |
| ⬜ | BUILD | **Agent-config linters are not a CI gate (agnix evaluated)** - ran `agent-sh/agnix` 0.60.2 (2026-10-31) over `.omp/skills`, `crates/gpty-cli/skills/gpty/SKILL.md`, `AGENTS.md` and `mcp.json`: 0 errors on every real config, and 28 of the 32 whole-repo findings are false positives on the Hugo guide pages under `docs/content/docs/agents/` (CC-AG-002/CC-AG-019 read their `title`/`weight` frontmatter as a Claude Code subagent that is missing `description`), plus CDX-AG-002 firing on `id-token: write` in the licensing paragraph. The signal that survives is four rules, all satisfied today: frontmatter shape, name equals directory, description within 1024 chars, body under 500 lines and ~5000 tokens (`release` is the largest at 212 lines / ~4800 tokens). Learnings kept from it: (1) AS-020 wants the description to say when to load the skill - 10 of ours say only what it does, which matters only outside OMP, because OMP caches generated trigger descriptions in `~/.omp/agent/skill-descriptions.db` and injects those instead of the file text; (2) `$1`-`$9` and `$ARGUMENTS` are substituted into skill bodies by clients with skill arguments (OMP does it for slash commands, Claude Code for skills), so `gpty-live-gui-smoke`'s `awk ... $2` would lose its field if the skill ever leaves OMP; (3) the reusable artifact is the machine-readable rules catalog (`knowledge-base/rules.json`, with severity, normative level, source URL and good/bad example per rule) - the 26 Agent Skills rules were applied here from it without installing anything. Reopening evidence: a skill ships for a client other than OMP, or a skill approaches the body budget - then add a dependency-free `scripts/check-skills` instead of the linter. |
| ⬜ | BUILD | **A review pass repeats its own verification work: the adjudications have nowhere to live** - measured 2026-11-08 on this tree: 24 slices through three lenses (a 12-13B local model, about 14 minutes of GPU) produced 195 findings, 165 distinct, 77 passing mechanical grounding, and after hand adjudication one new defect (the plugin output cap, queued in v0.9.5) - while about a dozen claims died on a *guard* worth remembering (`MAX_CAPTURE_BYTES` bounds the capture buffer, `note_path` rejects every non-`Normal` component, the audio resampler checks its sample arithmetic before allocating, IPC pending queues prune on timeout, `validate_program` refuses a relative PATH hit). None of it survives: the next pass pays the same hour of reading to reject the same claims, and a model cannot be told which ground is already settled. If built: (1) a one-line-per-entry JSONL ledger of *settled* claims (claim, file, symbol, verdict `open`/`fixed`/`rejected`/`accepted`, the refuting or protecting guard, the roadmap row for an `open` or `fixed` entry, and the model plus commit it was anchored at) checked by `scripts/check-review-ledger`: closed keys, an `open` entry's row title must exist on a chain page, a `fixed` entry's symbol and guard token must still exist, and `rejected` entries stay informational so an intentional refactor cannot trip it; (2) a local-only card runner - one file and one falsifiable question per call, accept only a JSON answer whose cited symbol and guard token exist in that file, retry once with the failure text appended, and refuse a card whose claim hash is already settled. Not committed: raw claims, evidence prose, line numbers or transcripts; a row stays the outcome, the ledger is the evidence a row cites, and no audit document is added. Entries anchor to a symbol and a commit because line numbers rot - the same pass produced a citation that `docs-check` rejects. Evidence to start it: the local profile stays in use for triage or changelogs and a second sweep would otherwise re-verify the same guards; the gate has a home beside `check-log-hygiene` in `ci-check` and in the gate table in `docs/content/docs/agents/testing.md`. |
| ⬜ | AGENT | **Hosting an `omp` session inside a gPTY pane is not the plan (ACP and RPC evaluated)** - `omp acp` (Agent Client Protocol over stdio, one command, no flags) and `omp --mode rpc\|rpc-ui` (versioned NDJSON, `omp://rpc.md`, protocol v1 with `rpc_chunk` reassembly for v2) would both let gPTY draw a *replacement* OMP TUI: structured assistant text, thinking, tool cards with `tool_result.content`, a real approval dialog, todo/plan state, and `get_entries`/`get_tree`/`get_messages_page`/`export_html`/`get_session_stats`/`session_info_update` for history. The Inspector already speaks a subset of that wire. Rejected for v1 because it moves L4 into core: hosting the user's session means gPTY owns auth prompts, tool approvals, the message queue, compaction and session lifecycle - the orchestration AGENTS.md's ADE boundary leaves to the ecosystem - and the pane would drift with every OMP release. Observation through the event socket (v0.14.1) plus the Inspector's private tool-free session covers what a display-only layer owes the user. Reopening evidence: a user-visible capability that cannot be expressed as observation - the plausible one is a structured diff-review surface for `edit`/`ast_edit` results, which needs `tool_result.content` rendering rather than session hosting, and would be built as a read-only projection over the transcript, not as an embedded agent. |
| ⬜ | AGENT | **Subagent work is invisible while it runs** - OMP has no per-subagent lifecycle or progress event (`omp://hooks.md`'s catalog: no spawn/child-progress entry; an extension's `ctx.agent` only names `{kind,id,name,depth,parentId}`), yet one `task` call can run several children for minutes and cost more than the parent turn - `stats.db`'s `agent_type='subagent'` rows show children at several times the parent's request count in this repo's own sessions. Three read paths exist and none is free: children's transcripts land as `<AgentName>.jsonl` in the session's sibling directory, `omp ps --json` lists daemon-supervised background jobs (not subagents), and RPC's `set_subagent_subscription{level}` streams child progress only in hosting mode (see the row above). Evidence that would start this: a user asking where a long turn's time or cost went. The cheap first step is a count-only chip ("3 agents") derived from the session directory's `*.jsonl` mtime window, never a progress view, because a per-child state machine is orchestration. |
| ⬜ | PROJECT | **Opt-in launch telemetry is the only install signal GitHub cannot provide** - the release badge sums every asset's cumulative download count with no timestamps, uniques, referrers or geo, so it counts the `SHA256SUMS` beside each archive, CI and mirror pulls, `gh release download` confirmations and v0.7.0's 36-asset multiplication. Measured 2026-11-09: 431 across all releases, while v0.8.0 (published 2026-11-06) showed 2 Linux, 0 macOS, 0 Windows and 0 checksum downloads - a documented-path human verifies the sum, so those 2 are self or bot - and the repository drew 53 unique viewers and 3 releases-page views in 14 days (2,758 clones against 376 workflow runs are CI, not people). Fix: move the existing startup update check (`update_checker.gd`, already one request per launch) to an endpoint we own that returns the latest-release JSON, with a separate default-off `cfg_telemetry` switch: when on, the request carries a locally generated, resettable UUIDv4 install id plus app version, OS, arch and event name; when off, no id, and the update request is unchanged. No IP, no machine id, no pane content; TLS with the existing timeout and body caps; aggregate retention only; a privacy note in the settings UI and docs. Serverless (Cloudflare Worker + D1/KV free tier) also stops every install spending GitHub's per-IP API rate limit. Answers what nothing else does: unique installs, DAU/WAU, version and OS split, update adoption, and download-to-first-launch conversion. Not scheduled because it creates an endpoint we must own and a consent/privacy design; evidence to start: a decision that needs the number (a grant or application, a launch retrospective, or a release whose download delta is cited). |
| ⬜ | GUI | **The palette's Save Command… seeds from the terminal's own selection** - evidence: the selection already lives in the grid (`TerminalPane._get_selected_text`), and the add form opens empty, so saving a command you just ran means retyping it from memory - the same friction the saved-commands row was filed for. Fix: when the active terminal holds a selection, the form's Command field starts from it, one line through `SavedCommandStore.clean_command` and capped at the same 1024 characters; with no selection the field stays empty, so the common case is unchanged. Not built with the v0.8.1 row because that row's contract is the store and the palette section, and the palette takes the keyboard as it opens - the grid's selection is the only thing that survives it, so this needs its own seam and its own test. |
| ⬜ | GUI | **A hidden workspace's streaming agent is unmeasured on the main thread** - `Workspace._route_agent_events` fans every drained envelope out to the receivers in the *source's* workspace, hidden workspaces included (their PTYs stay alive by design), so an OMP session streaming reasoning into `omp` while the user sits in `git` is work the visible workspace pays for: the Reasoning pane appends each delta and hands the accumulated turn to `MarkdownView.set_markdown`, which coalesces at `RENDER_DELAY` but still re-parses the turn (up to `reasoning_max_turn_bytes`, 64 KiB by default). Not measured - the 2026-11-09 workspace-switch investigation timed the switch only, and the reasoning-pane costs that were measured are the ones already fixed (the cap checks and the per-delta UTF-8 encoding). Evidence to start: a per-frame `Time.get_ticks_usec()` histogram over ~10 s while sitting in a second workspace with an OMP session streaming in the first, routing on against off, using the windowed timing recipe in `skill://gpty-live-gui-smoke`; any frame over the pane's work budget with the workspace hidden makes this a fix (drop hidden receivers from the per-event fan-out and deliver a coalesced turn on show, or drive them at the pane's own cadence), and a clean histogram closes it with a number instead of a guess. |
| ⬜ | GUI | **The agent badge's four tints are only contrasted against the shipped title-bar colour** - found 2026-11-10 while giving `working` a painted ring: `UiTokens.CONTRAST_PAIRS` (and `test_ui_palette`) check `ACCENT`, `SUCCESS`, `DANGER` and `WARNING` against `SURFACE_RAISED`, which is only the *default* `title_bar_bg` (`SettingsManager.cfg_title_bar_bg`, a free colour in the Appearance tab), so a user-set mid-tone or light bar can drop a badge below 4.5:1 with nothing noticing - the row that closed the badge's colour-only defect measured 4.80:1 as the tightest shipped pair and assumed the default bar.
